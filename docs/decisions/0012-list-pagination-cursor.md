# ADR-0012: 목록 페이지네이션 — 커서 방식 (`id` 기준)

- **상태**: accepted (2026-09-01)
- **결정자**: pm-lead (backend-dev 제안·구현·검증)
- **최초 적용**: [notification-list](../features/notification-list/api-contract.md) — `GET /api/v1/notifications`
- **관련**: [ADR-0010](./0010-datetime-model-localdatetime.md)(시간 규약 — **이 ADR 이 `created_at` 을 정렬 축에서 배제하는 근거와 맞물린다**) · [ADR-0007](./0007-environment-split.md)(배포 — 다중 인스턴스 시점)

> 🔵 **CLAUDE.md 규칙과의 관계.** 규칙 줄(*"페이지네이션은 프로젝트 전체에서 한 방식으로 통일 —

## 맥락

2026-09-01 이전까지 **이 프로젝트에는 페이지네이션이 하나도 없었다.** 목록을 반환하는
엔드포인트 전부가 조건에 맞는 행을 **전량 반환**했다 (실측):

| 엔드포인트 | 페이지 파라미터 | 자연 경계 |
|---|---|---|
| `GET /friends` | ❌ 0건 | 없음 — 친구 수만큼 |
| `GET /friends/requests/received` | ❌ 0건 | 없음 |
| `GET /rankings/losers` | ❌ 0건 | 친구 수 |
| `GET /challenges/active` | ❌ 0건 | 설계상 한정(진행 중 + 최근 종료) |
| `GET /challenges/received` | ❌ 0건 | 대기 중 도전장 |
| `GET /challenges/history` | `?month=` **있음** | 🔵 **월** — 페이지 경계 역할을 한다 |

백로그에 *"페이지네이션 일괄 도입"* 항목이 2026-08-26 부터 열려 있었고, **1순위 트리거는
계약서 보관함**이었다 — *"프로젝트 최초의 무한히 자라는 목록"*.

🔴 **2026-08-28 에 그 트리거가 소멸했다.** 보관함이 **월 단위 조회로 개정**되면서 한 응답의
상한이 한 달치로 고정됐다(mypage §1 v2). 남은 만기 신호는 친구·랭킹이 수백 건에 도달하는
경우뿐이라 항목의 우선순위가 내려갔다.

### 알림 목록이 그 자리를 그대로 물려받았다

| | 보관함 | **알림** |
|---|---|---|
| 자연 경계 | ✅ 월 (`?month=`) | ❌ **없다** |
| 증가 속도 | 챌린지 1건당 1행 | **챌린지 1건당 2~4행** (신청·수락/거절·인증) |
| 상한 | 한 달치 | **없음 — 계정 수명 내내 append** |

알림은 **날짜로 찾는 대상이 아니라 최근 것부터 훑는 대상**이라(design §6.2) 보관함이 쓴
월 축이 **애초에 생기지 않는다.** 백로그가 기다리던 만기 신호가 이것이었다.

🔴 **여기서 안 하면 첫 응답이 사용자 수명 전체를 싣게 되고, 그건 나중에 고칠 때 breaking
change 다.** 페이지네이션은 **계약**이라 되돌리는 비용이 크다.

## 결정

### 1. 커서 페이지네이션. shape 은 이것으로 고정한다

```
GET /api/v1/{resource}?cursor={마지막 항목의 키}&size={N}
```
```json
{ "error": false, "code": 200, "message": "",
  "data": { "items": [ ... ], "nextCursor": 38 } }
```

| | 규약 |
|---|---|
| `cursor` | optional. **생략 = 첫 페이지.** 앱은 직전 응답의 `nextCursor` 를 **그대로 되돌려 보낸다** |
| `size` | optional. 기본값·상한을 각 계약이 정한다. 🔴 **범위 밖은 clamp 하지 말고 `code 700` 으로 거부** |
| `nextCursor` | **nullable 절대값.** `null` = 끝. 🔴 **`hasNext` 불리언 금지** |
| 정렬·커서 키 | **동일해야 한다.** 기본은 **`id DESC`** |
| 총 개수 | **주지 않는다.** `COUNT` 쿼리를 걸지 않는다 |

**구현**: `size + 1` 건을 읽어 초과분이 있으면 잘라 내고 마지막 항목의 키를 `nextCursor` 로,
없으면 `null`.

🔵 **첫 호출이 파라미터 없이 성립하는 것이 설계다.** 앱은 커서를 **만들지 않는다.**
보관함 `?month=` 를 optional 로 둔 것과 같은 판단이며, *"클라이언트가 경계값을 스스로 계산하지
않게 한다"* 는 이 프로젝트의 반복 규약이다(`KstDeadlineCalculator` KDoc — 기기 시계 배제).

### 2. 커서는 **소비되지 않는다**

서버가 상태로 들고 있는 토큰이 아니라 **키 비교값**(`WHERE id < :cursor`)이다. 그래서:

- 같은 커서를 몇 번 보내도 **같은 페이지**가 온다 → **부분 실패 후 재시도를 같은 커서로** 할 수 있다
- **없는 키를 보내도 에러가 아니다** — 그보다 작은 것들이 온다(실측 `cursor=99999` → 200).
  커서로 들고 있던 행이 그 사이 삭제돼도 목록이 이어진다
- 만료가 없다

## 근거

### 🔴 근거 1 — offset 을 기각한다. 이 도메인에서 **상시** 깨지기 때문이다

| | offset (`?page=&size=`) | **커서 (채택)** |
|---|---|---|
| 머리에 새 행이 들어오는 동안 | 🔴 페이지가 밀려 **2페이지에 1페이지 항목이 다시 나온다** | ✅ 영향 없음 |
| 총 개수 | 제공 가능 | 제공 안 함 (*"1/N 페이지"* 를 그리지 않는다) |
| Spring 지원 | `Pageable` 기성품 | JPQL 직접 |

⚠️ **일반론으로 고른 것이 아니다.** offset 의 shift 문제는 대부분의 목록에서 **드문 경합**이라
그것만으로는 기각 사유가 안 된다. 알림에서 결정적인 이유는 **알림이 정의상 새 행이 목록 머리에
꽂히는 화면**이라는 것 — 사용자가 스크롤하는 동안 **상대가 인증 한 번만 해도 발생한다.**
**예외가 아니라 상시 조건**이다.

🔵 알림·피드처럼 **머리에 append 되는 목록**이 앞으로도 생길 것이므로 프로젝트 기본값을
커서로 둔다.

### 🔴 근거 2 — 정렬·커서 키가 `created_at` 이 아니라 **`id`** 다. 이게 제일 잃기 쉽다

```sql
WHERE user_id = :me AND (:cursor 있으면) id < :cursor
ORDER BY id DESC
LIMIT :size + 1
```

**`created_at` 은 DB 가 만드는 값이 아니다.** `NotificationEntity.createdAt` 의 기본값이
`KstTime.now()` 이고 **엔티티가 값을 채워 INSERT 에 실어 보낸다**(컬럼 DEFAULT 는 있지만 쓰이지
않는다). 즉 **애플리케이션 시계가 NTP 보정으로 뒤로 밀리면, 나중에 삽입된 행이 더 이른
`created_at` 을 갖는 구간이 생긴다.**

🔴 **커서가 그 위에 서면 어긋난 구간의 행이 통째로 건너뛰어진다 — 예외도 로그도 남지 않는다.**
사용자에게는 *"알림이 그냥 안 왔다"* 로만 보이고 서버는 정상으로 보고한다.

`id` 는 `BIGSERIAL` 이라 시퀀스가 발급하므로 **삽입 순서와 정확히 일치**하고 **동률이 없다.**
동률이 없으니 `(created_at, id)` 복합 커서도 필요 없고 커서가 `Long` 하나로 끝난다.

> 🔴 **표시는 시각, 순서는 `id`.**
> 이 분리를 모르는 사람은 *"시간순 목록인데 왜 시간으로 정렬 안 하지"* 하며 되돌린다.
> **되돌리면 위 실패가 조용히 부활한다.** 응답에 `createdAt` 이 그대로 실려 있어 더 그렇게 보인다 —
> 그 필드는 **화면에 그리라고 있는 것이지 정렬하라고 있는 것이 아니다.**

🔵 선례와 정합한다 — 보관함이 `ORDER BY challengeDate DESC, c.id DESC` 로 `id` 를 tiebreak 에
쓴다. ADR-0010 이 프로젝트 전체를 KST 벽시계로 고정했지만 **그 규약은 값의 표기에 대한 것이지
순서의 신뢰성에 대한 것이 아니다.**

### 근거 3 — `nextCursor` 절대값. `hasNext` 불리언을 쓰지 않는다

[mypage §1](../features/mypage/api-contract.md) 이 `hasPrevious`/`hasNext` 를 기각하고 절대값
(`firstArchivedMonth`)으로 간 선례를 그대로 잇는다. 여기서는 논거가 더 직접적이다 —
**`nextCursor` 는 앱이 다음 요청에 그대로 실어야 하는 값 자체**다.

불리언을 주면 앱이 *"마지막 항목의 id 를 커서로 쓴다"* 는 **규칙의 사본**을 갖게 되고, 나중에
서버가 커서 표현을 바꾸는 날 **그 사본이 조용히 틀린다.** 절대값은 앱에 규칙을 두지 않는다.

⚠️ **`result`/`myResult` 처럼 "두 표현이 경쟁하는" 경우와 혼동하지 마라** — 여기서 불리언은
절대값의 **손실 있는 투영**이지 더 적은 신호가 아니다. `null` 하나가 *"끝"* 을 뜻하므로
경쟁하는 신호도 없다.

### 근거 4 — 인덱스는 **관측 후에 만든다**

페이지네이션과 인덱스는 **되돌리는 비용이 다르다.** 페이지네이션은 **계약**이라 나중에 바꾸면
breaking 이고, 인덱스는 **1줄 마이그레이션**이라 계약 영향 0으로 아무 때나 붙는다.
**지금 정해야 하는 것은 앞의 것뿐이다.**

⚠️ *"목록이 무한히 자란다"* 는 **앱이 받아 그려야 하는 payload** 얘기이지 **DB 정렬 비용** 얘기가
아니다. 둘을 같은 근거로 묶지 마라.

## 🔴 차등 검증 — "정렬됐다"가 아니라 "**어느 축으로** 정렬됐는지"를 증명한다

**대부분의 정렬 테스트는 두 축이 우연히 일치할 때 통과하고 어긋날 때만 틀린다.** 즉 평소에는
`id` 순이든 `created_at` 순이든 **똑같이 초록**이라 근거 2 를 아무도 지키지 못한다.

**기법: 두 축이 갈리도록 일부러 어긋나게 시드한다.**

```
id=1  created_at 2026-09-01 10:00
id=2  created_at 2026-09-01 11:00
id=3  created_at 2026-08-01 09:00   ← 🔴 가장 오래된 시각을 중간 id 에 준다
id=4..7  2026-09-01 12:00~15:00
```

| 정렬 축 | 기대 결과 |
|---|---|
| `created_at DESC` | `7, 6, 5, 4, 2, 1, 3` |
| **`id DESC`** | `7, 6, 5, 4, 3, 2, 1` |

**실측 결과: `7, 6, 5, 4, 3, 2, 1`** → `id` 축 확인.

🔵 **이 기법은 정렬·커서를 다루는 다른 작업에서 그대로 재사용한다.** 시드가 두 축을 갈라놓지
않으면 그 테스트는 **아무것도 증명하지 않는다.**

### 실행 환경 — 단위 테스트로는 이 축을 덮을 수 없다

⚠️ **이 레포의 단위 테스트는 JPA 를 auto-configuration 에서 제외하고 repository 를 mock 으로
세운다.** 즉 **통과한 540건 중 어느 것도 새 JPQL 을 실제 DB 에 실행하지 않는다.**
Testcontainers 통합 테스트는 컨테이너 런타임 부재로 상시 skip 이다.

그래서 **throwaway DB + 별도 포트**로 확인한다 — 🔴 **공용 `challenge` DB 와 `:8080` 불가침**,
종료 후 정리 확인까지. notification-list 에서 **21항목**을 이 방식으로 검증했다
([api-contract §8](../features/notification-list/api-contract.md)). 커서 관련 핵심:

- **커서 페이징 중복 0 / 누락 0** — `size=3` 으로 7건을 `[7,6,5]→[4,3,2]→[1]` 로 완주
- **마지막 페이지에서 `nextCursor: null`**
- **없는 커서(`99999`)는 에러가 아니다** — 200
- `?cursor=` `?size=` **빈 문자열 = 미지정**
- `size` 0·51·`abc` / `cursor=abc` → **HTTP 200 + code 700** (clamp 아님)

근거 1 의 실패가 규모와 무관하게 발생하기 때문이다.

## 결과

**좋은 것**
- 알림 목록이 계정 수명 전체를 한 응답에 싣지 않는다
- 프로젝트에 페이지네이션 방식이 **하나** 생겼다 — 다음 도입자가 설계하지 않아도 된다
- 정렬 축 결정(`id`)과 그 검증 기법이 문서로 남았다

**대가**
- `Pageable` 기성품 대신 **JPQL 을 직접 쓴다**(커서 유무로 메서드 2개. `(:cursor IS NULL OR ...)`
  단일 쿼리는 **null 파라미터의 타입 추론이 드라이버/방언 조합에 따라 갈려** 쓰지 않는다)
- **총 개수를 줄 수 없다.** *"전체 N건"* 을 그려야 하는 화면이 생기면 별도 COUNT 엔드포인트가
  필요하다 — 지금은 그런 화면이 없다
- 목록 API 마다 **정렬 축과 커서 키가 같은지**를 사람이 지켜야 한다. 어긋나면 조용히 깨진다
  (위 차등 검증이 그 방어다)

**미해결**
- 🟢 **목록 조회용 인덱스** — notification 은 `(user_id, id DESC)` 를 아직 만들지 않았다
  (근거 4). 관측 후 추가
- 🟢 **적용 확대 시점** — 백로그 항목으로 열려 있다

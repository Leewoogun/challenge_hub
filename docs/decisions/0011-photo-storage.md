# ADR-0011: 인증 사진 저장 — 서버 로컬 폴더 + `PhotoStorage` 포트

- **상태**: accepted (2026-08-14) — 🔴 **§3(URL 발급 방식)만 2026-08-18 사용자 결정으로 superseded** (multipart 직접 수신으로 전환, 아래 §3 참조). §1(로컬 폴더)·§2(`PhotoStorage` 포트)·§4(접근 제어)는 유지
- **결정자**: 사용자
- **관련**: [ADR-0007](./0007-environment-split.md)(local→AWS phased) · [ADR-0006](./0006-stt-strategy.md)(superseded — "음성 맹세"가 채택되면 이 ADR이 그 쟁점이 된다고 예고했다)

## 맥락

`challenge-verification` feature 는 사용자가 촬영한 **미션 수행 사진**을 받아 상대에게 보여준다.
`verifications.photo_url TEXT` 컬럼은 V1 부터 있었으나 **업로드 인프라가 통째로 없다** —
`S3` / `MultipartFile` / `presigned` / `Storage` 어느 것도 코드에 0건이고 `spring.servlet.multipart` 설정도 없다.

ADR-0007 이 *"local → AWS phased"* 를 정했지만 **저장 매체를 특정하지 않았다.** 여기서 처음 걸린다.

### 🔴 `soul-oath` 선례를 답습할 수 없다

`soul-oath` 는 `_signature_url` → `_signature_data` 로 바꿔 **값을 컬럼에 직접 넣었다.**
서명은 좌표 목록이라 가능했던 것이다.

**사진은 다르다.** base64 를 `TEXT` 에 넣으면 row 크기·응답 크기·JVM 메모리가 동시에 부푼다.
사진 한 장이 수 MB 이고 조회는 목록으로 일어난다. **같은 판단을 반복하면 안 되는 지점이다.**

## 제약

- **개인 프로젝트. 유료 서비스를 쓰지 않는다** (사용자 결정)
- **서버 호스팅이 아직 미정이다.** 현재 로컬 기동이고, 나중에 어딘가 올린다
- 규모가 작다 — 1:1 챌린지, 사용자당 하루 1~2장

## 결정

### 1. 지금은 **서버 로컬 폴더**에 저장한다

파일을 서버 파일시스템의 폴더에 쓴다. 외부 서비스·계정·시크릿이 **0개**다.
현재 개발이 로컬 기동이므로 **오늘 당장 정상 동작하는 유일한 선택**이기도 하다.

### 2. 🔴 `PhotoStorage` 포트 뒤에 둔다 — 이것이 이 ADR 의 본체다

```kotlin
interface PhotoStorage {
    fun issueUploadTarget(key: String): UploadTarget  // 업로드할 곳
    fun issueReadUrl(key: String): String             // 읽을 곳 (만료 있음)
    fun delete(key: String)
}
```

로컬 디스크 구현체를 먼저 만들고, 호스팅이 정해지면 **구현체만 교체**한다.
`NotificationSender` ↔ `FcmNotificationSender` / `NoOpNotificationSender` 와 같은 구조다
(`push-fcm` 결정사항 4번 — 그 격리 덕분에 Firebase 프로젝트를 기다리지 않고 백엔드를 완성했다).

### 3. ~~🔴 API 는 **URL 발급 방식**으로 고정한다~~ — 🔴 **superseded (2026-08-18, 사용자 결정)**

> **폐기 사유**: 앱이 릴리즈 전이라 구버전 호환 제약이 없고, 현재 규모(1:1 챌린지, 하루 1~2장)에서
> URL 발급 방식의 이득이 0 이다. 3단계 왕복(발급→PUT→확정)과 만료·재발급 처리 복잡도만 남는다.
> **앱이 서버 API 에 multipart 로 직접 올리고 서버가 저장까지 한 번에 처리한다.**
>
> **인지된 트레이드오프**: 저장소 이사(PaaS化) 시 서버가 스토리지로 중계하거나 그때 presigned 로
> 전환하는 비용을 감수한다 — 아래 원문이 예고한 바로 그 비용이다. 원문은 기록으로 남긴다.
>
> ~~⚠️ **조회는 바뀌지 않는다.** `GET /verifications` 가 만료 있는 서명 `photoUrl` 을 내려주는
> 현행 방식 유지 — JWT 보호 이미지 엔드포인트로 바꾸면 앱 이미지 로더에 인증 헤더를 심어야 해서
> 오히려 복잡해진다.~~
>
> 🔴 **위 단서는 같은 날 2차 결정으로 철회됐다 (2026-08-18, 사용자).** 조회도 서명 URL 을 폐기하고
> **JWT 보호 엔드포인트의 서버 경유 서빙**으로 통일한다. 당시 근거였던 *"이미지 로더에 인증 헤더를
> 심는 복잡도"* 는 성립하지 않는 것으로 확인됐다 — Coil 3 의 `coil-network-ktor3` 는 앱의 기존 인증
> `HttpClient` 를 그대로 받으므로 JWT 첨부·토큰 갱신이 추가 배관 없이 적용된다. §4 참조.

<details><summary>폐기된 원문 (2026-08-14)</summary>

앱이 서버에 파일을 직접 밀어넣는(multipart) 대신, **서버가 "여기에 올려라"를 알려주고 앱이 그리로 올린다.**

**이유**: 나중에 오브젝트 스토리지로 옮기면 업로드 대상이 서버가 아니라 스토리지가 된다.
multipart 로 시작하면 그때 **API 계약과 앱 코드를 함께 고쳐야 한다.** URL 발급으로 시작하면
**앱은 무변경**이고 서버 구현체만 바뀐다.

> ⚠️ 로컬 디스크 단계에서는 그 URL 이 결국 우리 서버를 가리킨다. **형태만 미리 맞추는 것**이고
> 지금 당장의 이득은 없다. 이득은 이사할 때 나온다. `push-fcm` 이 `challengeId` 를 미리
> 실어 둬서 `push-deeplink` 의 서버 변경이 0 이었던 것과 같은 종류의 선투자다.

</details>

### 4. 🔴 접근 제어는 **서버가 한다**

> 🔴 **수단 변경 (2026-08-18, 사용자 결정 — 원칙은 유지)**: ~~만료 있는 서명 읽기 URL 발급~~ →
> **요청 시점 JWT 당사자 검사 + 서버 경유 바이트 서빙** (`GET /challenges/{id}/photos/{party}` 형태).
> `exp`/`sig` 서명 체계와 비인증 `/api/v1/photos` 경로는 제거한다. 업로드 multipart 전환(§3 supersede)과
> 같은 원리다 — **지금 규모에서 안 쓰는 유연성에 복잡도를 지불하지 않는다.**
> 기록: 저장소 이사로 서버 경유가 부담이 되면 이 엔드포인트가 스토리지 서명 URL 로 **302 리다이렉트**하는
> 확장 경로가 있다 — 앱 무변경.

인증 사진은 **당사자 2명만** 봐야 한다. 이 앱은 Firebase Auth 가 아니라 **자체 JWT** 를 쓰므로,
스토리지의 규칙 엔진(Firebase Security Rules 등)은 *"이 사람이 이 챌린지의 당사자인가"* 를 판정할 수 없다.

**→ 서버가 당사자를 검사한다.** 이 구조는 저장소가 바뀌어도 유지된다.
(~~만료가 있는 읽기 URL 을 발급한다~~ — 수단은 위 2026-08-18 결정으로 JWT 직접 서빙으로 바뀌었다.)

`ChallengeDetailService` 가 이미 같은 검사를 한다(*"당사자만 볼 수 있다 — 계약서에는 양측의 미션·서명이 들어 있다"*).

## 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **DB 컬럼에 base64** | row·응답·메모리가 동시에 부푼다. `soul-oath` 서명과 달리 사진은 크기가 다른 문제다 |
| **Firebase Storage** | 서버에 `firebase-admin` 이 이미 있어 매력적이지만, **결제 플랜 등록이 필요할 수 있다.** "유료 서비스를 쓰지 않는다" 제약에 정면으로 걸릴 위험이 있어 1순위에서 뺐다. ⚠️ 확인은 사용자 몫 |
| **S3 / R2 즉시 도입** | 새 계정·시크릿·SDK 가 필요하고, **호스팅이 안 정해진 상태에서 고르면 근거가 없다.** 포트를 두면 나중에 고를 때 비용이 작다 |
| **multipart 로 서버가 직접 수신** | ~~이사할 때 앱까지 고쳐야 한다 (§3)~~ → 🔴 **2026-08-18 이 안으로 전환** (§3 supersede). 릴리즈 전 + 현재 규모에서 URL 발급의 이득이 0 이라는 사용자 판단 |

## 결과 / 후속

### 지금 생기는 부채 (인지하고 받는다)

- 🔴 **서버가 죽으면 사진도 죽는다.** 백업이 없다. 개인 프로젝트 초기 단계라 수용한다
- 🔴 **PaaS 형 호스팅으로 가면 이 방식이 깨진다** — 재배포 시 파일이 사라진다.
  **VM 형(디스크 영속)이면 그대로 쓸 수 있다.** 호스팅 결정이 이 부채의 만기다
- 정적 파일 서빙을 서버가 한다. 규모가 작아 지금은 무의미하나 이사 시점의 신호로 본다

### 호스팅이 정해질 때 다시 볼 것

| 호스팅 모양 | 조치 |
|---|---|
| **VM 형** (디스크 영속) | **그대로 유지.** 추가 서비스 0. 백업만 별도 고려 |
| **PaaS 형** (디스크 휘발) | 오브젝트 스토리지 구현체 추가. S3 호환(R2 등)이면 조회 트래픽 비용이 유리 |

### 별도로 정해야 할 것 (이 ADR 범위 밖)

- **보관 기간** — 챌린지 종료 후 삭제 여부. 랭킹·전적은 사진 없이 성립한다. 안 지우면 용량이 단조 증가
- 🔴 **앱에서 리사이즈** — 장당 ~500KB 목표. **저장소 선택보다 실질 영향이 크다.**
  원본 그대로면 어떤 무료 한도든 금방 찬다. `challenge-verification` spec 에서 다룬다

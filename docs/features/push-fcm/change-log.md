### api-contract.md — §3 페이로드에 `android` 블록 추가

- **🔴 `notification`·`data` 블록은 무변경이다.** shape이 바뀌면 모바일 파서와 이 `confirmed` 계약이 동시에 깨진다. 이번 변경은 `android` 블록 **추가**뿐이며, **모바일은 손댈 것이 없다** — `android.notification.tag`는 시스템 트레이가 소비하고 앱에 전달되지 않는다.
- **`android.notification.tag = "challenge-{referenceId}"`** — 같은 도전장 알림을 트레이에서 하나로 덮어쓴다(push-deeplink 판정 3). 포그라운드 경로는 이미 `challengeId`를 알림 id로 써서 덮어쓰고 있었으므로 **백그라운드를 포그라운드에 맞추는 정합성 작업**이다.
- 🔴 **`referenceId`가 `null`이면 tag를 붙이지 않는다** — `"challenge-null"`로 뭉치면 무관한 알림들이 한 덩어리가 되어 서로를 덮어써 **예외도 로그도 없이 알림이 사라진다.** `putData`가 `challengeId` 키를 조건부로 넣는 것과 같은 판단이고, **오픈 이슈 3(`reference_id`를 `challenge_id`로 못 박지 않는다)이 현실이 되는 순간 이 분기가 유일한 방어**다.
- **`android.priority = "high"`** — **오늘 기준 동작 변화 0.** FCM은 `notification`을 포함한 메시지를 이미 high로 취급한다(data-only만 normal이 기본). 새 동작을 켜는 게 아니라 **현재 실효 동작을 명시로 고정**해, 나중에 data-only로 바뀌어도(push-deeplink 판정 4에서 **보류**, 폐기 아님) 즉시성이 조용히 normal로 떨어지지 않게 한다.
  - ⚠️ **`RESULT`(자정 배치)·`REMIND`(마감 1시간 전 배치) 도입 시 재검토.** 자정 배치가 전 사용자 기기를 한꺼번에 Doze에서 깨우는 게 바로 high 남용 패턴이다. 타입별 분기는 **미리 만들지 않았다** — 근거를 정할 타입이 아직 없다.
- **회귀 장치 `FcmNotificationSenderTest` +6건 (4 → 10).** `AndroidConfig`에 공개 getter가 없어, firebase-admin이 **실제 전송에 쓰는 직렬화 경로**(`@Key` + `JsonFactory`)를 그대로 태워 **JSON 원문**으로 단언했다 — 술어를 Kotlin으로 다시 쓰는 §0.2 fake의 반대편이다.

  - 부수 효과로 `send()`의 **메시지 빌드부에 처음으로 테스트가 닿았다** — summary가 *"`send()`의 메시지 빌드·호출·catch는 어떤 테스트도 태우지 않는다"*고 적어 둔 공백의 일부.

### api-contract.md — §0.6.1 신설: 새 타입 **발송 개시** 전 모바일 통지

backend-dev와 mobile-dev-3이 독립적으로 같은 제안에 도달했고 pm-lead가 배정했다. **코드 변경 0건 — 규약만 추가한다.**

- **규약**: 서버는 새 `NotificationType`의 **발송을 시작하기 전에** 모바일에 통지한다. ⚠️ **enum에 값을 추가하는 것과 실제로 발송이 시작되는 것은 다른 사건**이고, 규약이 거는 것은 **후자**다.
- **오늘의 게이트 (실측)**: 3종 외 5종(`REMIND`/`OPPONENT_VERIFIED`/`RESULT`/`TAUNT`/`FRIEND_REQUEST`)은 `NotificationMessages.of()`가 `null`을 반환해 **발송이 구조적으로 불가능**하다. 🔵 **의도된 게이트지 미완성이 아니다** — 해당 함수 KDoc이 *"문구가 없으면 아예 보내지 않는 쪽이 맞다"*고 근거를 적어 뒀다.
- 🔴 **위험은 게이트가 풀리는 방식에 있다.** `NotificationMessages`에 문구 한 벌을 추가하는 것만으로 새 타입이 즉시 실사용자에게 도달한다 — 배관(`NotificationDispatcher` → `NotificationSender`)이 이미 전부 깔려 있어 **다른 승인 단계가 없고, 모바일은 그 사실을 알 방법이 없다.** 그래서 **"문구 추가 = 발송 개시"로 간주**하고, 통지 기준선을 enum 값 추가가 아니라 `of()`에 `Message`가 생기는 시점으로 잡았다.
- **통지 없이 개시하면**: 구버전 앱의 `PushEvent.from`이 모르는 `type`을 버려 **크래시는 없다 — 그래서 문제다.** 알림을 눌러도 아무 데도 가지 않고 앱은 열리므로 로그·크래시 리포트에 아무것도 안 남는다. push-deeplink spec §0.2의 *"조용히 홈에만 머무는"* 실패와 같은 모양.
- **왜 코드 방어가 아니라 계약인가**: 게이트를 푸는 사람과 라우팅을 붙이는 사람이 다른 레포에 있고 **서버 변경만으로 완결되므로, 서버 안에는 모바일을 멈춰 세울 지점이 없다.**
- 🔵 **`FRIEND_REQUEST`는 통지 항목이 하나 더 있다** — 개시되는 순간 §0.1(`challengeId` 키 조건부 누락)과 §3.1(`android.notification` 블록 조건부 부재)이 **처음으로 실제 발생**한다. 통지에 `referenceId`가 무엇을 가리키는지를 함께 넣어야 한다. 오픈 이슈 3이 `reference_id`를 못 박지 않은 대가를 치르는 지점이다.

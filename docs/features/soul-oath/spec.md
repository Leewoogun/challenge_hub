# 영혼의 맹세 (soul-oath)

- **feature-id**: soul-oath
- **owner**: pm-lead
- **상태**: draft
- **생성**: 2026-08-03

> 이전 문서들이 `contract-signing`이라는 가칭으로 언급한 feature다(`home-feed/backend-report.md`, `challenge-create/spec.md`). 제품 개념명(영혼의 맹세 / SOUL CONTRACT)을 따라 `soul-oath`로 확정한다.

## 배경 / 문제

제품 컨셉의 **핵심 차별점**이다 — repos.json `concept`: *"친구와의 1:1 약속에 책임감을 부여하는 챌린지 앱. **영혼의 맹세(계약서)까지 작성해야 시작되는** 진짜 약속."*

`challenge-create`에서 이 단계를 **의도적으로 건너뛰었다**(수락 즉시 `IN_PROGRESS`). 그 결정의 근거는 "이번 feature 단독으로 동작 확인이 가능해야 한다"였고, 같은 문서에 *"영혼의 맹세 feature가 나중에 `ACCEPTED`와 `IN_PROGRESS` 사이에 `CONTRACT_SIGNING`을 삽입한다"*고 적어뒀다. **이 feature가 그 약속을 이행한다.**

현재 챌린지는 수락하면 곧바로 진행된다. 제품이 내세우는 "무를 수 없는 약속"의 무게가 없다.

## 착수 전 확인된 사실 (2026-08-03 pm-lead 실측)

**디자인이 이미 상당 부분 존재한다.** 백로그의 *"영혼의 맹세 화면 디자인 부재"*는 부정확했다.

| 위치 | 내용 |
|---|---|
| `challenge-new.tsx` **step2** | "영혼의 맹세 📜" / "서명하면 수정 불가! 진짜야?" / 계약서 카드(상대·나의 미션·내기·마감) / **서명란**(`h-24` dashed placeholder "여기에 서명하세요") / "맹세한다! 🔥" CTA |
| `challenge-detail.tsx` | "영혼의 맹세" 섹션 + **양측 서명 표시**("나의 서명 ✓" / "민수 서명 ✓") |

**🔴 STT는 이 feature와 무관하다.** Lovable의 마이크 버튼은 **step1의 미션·내기 입력용**(`handleMic("mission")` / `handleMic("bet")`)이고 step2에는 없다. 즉 **ADR-0006(STT 클라이언트 SDK) 실행이 이 feature를 막지 않는다.** 백로그의 "영혼의 맹세(STT + 서명)" 묶음 표기는 분리해야 한다.

**`contracts` 테이블은 V1에 이미 있다.**
```
id / challenge_id / content(TEXT NOT NULL)
challenger_signature_url(TEXT NULL) / opponent_signature_url(TEXT NULL)
challenger_signed_at / opponent_signed_at / is_finalized(BOOLEAN NOT NULL) / created_at
```

## 🔴 핵심 결정 사항 — 서명을 어떻게 저장할 것인가

`*_signature_url`은 **URL 컬럼**이다. 이름 그대로 가면 이미지 파일을 어딘가에 올려야 하고, 그러면 **파일 스토리지 ADR이 선행**돼야 한다(프로젝트에 아직 없다. ADR-0007 local→AWS와 연결됨).

**초안 제안: 파일 스토리지를 도입하지 않고 서명을 벡터 경로 데이터로 DB에 저장한다.**

- 서명은 손가락 획의 좌표 목록이다. 정규화된 `[[x,y],...]` 스트로크 배열을 JSON으로 두면 보통 수 KB이고, 렌더는 Compose `Path`로 그대로 그린다.
- **파일 스토리지 ADR·인프라·수명주기 관리·CDN을 전부 회피**한다. 이 feature 하나 때문에 인프라 축을 새로 세우지 않는다.
- 벡터라 어느 해상도에서도 깨지지 않는다. 이미지보다 낫다.
- 컬럼은 이름이 `_url`이라 오해를 부르므로 **마이그레이션으로 `*_signature_path`(또는 `_data`)로 rename**하거나 신규 컬럼을 쓴다. `contracts` row가 0건이라 지금이 가장 싸다.

> **파일 스토리지가 필요해지는 진짜 시점은 카메라 인증**(`verifications.photo_url`)이다. 사진은 벡터로 대체 불가다. **그때 ADR을 쓰는 게 맞고**, 서명을 이유로 앞당길 이유가 없다.

**이 결정이 뒤집히면** 파일 스토리지 ADR이 선행 조건이 되고 이 feature는 그만큼 미뤄진다.

## 🔴 발견 1 — 취소가 FK 위반으로 500을 낸다 (2026-08-03 backend-dev, pm-lead 재현)

```
contracts_challenge_id_fkey : FOREIGN KEY (challenge_id) REFERENCES challenges(id)
                              ← ON DELETE 절 없음
```

`cancel`은 `challengeRepository.deleteById()` **물리 삭제**다(challenge-create 스코프 결정). 그런데 이 feature는 **생성 시점에 contract row를 만든다.** → **챌린저가 자기 `PENDING` 챌린지를 취소하는 순간 FK 위반 → `DataIntegrityViolationException` → HTTP 500.**

지금은 `contracts` row가 0이라 안 터지지만 **이 feature가 들어가는 첫날부터 터진다.**

**결정: `ON DELETE CASCADE`가 아니라 서비스에서 contract를 명시적으로 먼저 삭제한다.**
> 근거(backend-dev): 이 제품의 컨셉이 "무를 수 없는 약속"인데 CASCADE는 **다른 이유로 challenge를 지울 때도 맹세를 조용히 함께 지운다.** 물리 삭제 + 감사 추적 없음이라는 기존 선택 위에 암묵적 연쇄 삭제까지 얹으면 되돌릴 근거가 사라진다. 명시적 삭제는 코드에 순서가 보인다.

**거절과 취소는 다르다** — 거절은 row 보존(`REJECTED`)이라 FK 문제가 없다. 초안이 "거절·취소"로 묶어 쓴 건 부정확했다.

## 🔴 발견 2 — `CONTRACT_SIGNING`을 도입하지 않는다 (2026-08-03 backend-dev)

초안은 이걸 🟢로 뒀으나 **도입하면 실질 결함이 생긴다.**

```
GET /challenges/received  →  status = 'PENDING'      만
GET /challenges/active    →  status = 'IN_PROGRESS'  만
```

`CONTRACT_SIGNING`을 실제 상태로 도입하면 **상대가 수락은 했는데 서명 전에 이탈한 챌린지가 두 목록 어디에도 안 나온다. 재개할 경로가 없다** — `challenge-create`에서 `/sent` 부재로 취소가 도달 불가였던 것과 **정확히 같은 구조**다.

**결정: `CONTRACT_SIGNING`을 쓰지 않는다. 수락 + 서명을 단일 원자 요청으로 묶는다.**

- 시나리오 4("맹세 화면에서 이탈하면 진행되지 않는다")가 **자동으로 성립한다** — 요청을 안 보냈으니 아무것도 안 바뀌고 `PENDING` 그대로, 받은 도전장 목록에도 남는다. 재개는 다시 들어가면 된다.
- 상태를 늘리지 않으니 목록 필터·모바일 분기·테스트가 그대로다.
- **계약 완결 여부는 contract의 속성(`is_finalized`)이지 challenge의 상태가 아니다.**
- 부수 효과: 최종 상태가 여전히 `IN_PROGRESS`라 **교체 대상 테스트가 최소화**된다. 바뀌는 건 "요청에 서명이 추가되고 서명 없으면 거부"뿐이다.

> enum의 `CONTRACT_SIGNING` 값 자체는 V1부터 있으므로 제거하지 않는다. **쓰지 않을 뿐이다.**

## 사용자 시나리오

1. (챌린저) 챌린지 신청 위저드 step1 완료 → **step2 "영혼의 맹세"** → 계약서 내용 확인 → 서명란에 손가락으로 서명 → "맹세한다!" → `PENDING` 생성
2. (상대) 받은 도전장 수락 → **맹세 화면** → 계약서 확인 + 본인 미션 입력 + 서명 → 양측 서명 완료 → 챌린지가 `IN_PROGRESS`로 전환
3. (양측) 챌린지 상세에서 **양쪽 서명이 그려진 계약서**를 다시 볼 수 있다
4. (상대) 맹세 화면에서 이탈하면 챌린지는 진행되지 않는다 — 수락은 서명으로 완성된다

## 수용 기준 (Acceptance Criteria)

### 상태 전이
- [ ] 챌린저가 서명하고 생성하면 `challenges`는 `PENDING`, `contracts` row 1건이 생성되며 **챌린저 서명만** 채워진다
- [ ] 상대가 수락 + 서명하면 `contracts`의 상대 서명이 채워지고 `is_finalized = true`가 된다
- [ ] `is_finalized = true`가 된 시점에만 챌린지가 `IN_PROGRESS`로 전환되고 `verifications` PENDING 2건이 생성된다
- [ ] **서명 없이는 챌린지가 시작되지 않는다** — 수락만 하고 서명 전에 이탈하면 `IN_PROGRESS`가 되지 않는다
- [ ] 이미 `is_finalized`인 계약에 재서명을 시도하면 거부된다 ("무를 수 없다"는 컨셉)
- [ ] **취소 시 `contracts` row를 명시적으로 먼저 삭제한다** — 아래 🔴 발견 1 참조. 거절은 다르다.
- [ ] **거절된 챌린지의 `contracts` row는 보존한다** — FK 문제가 없고(`REJECTED`는 row 유지) "거절당한 맹세"도 이력이다.

### 서명 데이터
- [ ] 서명이 저장·조회 왕복에서 **동일하게 렌더된다**
  > **"무손실"의 정확한 범위** (2026-08-03 mobile-dev 정의, pm-lead 채택): **원본 손가락 입력에 대한 무손실이 아니다.** 손실은 **캡처 시점의 양자화 한 번**뿐이고(정규화 후 `0..1000` 정수), 그 뒤 encode↔decode가 **정확한 전단사**다. 이 수용 기준은 후자를 가리킨다. 뭉뚱그려 "무손실"이라고 쓰면 나중에 *"손가락 궤적이 그대로 보존되나?"* 라는 질문에 답이 안 된다.
  > **좌표를 `Float`로 두지 않은 이유**: JSON 크기가 3~4배 늘고, **무손실 주장이 부동소수 표현에 의존하게 된다.**
- [ ] 빈 서명(획 0개)은 거부된다
- [ ] 서명 데이터 크기 상한이 있고 초과 시 거부된다 (악의적 대용량 방지). **두 축(점 수 + 바이트)** — 한 축만 걸면 우회된다
- [ ] 🔴 **종횡비 2:1이 컴포넌트 내부에서 강제된다. 호출부는 폭만 정하고 비율을 덧붙이지 않는다** (2026-08-03 design-bridge 발견 → mobile-dev 구조 개선 → 기준 정정)
  > **이건 테스트로 안 잡힌다.** 좌표를 `x/width`·`y/height`로 **각각** 정규화하므로, 비율이 어긋나면 **왕복 무손실 테스트는 통과하는데 화면에서만 찌그러진다.**
  > **초안은 "호출부 책임"이었다.** design-bridge가 `grep aspectRatio` → 0건을 근거로 수용 기준으로 올렸고, mobile-dev가 그걸 받아 **불변식을 컴포넌트 안으로 옮겼다** — `SignatureCanvas.kt:69` / `SignatureView.kt:33`이 `aspectRatio(SIGNATURE_ASPECT_RATIO)`를 직접 걸고 상수는 `:core:ui` `internal`이라 호출부가 손댈 수 없다. `strokeWidth` 파라미터도 제거됐다.
  > **이 구조가 원래 명세보다 낫다** — 호출부 책임으로 두면 **호출부가 늘 때마다 깨질 기회가 생긴다.** "실기에서 발견할 게 아니라 애초에 불가능하게" 만드는 쪽이 맞다. **불변식은 파라미터로 열어두지 않는다.**
  > 검증 방법: 입력 화면과 상세 화면에서 **같은 서명이 같은 모양으로 보이는지**를 눈으로 확인해야 한다. 단위 테스트로는 대체되지 않는다.
  > ⚠️ **`x`는 width, `y`는 height로 각각 곱해야 한다.** 같은 스케일로 곱하면 세로가 절반으로 눌린다 — design-bridge가 Lovable 프리뷰에서 **실제로 이 버그를 냈다**(`viewBox="0 0 1 0.5"`인데 `y`를 `[0,1]` 그대로 씀 → 서명 아래 절반이 박스 밖으로). 클리핑 건을 파지 않았으면 못 찾았을 자리다.
- [ ] **서명 인셋: drawable rect를 실제 획 굵기의 절반만큼 4변 인셋하고, 좌표 수집과 렌더가 같은 인셋을 쓴다** (design.md §2.6)
  > 좌표 `0`/`1000`이 경계에 정확히 닿아 `StrokeCap.Round`가 굵기/2만큼 번지므로 그대로 두면 잘린다. **입력 패딩만으로는** 손가락이 보이지 않는 벽에 눌려 가장자리에서 획이 납작해지고, **렌더 인셋만으로는** 그리는 위치와 보이는 위치가 어긋난다 — **둘 다 필요하다.**
  > ⚠️ **인셋은 비율(0.9%)이 아니라 clamp까지 끝난 실제 굵기에서 뽑는다.** 상세 박스는 0.9%가 1.42dp라 최소값 1.5dp로 올라가는데, 비율로 계산하면 인셋이 모자라 여전히 잘린다.

### 화면
- [ ] 챌린지 상세에서 **양쪽 서명이 실제로 그려져** 보인다 (플레이스홀더가 아니라)
- [ ] **관점 판정이 불가능하면 "나/상대" 라벨을 쓰지 않고 양쪽 다 실명으로 떨어뜨린다** (2026-08-03 mobile-dev 제기 → design-bridge 채택, design.md §3.3)
  > `UserInfoRepository`가 `CACHE_FIRST`라 **캐시가 비었고 네트워크가 실패하면 "내가 누구인지" 판정이 안 된다.** 그때 챌린저를 "나" 자리에 놓으면 **사용자가 계약서를 잘못 읽는다** — 라벨은 "나"인데 실제로는 상대 서명이다.
  > 배치는 challenger 왼쪽 **고정**, **라벨만** 전환한다 — 위치까지 흔들면 같은 계약서가 진입할 때마다 달라 보인다. 스낵바는 띄우지 않는다(사용자가 할 수 있는 게 없고 화면은 정상 동작한다).
- [ ] **"서명 대기 중"과 "디코드 실패"를 구분해 표시한다** (2026-08-03 design-bridge 신설)
  > `signedAt`은 있는데 서명 문자열 파싱이 실패한 경우를 **"서명 대기 중"으로 그리면 거짓말이다 — 저 사람은 서명했다.** 같은 dashed 시각에 문구만 `"서명을 불러오지 못했어요"`로 가른다.
  > **`datetime-model-migration`의 `Instant.DISTANT_PAST` 센티넬이 파싱 실패를 "이미 만료된 카드"로 위장했던 것과 같은 계열이다.** 실패를 정상 상태로 위장하면 발견이 늦는다.
- [ ] 맹세 화면의 계약서 내용이 실제 챌린지 데이터와 일치하고, **양측 당사자의 미션이 모두 보인다**
  > **화면별로 행 수가 다르다** (2026-08-03 mobile-dev 발견 → design-bridge 채택, design.md §4.6): 챌린저 step은 4행(상대 미션이 **아직 존재할 수 없다**), 상대 맹세 화면은 5행(챌린저 미션 포함).
  > **빠뜨리면 계약서에 한쪽 당사자의 의무가 없다.** 게다가 §4.4에서 **챌린저 서명은 보여주면서 그 서명이 보증하는 내용은 안 보여주는** 모순이 되고, 삭제 대상인 `AcceptChallengeDialog`엔 있던 정보라 **교체가 정보를 줄인다.**
  > **`null`의 의미가 필드마다 다르다** — `myMission`의 `"—"`는 *"지금 쓰는 중이라 아직 비었다"*(자리를 지켜야 곧 채워질 곳으로 읽힌다), `opponentMission`의 **부재**는 *"이 시점엔 존재할 수 없다"*(빈 자리를 남기면 결손으로 보인다). `"—"`로 통일하면 챌린저 step에 **영원히 안 채워지는 빈 칸**이 남는다.
- [ ] 서명 전에는 "맹세한다" CTA가 비활성이다

## 🔴 반복되는 결함 계열 — "테스트는 통과하는데 화면이 거짓말한다"

이 feature에서만 **네 번** 나왔다. 우연이 아니라 계열이다.

| # | 건 | 위장 방식 |
|---|---|---|
| 1 | `aspectRatio` 미적용 | 왕복 무손실 테스트는 통과 → **화면에서만 찌그러짐** |
| 2 | 취소 FK 제약 | 단위 테스트는 fake라 **FK 자체를 재현 못 함** |
| 3 | 서명 디코드 실패 | 실패를 **"서명 대기 중"으로 위장** — 저 사람은 서명했다 |
| 4 | 관점 판정 불가 | 챌린저를 "나"로 표시 → **사용자가 계약서를 잘못 읽음** |
| 5 | 서명 캔버스 `consume()` 순서 | 218건 전부 초록인데 **기능이 아예 동작 안 함**(획당 점 1개). 제스처 루프를 구동하는 테스트가 0건이었다 |
| 6 | `UnknownApiError`가 `onError` 미호출 | 역직렬화 실패가 **에러도 스낵바도 없이 무한 로딩**이 된다 — **실패를 로딩으로 위장** |

**공통 구조**: 실패나 미설정이 **정상으로 보이는 값**으로 떨어져 발견이 늦는다. 앞선 feature의 `Instant.DISTANT_PAST` 센티넬(파싱 실패 → "이미 만료된 카드")도 같은 계열이다.

**🔴 픽스처의 출처도 같은 함정이다** (2026-08-03) — 실서버 응답을 원문 그대로 박아 "손으로 쓴 픽스처의 사각지대를 닫았다"고 했으나, 뜬 응답이 `challengeId=18`(**`IN_PROGRESS`**)이었고 **맹세 화면이 실제로 여는 상태는 `PENDING`**이었다. `PENDING`에서는 `opponent.mission`이 `null`이라 DTO(`String = ""`)가 역직렬화에 실패한다 — **화면이 100% 안 열린다.**
> **"실서버에서 떴다"가 "대표적인 응답을 떴다"를 보장하지 않는다.** 픽스처 출처를 **화면이 실제로 밟는 경로**와 맞춰야 한다.
> ⚠️ `kotlinx.serialization`의 기본값(`= ""`)은 **키 누락만** 덮는다. **명시적 `null`은 non-nullable 타입에서 그대로 실패한다.**

**대응 원칙**: 실패는 실패로 보이게 한다. 판정이 안 되면 **판정한 척하지 말고 중립으로 떨어뜨린다**(라벨 대신 실명, 폴백 대신 제외+`onError`). 그리고 **이 계열은 단위 테스트로 안 잡히므로 눈으로 확인해야 한다** — 시각 검증 항목에 반드시 포함한다.

## 리스크 / 오픈 이슈

- **🔴 서명 저장 방식이 미확정** — 위 "핵심 결정 사항". 벡터로 가면 파일 스토리지를 피하지만 `_url` 컬럼 이름과 어긋나 마이그레이션이 필요하다. 뒤집히면 파일 스토리지 ADR이 선행 조건이 된다.
- **🔴 `challenge-create`의 수락 동작을 바꾼다** — 방금 완료·커밋된 feature의 핵심 경로다. 수락 즉시 `IN_PROGRESS`를 고정한 테스트가 있으면 교체 대상이고, **교체를 회귀와 섞어 보고하면 진짜 회귀가 숨는다.** `datetime-model-migration`에서 쓴 "회귀 0 / 의도적 교체 N" 분리 보고 형식을 그대로 적용한다.
- **🟡 상대방 맹세 화면이 다이얼로그로 감당될지 불확실** — 현재 `AcceptChallengeDialog`는 미션 입력 1개짜리다. 여기에 계약서 요약 + 서명 캔버스가 들어가면 다이얼로그 면적을 넘을 수 있다. `challenge-create`에서 **바텀시트를 기각한 근거(CMP 시트 선례 0건 + iOS IME 리스크)**가 여전히 유효하므로, 전체 화면 승격이 더 나을 수 있다. T-D1에서 판단.
- **🟡 종횡비 2:1이 불변식이다** (T-D2) — 좌표를 `[0,1]`로 정규화해 저장하는데 **입력 캔버스와 상세 렌더의 비율이 다르면 서명이 찌그러진다.** 즉 수용 기준의 "왕복 무손실"이 성립하려면 비율이 고정이어야 한다. 획 굵기도 고정 dp가 아니라 **캔버스 폭 비율(0.9%)** 이어야 한다 — 입력(335dp)에서 3dp인 획이 상세(158dp)에서도 3dp면 상대적으로 2배 굵어진다.
- **🟡 `PENDING` 구간에 한쪽만 서명된 계약서가 실재한다** (T-D3에서 design-bridge 발견) — 챌린저는 생성 시, 상대는 수락 시 서명하므로 그 사이 구간이 있다. Lovable에 없던 상태라 "서명 대기 중"(dashed)을 신설했다. 상세 화면이 이 상태를 그릴 수 있어야 한다.
- **🟡 자정 경계에서 위저드 힌트와 계약서 날짜가 갈릴 수 있다** (2026-08-03 backend-dev 발견) — 모바일 위저드 힌트는 **클라 시계**로 계산하고(`KstDeadline.kt:26-29`), `challengeDate`는 **서버가 요청 도착 시점**에 결정한다(`deadlineType`이 존재하는 이유 — 기기 시계 조작 차단). → `23:59:5x`에 `"7/28 24:00"`을 보고 서명 → 요청이 자정을 넘겨 도착 → 서버가 `challengeDate=7/29` 부여 → **계약서에 "7월 29일 24:00"이 박제된다.**
  > 표기 형식은 이미 일치하고 **갈리는 건 날짜**다. 창이 초 단위로 극히 좁고 `challenge-create`부터 있던 구조지 `soul-oath`가 만든 게 아니다. **다만 성격이 바뀐다** — 전에는 화면 힌트가 잠깐 틀리는 것이었는데 이제 **틀린 날짜가 영구 기록**된다.
  > **지금 고치지 않는다.** **백로그 등재** (Phase 5).
  > 🔴 **백로그를 집는 사람에게 — "클라 시계를 맞추면 된다"가 아니다.**
  > ```
  > 23:59:59  사용자가 서명 (화면엔 "7/28 24:00")
  > 00:00:01  요청이 서버 도착 → challengeDate = 7/29 확정
  > ```
  > **클라 시계가 완벽히 정확해도 갈린다.** 원인은 시계 오차가 아니라 **`challengeDate`가 서명 시점이 아니라 요청 도착 시점에 결정된다**는 것이고, 그 사이엔 서명·직렬화·네트워크가 들어간다. **시계를 맞추면 창이 좁아질 뿐 없어지지 않는다.**
  > 진짜 고치려면 **클라가 의도한 날짜를 함께 보내고 서버가 그걸 존중**해야 하는데, 그건 `deadlineType`을 enum으로 둔 이유(**기기 시계 조작·타임존 불일치 차단**)와 정면으로 맞바꾸는 것이다. 즉 이 항목은 **버그 수정이 아니라 트레이드오프 재검토**다.
  > **현재 판단은 안 고치는 쪽** — 창이 초 단위이고, 맞바꾸는 것이 보안 성격의 결정이다. 이 근거 없이 시계 동기화를 시도하면 **"고쳤다"고 잘못 결론낼 수 있다.**
  > **부분 완화는 지금 한다**: **상대 맹세 화면**은 챌린지가 이미 존재하므로 `GET /challenges/{id}`의 `deadline`을 그대로 쓴다(클라 재계산 금지). ⚠️ **챌린저 step은 적용 불가** — 생성 전이라 서버 값이 아직 없다. 거기서는 클라 추정이 구조적으로 불가피하다.

## 2026-08-06 — `contract: null` 실기 크래시 → 전 계약 감사 (#25)

### 발단

실기에서 `GET /challenges/11` 이 `"contract": null` 을 돌려줘 `JsonDecodingException`. 원인은 **맹세 도입 이전에 만들어진 레거시 챌린지**(`id=11`)다. 코드 경로를 전수로 확인한 결과 **현재 코드로는 재현되지 않는다** — INSERT 경로가 하나뿐이고 같은 트랜잭션에서 contract를 만들며, challenge를 남긴 채 contract만 지우는 경로가 없다.

**양측 합의**: 서버는 레거시 방어(#25 계약 명문화), 모바일은 **`contract` 를 nullable 로 유지**한다. 서버가 안 보낸다고 클라 방어를 지우지 않는다 — 아래 "보증의 범위" 참조.

### 🔴 보증에는 범위가 있다 — "서버가 안 보낸다" ≠ "클라가 항상 파싱한다"

모바일 `WireLocalDateTimeSerializer` 는 **포맷 파싱 실패도 `null` 로 흡수**한다. 즉 서버가 non-null 을 보내도 **역직렬화 층이 `null` 을 만들어낸다.** non-null 보증을 근거로 클라 방어를 지우면 서버가 규약을 지켜도 깨진다.

> 계약의 nullable 표는 이제 **보증과 함께 그 보증이 닿는 범위**를 적는다.

관련해 pm-lead가 모바일 `Json` 설정을 실측했다:
```kotlin
Json { ignoreUnknownKeys = true; isLenient = true; encodeDefaults = true }
// coerceInputValues 미설정 → false → non-nullable 에 명시적 null 오면 throw
```
`ignoreUnknownKeys = true` 때문에 **개명은 제거보다 더 조용하다** — 옛 필드가 기본값으로 떨어지는 동시에 새 필드가 버려져서, 앱이 **틀린 값으로 정상 렌더한다.**

### 🔴 감사가 찾은 것 — nullable 이 아니라 **시간 포맷** 축

`friends` 계약이 여전히 이렇게 적혀 있었다:
```
계약:  val since: Instant  // ISO-8601 UTC   →  "2026-06-20T12:34:56Z"
서버:  val since: LocalDateTime @JsonFormat  →  "2026-06-20 12:34:56"
```

**누락이 아니라 능동적 오류다. 계약이 서버가 보내지 않는 것을 보낸다고 말한다.** 그리고 **nullable 표를 아무리 잘 만들어도 이 축은 안 잡힌다.**

> **근본 원인은 도구가 아니라 커버리지다.** `datetime-model-migration`(ADR-0010)이 수용 기준에 "confirmed 계약 3건 개정"을 넣었는데 **`friends` 가 그 3건에 없었다.** pm-lead가 영향 범위를 셀 때 `Instant` 를 쓰는 계약을 전수로 세지 않았다. **횡단 변경(ADR급)에서 "영향받는 문서 목록을 빠짐없이 만드는 방법"이 없다는 게 진짜 결함이고, 다음 ADR에서 또 난다.**

같은 이유로 `home-feed` 에서도 낡은 예시 2곳이 더 나왔고, `challenge-create` 는 헤더에 취소선이 있음에도 **본문 예시 11곳이 여전히 `Z` 표기**다(예시를 복사하는 사람은 헤더를 안 본다).

## 2026-08-25 — `GET /challenges/{id}` 에 `result` 추가 (challenge-result)

### 변경

`ChallengeDetailData` 에 **`result` 필드 하나를 추가**한다. `CHALLENGER_WIN` / `OPPONENT_WIN` /
`DRAW` / `BOTH_LOSE` 또는 `null`. **기존 필드는 이름·타입·의미 전부 무변경**이고, 계약서·서명 관련
필드는 하나도 건드리지 않았다. 자정 직후 판정 배치가 채운다.

- `status == COMPLETED` ⟺ `result != null` 이 서버 불변식이다
- `EXPIRED` 는 판정이 아니라 **계약서가 체결된 적 없는** 챌린지라 `result` 는 `null` 로 남는다
- 🔴 `null` 이어도 **키는 항상 나간다** — `WireShapeContractTest` 가 고정한다

### 🔴 이 feature 가 세운 원칙이 여기서 그대로 적용됐다

soul-oath §3 은 *"상세는 계약서를 보여주는 화면이라 `challenger`/`opponent` 를 역할 그대로 준다 —
홈 카드는 '내 시점'이 맞지만 계약서는 아니다"* 를 확립했다. `result` 도 **역할 기준**으로 둔다.
뒤집기(`CHALLENGER_WIN` → "내가 이겼다")는 앱의 몫이다.

> 뒤집어 주면 **같은 응답 안에 두 기준이 섞인다** — 양쪽 서명을 역할로 그리면서 결과만 내 시점이면,
> "이 서명이 누구 것인지" 를 다시 계산하게 만들지 않으려던 원칙이 반쪽이 된다.

같은 이유로 홈 카드(`/challenges/active`)는 **정반대 선택**을 했다: 거기는 `myMission` 처럼 전부
내 시점인 응답이라 `myResult`(내 시점)를 **서버가 계산해서** 준다. 게다가 그 응답에는 *"내가
challenger 인가"* 를 알 정보가 아예 없어서(상대 닉네임만 있고 역할이 없다) 앱이 뒤집을 수도 없다.

**한 원칙이 두 엔드포인트에서 반대 결론을 냈고, 그게 원칙이 제대로 작동한 증거다** —
"항상 역할 기준" 이나 "항상 내 시점" 이 아니라 **화면의 성격이 시점을 정한다.**

### 곁가지 — `contract: null` 레거시와 같은 자리에 `result: null` 이 들어갔다

`3.1 nullable 전수 표`에 `result` 행을 추가했다. `contract` 의 `null` 은 **레거시 1건에서만**
나오는 예외였지만, `result` 의 `null` 은 **`COMPLETED` 가 아닌 모든 구간** — 즉 챌린지 수명의
대부분이 `null` 이다. **가장 흔한 nullable 이 됐다.**

# Change Log — soul-oath

## 2026-08-03

### 🔴 실기에서 나온 버그 3건 (전부 테스트가 초록인 채였다)

**1. 서명 캔버스가 획당 점 1개만 기록** — `SignatureCanvas.kt`
```kotlin
change.consume()
if (change.positionChanged()) { ... }   ← consume 후라 항상 false
```
Compose의 `positionChange()`가 consume된 change에 `Offset.Zero`를 돌려주므로 `extend()`가 한 번도 안 불린다. **223건 전부 초록인데 기능이 아예 동작하지 않았다** — 제스처 루프를 구동하는 테스트가 0건이었고 모든 서명 테스트가 이미 만들어진 `Signature` 객체에서 출발했다.
> **`adb input swipe`를 못 믿고 대조 실험**을 한 게 진단을 갈랐다 — 같은 방식으로 스크롤 영역을 스와이프하니 정상 스크롤(변화 픽셀 58,777). **MOVE는 도달하고 캔버스가 받고도 버린다**는 게 확인돼 "인젝션 artifact겠지"로 끝나지 않았다.
→ 판정을 `consume()` 앞으로. 획 픽셀 **97 → 13,701**.

**2. 맹세 화면이 100% 안 열림** — `ContractPartyDto.mission: String = ""`인데 서버는 `PENDING`에서 `null`을 보낸다. **맹세 화면은 오직 `PENDING`만 연다.**
> 🔴 **wire 픽스처가 이걸 놓친 이유가 핵심이다.** 전날 "손으로 쓴 픽스처의 사각지대를 닫았다"며 실서버 원문을 박았는데, 그 원문이 `challengeId=18`(**`IN_PROGRESS`**) — **유일하게 동작하는 상태**였다. **"실서버에서 떴다"가 "대표적인 응답을 떴다"를 보장하지 않는다.**
> ⚠️ `kotlinx.serialization` 기본값(`= ""`)은 **키 누락만** 덮는다. **명시적 `null`은 non-nullable 타입에서 그대로 실패한다.**
→ `String?`로 변경 + **`PENDING` 픽스처 5건 추가**(두 상태 모두 고정).

**3. 🔴 전역 — 역직렬화 실패가 조용한 무한 로딩** — `ApiResult.kt`의 `UnknownApiError` 분기만 `onError`를 부르지 않았다(나머지 3개 분기는 전부 부름). **어떤 화면이든 응답 shape이 어긋나면 에러도 스낵바도 없이 영원히 로딩**이다.
> `soul-oath`가 만든 게 아니다. Flow 기반 repo에서는 emit 없이 완료돼 `combine` 함정으로 나타났고, **suspend+콜백인 `getChallengeDetail`에서 처음 "완전히 멈춤"으로 드러났다.**
> **백로그로 미루지 않은 이유**: 무한 스피너는 **실패를 로딩으로 위장**하는 것이고, 이 feature에서 싸워온 계열의 여섯 번째다. 발견해 놓고 "전역이라 위험하니 남겨두자"는 앞뒤가 안 맞는다. 그리고 이 계열 중 **최악**이다 — 다른 사례는 틀린 것을 보여주기라도 하는데 이건 사용자가 뭐가 잘못됐는지조차 모른다.
→ `onError("요청을 처리하지 못했어요")` + `:remote:network`에 `commonTest` 신설(모듈 최초) + `ApiResultTest` 7건. 영향 범위 **24곳 / 6 RepositoryImpl**.

> **문구 결정 경위**: pm-lead가 `"일시적인 오류"`를 기각(재시도로 오도)하고 `"화면을 불러오지 못했어요"`를 제안했으나 **mobile-dev가 그것도 기각했다** — 호출부 24곳 중 상당수가 조회가 아니라 **mutation**(챌린지 신청/수락/거절/취소, 친구 요청/수락/거절/취소, 로그인)이라 *"수락 실패에 화면을 불러오지 못했어요는 틀린 말"*이다. pm-lead가 **호출부를 안 보고 문구를 골랐다.**

### spec 초안의 전제 2건이 사실과 달랐다 (backend-dev 착수 전 발견)

**1. 취소가 FK 위반으로 500을 낸다** — `contracts_challenge_id_fkey`에 `ON DELETE` 절이 없는데 취소는 challenge를 **물리 삭제**한다. 초안 수용 기준에 "정리된다"는 **결과만 있고 원인이 없어서** 구현 중 놓치기 쉬웠다.
→ **명시적 삭제 채택** (CASCADE 기각 — *"무를 수 없는 약속"인데 CASCADE는 다른 이유로 challenge를 지울 때도 맹세를 조용히 함께 지운다*). **거절/취소를 묶어 쓴 것도 부정확** — 거절은 row 보존이라 FK 문제가 없고 contract를 **보존**한다.

**2. `CONTRACT_SIGNING` 도입은 `/sent` 부재와 같은 실수다** — 초안은 🟢로 뒀으나 🔴였다. 도입하면 "수락했으나 서명 전 이탈" 챌린지가 `/received`(PENDING만)·`/active`(IN_PROGRESS만) 어디에도 안 나와 **재개 경로가 없다.**
→ **미도입 + 수락·서명 원자 요청.** enum 값은 **제거하지 말고 쓰지도 않는다**(그 이유를 `is_finalized` 컬럼 주석에 남겼다 — 하지 않은 선택은 코드에 흔적이 없어 다음 사람이 같은 아이디어를 떠올렸을 때 막을 게 없다).
> 부수 효과: 최종 상태가 여전히 `IN_PROGRESS`라 **교체 대상 테스트가 0건**이 됐다(착수 전 추정 5건). backend-dev가 **자기 추정이 틀렸다고 먼저 밝혔다.**
> 일반 원칙으로 계약에 남겼다: **"상태를 하나 늘리면 그 상태에 갇힌 것을 꺼낼 경로가 함께 필요하다."**

### 🔴 계약이 스스로를 검증했다 — `signature` 타입

mobile-dev가 §4.4의 **"길이 1차 → 파싱 2차"** 순서를 읽고 *"그러려면 필드가 문자열로 도착해야 하는 것 아니냐"*를 역산했다. 확인 결과 서버 DTO가 `JsonNode?`(**객체**)였다.

**계약에 적히고 단위 테스트로까지 고정된 순서가 프로덕션에서 무효였다** — Jackson이 DTO 바인딩 시점에 파싱을 끝내므로 32KB 상한이 막으려던 대용량이 검증기에 닿기 전에 파싱된다. backend-dev 자기 진단: *"DTO 바인딩 층이 테스트 범위 밖이었다."*

→ 요청·응답 **모두 문자열로 대칭**. **응답의 `@JsonRawValue`도 제거** — raw로 주면 모바일이 `JsonElement` → 문자열 재인코딩을 타서 **무손실을 지키려고 넣은 장치가 무손실을 깨는 자리**가 된다.

### 계약서 본문 3건 정정 (design-bridge 검토 → 박제라 지금이 마지막)

**톤은 바꾸지 않았다** — 화면이 반말·불꽃인데 계약서가 격식체인 건 **의도된 대비**다(*"화면은 앱이 나에게 말을 거는 것이고, 계약서는 문서다"*). pm-lead의 "어색하지 않나" 우려를 근거로 기각했다.

1. **조사 병기 + 띄어쓰기** — `도윤 와(과) 수아 은(는)` → 받침 판정으로 `도윤과 수아는`
   > ⚠️ **1차 수정에 구멍이 있었다** — 숫자로 끝나는 닉네임(`테스터3`)을 "비한글"로 묶어 받침 없음 처리했다. `3`은 "삼"이라 받침 ㅁ이 있다. **"판정 불가"와 "판정 안 함"을 한 덩어리로 묶은 것**이 원인이다 — 영문은 표기만으로 발음이 안 정해져 포기가 옳지만 **숫자는 읽기가 하나로 정해져 있어 추정이 아니다.** 숫자 10종 전수 + 여러 자리 테스트로 고정.
2. **상대 미션이 영구 공란** — 생성 시점 박제인데 상대 미션은 수락 시점에 정해져 `(수락 시 기재)`가 완성된 계약서에도 남았다.
   > **박제의 취지는 "템플릿 변경 소급 방지"이지 "미완성 스냅샷 영구 보존"이 아니다. 박제 대상은 완성된 약속이어야 한다.** → `is_finalized` 시점 재렌더 후 굳힘. 테스트 3단계(수락 전 자리표시 존재 / 완결 후 부재 + 실제 미션 / **재서명 거부 후 바이트 동일**)로 고정.
3. **마감 표기가 화면과 다른 날짜** — `8월 1일 00:00` vs 화면 `7/31 24:00`. **같은 순간을 두 날짜로** 말했다. → 계약서도 `24:00` 표기.

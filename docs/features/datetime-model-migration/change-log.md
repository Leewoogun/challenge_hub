# Change Log — datetime-model-migration

## 2026-07-31

### 🔴 문제 정의가 통째로 뒤집혔다 (backend-dev 착수 전 발견 → pm-lead 재현)

pm-lead 초안의 전제 2건이 **사실과 달랐다.** 그대로 갔으면 **멀쩡한 데이터를 손상시킬 뻔했다.**

**(1) `users` 1행은 이미 KST였다 — `+9h` 보정은 손상이다**

초안 T-B2와 수용 기준은 "기존 `users` 1행을 UTC → KST(+9h) 보정"이었다. 실측:
```
refresh_token_issued_at = 2026-07-31 08:55:05
DB now()                = 2026-07-31 09:26:25   ← 28분 전
```
UTC였다면 KST로 `17:55`, 즉 **미래**다. 리프레시 토큰이 미래에 발급될 수 없다.

> 판별 방식이 중요하다 — `created_at`(5월)·`updated_at`(7월)만 봐서는 UTC인지 KST인지 구별할 근거가 없다. **"방금 로그인"이라는 의미를 가진 필드를 골라 반증**한 것이 핵심이다.

→ **T-B2를 "보정 불필요 확인 + 근거 기록"으로 재정의.** 수용 기준을 "보정된다" → "**변경되지 않고 그대로 유지된다**"로 교체.

**(2) 서버 `now()`는 미래형 리스크가 아니라 현재형 버그였다**

초안은 §1.4를 "배포 환경에서 어긋날 수 있다"로 썼으나 실측 결과 **이미 9시간 갈라져 있었다**:
```
ChallengeCommandService       Clock.systemUTC()      → 00:26 (UTC)
엔티티 5종 + FriendService 등  LocalDateTime.now()    → 09:26 (KST)
```
"DB TIMESTAMP를 UTC로 간주한다"는 **문서상 규약을 레포의 나머지 코드가 한 번도 지키지 않았다.** `challenge-create`가 그 규약을 충실히 따르며 `Clock` 을 도입하면서 **UTC 섬**이 생겼다.

→ spec의 feature 성격을 **"UTC → KST 전환" → "이미 갈라진 두 기준의 통일"** 로 전면 재작성. 오픈 이슈 1의 답이 **(c) 병행**이어야 하는 실증 근거가 됐다.

### `kotlinx-datetime` — 원인 규명으로 결론이 뒤집혔다

`challenge-create` 당시 mobile-dev 보고("0.7.x에서 `Instant` 관계가 바뀌어 안 맞는다")를 **본인이 절반만 맞았다고 정정**하고 메커니즘을 규명했다:

> `libs.versions.toml` 선언 **0.6.2** → JVM/Android는 그 0.6.2를 사용, common metadata만 `compose.material3` 제약으로 **0.7.1** 해석. 0.6.2의 `kotlinx.datetime.Instant`는 `kotlin.time.Instant`와 **별개 클래스**라 확장 미매칭. **선언을 0.7.1로 맞추면 그대로 컴파일된다.**

→ **라이브러리가 아니라 우리 버전 선언이 문제였다.** 안 팠으면 자체 타입을 만들어 `floorDiv` + `civil_from_days`를 또 손으로 짜면서 "kotlinx-datetime은 못 쓴다"는 **잘못된 통념이 레포에 굳었을 것**이다.

부수 확인: `compose.material3`가 이미 그래프에 끌어오고 있어 **신규 서드파티 추가가 아니라 이미 있는 것을 선언하는 것**이다.

### 회귀 카운트 규약 — 두 번 정밀화

1. **1차** (mobile-dev 제기): `DISTANT_PAST 폴백` 테스트는 이번 결정으로 **정반대 동작을 고정한 테스트**가 되므로 "88/88 그대로"는 **오히려 실패 신호**다. → "87 회귀 0 + 의도적 교체 1"로 기준 변경.
2. **2차** (mobile-dev 재정정): 그 테스트가 한 케이스에서 `deadline`과 `createdAt`을 **동시에 단언**하는데 새 정책이 두 필드를 정반대로 가른다. **1:1 교체가 불가능**하다. → "**삭제 1 → 신설 최소 2**"로 재조정. 억지로 숫자를 맞추면 정책이 갈린 사실이 테스트에서 안 보인다.

같은 판단이 백엔드에도 적용됐다 — `KstDeadlineCalculatorTest` 17 → **16**. UTC↔KST 경계 6건이 **검증 대상 자체를 잃어** 삭제되고 5건이 신설됐다.

### 검증 방법이 두 번 강화됐다

- **`TZ=UTC` 전체 실행** (pm-lead 제안 → backend-dev 채택): backend-dev가 한 건 **두 함수만** 타임존을 바꿔가며 확인한 것이었다. 제안을 "이미 했다"로 넘기지 않고 **전 코드베이스** 대상으로 다시 돌렸다. `TimeZone.getDefault()` 선확인 + **`--stop`으로 데몬 선제 종료**(KST로 뜬 데몬이 살아 있으면 워커가 환경을 물려받아 **가짜 통과**가 난다)까지 갖췄다. 안전망이 테스트 경로에 적용되지 않으므로 **정본만으로 선다는 직접 증거**가 됐다.
- **baseline 대조 자동화** (mobile-dev): spec은 대조를 **사람이 눈으로 보는 항목**으로 뒀는데, `WireFormatBaselineTest` 4건으로 못박았다. **시각이 이동하면 사람이 대조하기 전에 테스트가 먼저 깨진다.**

## §0 핵심 결정

### 0.1 🔴 앱은 서버에 **multipart 로 직접 올린다** — 한 번의 요청 (2026-08-18 개정)

```
POST .../verification   multipart/form-data; part name = "photo"  (JPEG)
                      → { challengeId, status, verifiedAt }
```

**한 번이다.** 예전의 3단계(`upload-url` 발급 → 서명 URL 에 `PUT` → `photoKey` 로 제출 확정)는
**전부 사라졌다.** 사용자 결정(2026-08-18)으로 ADR-0011 §3 이 supersede 됐다.

**사유**: 앱이 릴리즈 전이라 구버전 호환 제약이 없고, 현재 규모(1:1 챌린지, 하루 1~2장)에서
URL 발급 방식의 이득이 **0** 이다. 3단계 왕복과 만료·재발급 처리 복잡도만 남는다.

> 🔴 **인지된 트레이드오프**: 오브젝트 스토리지로 이사하면 **서버가 스토리지로 중계**하거나
> 그때 presigned 로 전환해야 한다. ADR-0011 §3 원문이 예고한 바로 그 비용이고, 감수하기로 했다.
> 원문은 ADR 에 `<details>` 로 박제돼 있다.

⚠️ **조회는 바뀌지 않았다.** §4 가 만료 있는 서명 `photoUrl` 을 내려주고 §5 가 그것을 서빙하는
구조는 **그대로**다. JWT 보호 이미지 엔드포인트로 바꾸면 앱 이미지 로더에 인증 헤더를 심어야 해서
오히려 복잡해진다.

### 0.2 ✅ 인증 헤더 규약이 **전 경로 동일**해졌다 (2026-08-18 2차 개정)

| 경로 | `Authorization: Bearer` |
|---|---|
| §3 업로드(multipart) · §4 조회 · **§5 사진 서빙** | ✅ **전부 필수** |

**예외가 없다.** `SecurityFilterChain` 에 사진용 permitAll 이 더는 없고, §5 는
`anyRequest().authenticated()` 가 덮는 **평범한 인증 엔드포인트**다.

<details><summary>🔴 폐기된 규약과 그 근거 (2026-08-14~08-18) — 되살릴 때 반드시 읽을 것</summary>

예전에는 **§2 업로드·§5 서빙에 `Authorization` 을 붙이는 것이 금지**였다. 근거:

> Bearer 를 요구하면 앱이 그 URL 에 토큰을 붙이는 코드를 갖게 되고, **이사하는 순간 앱이 남의
> 스토리지로 우리 JWT 를 보낸다.** 대신 URL 쿼리의 `exp`/`sig` 가 열쇠다 — HMAC-SHA256 서명이
> *"이 key 를, 이 시각까지, 이 동작만"* 을 허가한다.

**그 위험은 "URL 이 남의 도메인을 가리킬 수 있다"는 전제 위에 있었다.** 두 번의 결정으로 업로드도
조회도 **우리 서버 엔드포인트로 고정**되면서 전제가 사라졌다. 🔴 **presigned/서명 URL 방식을
되살리면 이 규약도 함께 되살려야 한다** — 그때 이 근거를 새로 발명하지 말고 여기서 꺼내 쓰라.

</details>

> 🔵 **이번 개정으로 앱에서 사라지는 것**: §5 전용 `HttpClient`(`PHOTO_SERVING_HTTP_CLIENT`),
> 서명 URL 파싱·보관, `photoUrlExpiresAt` 기반 만료 재조회. 🔴 **`sendWithoutRequest` 가 헤더를
> 선제 주입하는 것이 이제 문제가 아니라 정확히 원하는 동작**이다 — 기본 인증 클라이언트를 그대로 탄다.

### 0.3 🔴 당사자 검사는 **서버가** 한다 (ADR-0011 §4 — 유지)

자체 JWT 라 스토리지의 규칙 엔진은 *"이 사람이 이 챌린지의 당사자인가"* 를 판정할 수 없다.

- **§3**: JWT 로 당사자·`IN_PROGRESS` 를 확인한 뒤에만 바이트를 저장한다.
- **§4**: 당사자에게만 읽기 URL 을 발급한다. **제3자에게는 URL 자체가 나가지 않는다.**
- **§5**: *"유효한 서명을 가진 자"* 만 본다.

### 0.4 `photoKey` 는 이제 **앱에 노출되지 않는다**

예전에는 서버가 발급하고 앱이 되돌려주는 **불투명 문자열**이었다. 이제 **서버 내부 사정**이다 —
`store()` 안에서 만들어져 `verifications.photo_url` 에 들어가고, 앱은 §4 가 주는 완성된 URL 만 본다.

🔴 **따라서 앱은 `photoKey` 를 보관하지도, 되돌려주지도 않는다.** 예전 계약의
*"`photoKey` 를 §3 성공까지 들고 있어라"* 규칙은 **소멸했다.**

> 사용자 입력이 파일명이 되는 경로가 애초에 없어진다 — 경로 탈출은 형태상 불가능하다.
> 서버 내부 형태는 여전히 `{challengeId}/{userId}/{난수32}.jpg` 이며 **호출마다 새 난수**다.

### 0.5 ✅ `OPPONENT_VERIFIED` 발송 **개시됨** (2026-08-14) — push-fcm 계약 §0.6.1 절차 완료

`NotificationMessages.of()` 에 문구를 넣는 순간 실사용자에게 도달한다. 그래서 §0.6.1 이 **모바일 통지
선행**을 요구한다. **절차를 밟고 열었다:**

| 단계 | 결과 |
|---|---|
| ① backend-dev → `verif-mobile` 통지 | 타입 문자열 · `referenceId` 의미 · 발송 시점 · 수신자 전달 |
| ② 앱 `PushEvent.from` 이 `"OPPONENT_VERIFIED"` 를 아는가 | ✅ `verif-mobile` 반영 — `PushEvent.OpponentVerified(challengeId)` + `from()` 분기 |
| ③ 딥링크가 챌린지 상세로 가는가 | ✅ `MainViewModel.toRoute()` → `Route.Challenge.Detail(challengeId)` |
| ④ 회신 수신 → 문구 투입 | ✅ **발송 개시** |

`verif-mobile` 측 회귀 테스트 2건이 이를 고정한다 — `PushEventTest` 10/10, `MainViewModelTest` 10/10
(각 +1). 🔵 그쪽 `toRoute()` 는 **`else ->` 없는 exhaustive `when`** 이라, 다음 새 타입에서
**컴파일러가 목적지 지정을 강제**한다 — §0.6.1 규약의 코드 쪽 짝이다.

| 항목 | 값 |
|---|---|
| `data.type` | `"OPPONENT_VERIFIED"` (enum name 그대로) |
| `data.challengeId` | **`challenges.id`** — ✅ 실측 확인: `NotificationDispatcher` 가 `referenceId = challengeId` 로 저장하고 `FcmNotificationSender` 가 `putData("challengeId", …)` 로 싣는다. 기존 3종과 완전히 같은 페이로드다 |
| 수신자 | **상대** (인증한 본인이 아니다) |
| 발송 시점 | 제출 확정(§3) 트랜잭션의 `AFTER_COMMIT` |
| 딥링크 목적지 | **`Route.Challenge.Detail(challengeId)`** — pm-lead 판정 (2026-08-14). *"상대가 인증했다"* 를 누르는 이유는 그 사진을 보려는 것이고 이 feature 가 사진을 상세에 붙인다. `CHALLENGE_REJECTED` 를 Home 으로 보낸 것과 다르다 — **거기는 볼 것이 없었고 여기는 볼 것이 생긴다** |
| title | 🟡 **초안값** `"증거 도착"` |
| body | 🟡 **초안값** `"{닉네임}님이 인증 사진을 올렸습니다"` |

⚠️ `data.challengeId` 가 없으면 앱 `PushEvent.from` 이 이벤트를 **버린다.** 위 실측이 그 조건을 만족함을 확인한 것이다.

⚠️ **문구는 사용자 확정 대상이다.** 기존 3종에 톤을 맞추지 않았다 — `NotificationMessages` KDoc 이
*"임의로 통일하지 마라, 확정분을 초안에 맞추는 방향은 특히 안 된다"* 고 명시한다.

발송은 `AFTER_COMMIT`(push-fcm 결정사항 3번). **알림 실패가 인증을 롤백시키지 않는다.**

> ### 🔴 각주 — §0.6.1 의 "발송 개시" 기준 (pm-lead, 2026-08-14)
>
> **발송 개시 기준은 배포된 앱이다.** *"소스에 분기가 있다"* 와 *"그 빌드가 기기에 깔려 있다"* 는
> 다른 사건이고, §0.6.1 이 막으려는 조용한 실패는 **설치된 앱**에서 난다. 이번 승인 시점에
> `verif-mobile` 의 변경은 워킹트리에만 있었고 커밋도 배포도 되지 않았다.
>
> **그럼에도 연 이유**: 🔵 **이 프로젝트에 실사용자가 없다.** 앱이 깔린 기기는 사용자 본인의 테스트
> 기기뿐이고, **T-I1 실기 검증 때 새 빌드를 깔면 그 창이 닫힌다.** 규약을 문자 그대로 적용해
> 교착시키면 개발이 멈추는데, 규약이 막으려던 피해는 여기서 발생하지 않는다.
>
> 🔴 **따라서 이 갈음은 개발 단계 한정이다** — *"다음 실기 검증 빌드에 포함"* 으로 갈음한다.
> **릴리스 이후에는 성립하지 않는다.** 다음 사람이 이 선례를 근거로 릴리스 후에도 같은 판단을
> 하면 안 된다. 그때는 **배포 완료가 곧 개시 조건**이다.

아래는 삭제된 §2 의 핵심이다. **원문을 남기는 이유**: 여기 적힌 위협 모델은 *"앱이 key 를 알고

돌아온다** — 그때 이 조항들을 새로 발명하지 말고 여기서 꺼내 쓰라.

### 409 — 덮어쓰기를 허용하지 않았다

`verif-mobile` 이 *"이미 그 key 로 올림"* 의 status 를 물었고, **덮어쓰기가 아니라 거부**로 답한다.

**이유**: §3 의 재제출 정책은 *"이미 `VERIFIED` 면 다른 key 를 거부"* 로 사진 교체를 막는다.
그런데 **업로드 URL 은 제출 뒤에도 자기 만료(10분)까지 살아 있다.** 덮어쓰기를 허용하면 같은 key 에
다른 바이트를 다시 올려 **상대가 이미 본 사진을 흔적 없이 바꿔치기**할 수 있고, `verifications` row 는
그대로라 아무 데도 기록이 남지 않는다. 기획서 §2.4 *"작성 완료된 계약서는 수정 불가 (증거 보존)"* 가
깨지는 지점이다.

**정상 흐름은 막히지 않는다.** §1 은 부를 때마다 **새 key** 를 만들므로, 다시 찍어 올리는 경로는
항상 빈 key 로 간다. 409 가 나오는 경우는 **업로드는 성공했는데 응답을 못 받아 앱이 재시도한 때**뿐이다.
전송이 중간에 끊긴 경우는 원자적 쓰기라 **잘린 파일이 key 에 나타나지 않으므로** 여기 걸리지 않고 204 다.

> 🔴 이 조항은 **로컬 디스크 단계에서만 서버가 강제할 수 있다.** 오브젝트 스토리지로 이사하면
> presigned PUT 이 대개 덮어쓰기를 허용하므로, 그때는 **버킷 정책(오브젝트 잠금·버저닝)으로 옮겨야 한다.**
> 이사 체크리스트에 올려 둔다.

#### 409 가 보증하는 것 — 앱이 204 와 접어도(fold) 되는 근거

`verif-mobile` 이 매핑 계층에서 **204 와 409 를 같은 도메인 결과("올라갔다")로 접겠다**고 했다.
그 접기가 안전하려면 **409 ⟹ 온전한 바이트가 있다**가 성립해야 한다. 서버 구현으로 확인했다:

| 보증 | 근거 |
|---|---|
| 409 시점에 파일은 **완전하다** | 목적지에는 임시 파일 + 원자적 이동으로만 나타난다. **잘린 파일이 key 에 존재할 수 없다** |
| 409 시점에 파일은 **검증을 통과했다** | 크기 상한·JPEG 매직 넘버 검사를 통과한 바이트만 이동된다 |
| 409 는 **키 존재를 누설하지 않는다** | 🔴 **서명 검증이 먼저다.** 서명 없이 찔러보면 403 이고 409 는 볼 수 없다 |

> 🔴 **단, 409 는 "먼저 올라간 바이트가 이긴다"는 뜻이다.** 같은 `photoKey` 로 **다른 사진**을 보내면
> 그 사진은 **버려지고** 이후 §3 은 **처음 올라간 사진**을 확정한다(그게 이 조항의 목적이다).
>
> 따라서 접기가 안전한 조건은 **`photoKey` 재사용이 "같은 촬영본의 재시도"일 때뿐**이다.
> **사용자가 다시 찍었다면 §1 부터 새 key 를 받아야 한다** — 옛 key 로 보내면 새 사진이 조용히 버려진다.

### 이 조항들이 지키던 것은 어디로 갔나

🔴 **아래 문단의 *"§3 의 재제출 거부"* 는 2026-09-02 에 폐기됐다.** 현행에서 증거 보존을 지는
것은 **§3 의 `IN_PROGRESS` 검사**다 — *"마감 시점의 사진이 최종본이고 그 뒤로 불변"*.
마감 전 교체는 허용된다.

~~**증거 보존(기획서 §2.4)은 §3 의 재제출 거부 단일 지점이 진다.**~~ 저장소 계층의 덮어쓰기 방어는
**제거**했다 — 위협 모델이 *"앱이 발급받은 key 를 재사용해 같은 자리에 다른 바이트를 올린다"* 였는데,
이제 **key 는 저장 호출마다 서버가 새로 만들고 앱은 key 를 보지도 못한다.** 덮어쓸 대상이 존재하지 않는다.
(원자적 쓰기 자체는 유지된다 — 쓰기가 끊겨도 잘린 파일이 남지 않는 성질은 여전히 필요하다.)

> ⚠️ **이사 체크리스트 항목도 함께 내린다.** *"presigned PUT 은 덮어쓰기를 허용하므로 버킷
> 정책(버저닝·오브젝트 잠금)으로 옮겨야 한다"* 는 **URL 발급 방식을 되살릴 때만** 유효하다.

## §3 POST /api/v1/challenges/{id}/verification

### 설명
🔴 **사진을 올리고 그 자리에서 내 인증으로 확정한다.** 저장 + `VERIFIED` 전이 + `verified_at` 기록 +
상대에게 알림이 **한 요청·한 트랜잭션**에서 끝난다.

🔴 **이미 인증했으면 같은 요청이 사진을 교체한다** (2026-09-02 — 아래 재제출 정책).
교체 전용 엔드포인트·메서드·플래그가 **따로 없다.** 앱은 첫 제출과 **완전히 같은 요청**을 보낸다.

### 인증
Bearer JWT. **당사자만. `IN_PROGRESS` 만.**

### Request — 🔴 `multipart/form-data`

| 항목 | 값 |
|---|---|
| `Content-Type` | `multipart/form-data` (boundary 는 클라이언트가 생성) |
| part 이름 | 🔴 **`photo`** — 이 이름 하나뿐이다. 다른 part 를 보내지 않는다 |
| part 본문 | **JPEG 바이트**. base64 아님 |
| 크기 상한 | **`photo` part 바이트 기준 5 MiB** (`max-file-size`) — 요청 전체는 6 MiB (`max-request-size`) |

**JSON 본문이 없다.** `photoKey` 를 포함해 예전 요청 필드는 전부 사라졌다.

> ⚠️ **part 이름이 계약이다.** `photo` 가 아니면 서버가 `code=700` `사진을 첨부해주세요` 로 답한다.
> 파일명·part 의 `Content-Type` 은 서버가 **보지 않는다** — 실제 바이트의 **JPEG 매직 넘버
> (`FF D8 FF`)** 로 판정하므로, 헤더만 `image/jpeg` 인 PNG 는 거부된다.

> ✅ **상한이 걸리는 단위** (`verif-mobile` 질문 2). **5 MiB 는 `photo` part 하나의 바이트**이며,
> 요청 전체 상한(6 MiB)은 multipart 경계·헤더 오버헤드 몫이다. **둘 다 초과 시 같은 700**
> (`사진 용량이 너무 커요 (최대 5MB)`) 이므로 앱이 구분할 필요는 없다.

### 🔴 EXIF 는 **서버를 그대로 통과한다** — 앱이 지워야 한다 (`verif-mobile` 질문 3의 확장)

EXIF 가 붙은 JPEG 는 **통과한다.** 매직 넘버 검사는 앞 3바이트(`FF D8 FF`)만 보고, JFIF·EXIF 는
그다음 마커에서 갈리므로 둘 다 같은 3바이트로 시작한다.

🔴 **그런데 서버는 바이트를 한 글자도 손대지 않는다.** 저장은 받은 바이트 그대로 쓰고, §5 는
저장된 바이트 그대로 돌려준다. **따라서 앱이 EXIF 를 실어 보내면 상대가 그 EXIF 를 받는다** —
`GPSLatitude` / `GPSLongitude` 가 들어 있으면 **인증 사진 한 장이 촬영 위치를 상대에게 넘긴다.**

**이 앱은 즉석 촬영을 강제**(기획서 §2.5, 갤러리 진입점 금지)하므로 사진에 위치가 붙을 확률이
오히려 높고, 상대는 *"내가 아는 사람"* 이지 신뢰 경계 안쪽이 아니다.

| 누가 | 무엇을 |
|---|---|
| 🔴 **앱** | 업로드 전 **EXIF 를 제거**한다. 리사이즈(spec T-M2)에서 재인코딩하면 대개 자연히 떨어지지만 **부수 효과에 기대지 말고 명시적으로 확인**하라 — 인코더에 따라 보존된다 |
| 서버 | **하지 않는다.** 지금 시점에 이미지 디코딩 라이브러리를 들이는 비용이 크고, 앱이 이미 재인코딩 단계를 갖고 있다 |

⚠️ **서버가 안 한다는 것은 이 부담이 앱에 온전히 있다는 뜻이다.** 앱이 아닌 클라이언트가 EXIF 를
실어 보내면 그대로 저장된다 — 그 경우는 **인지하고 받는 부채**로 두며, 실사용자 유입 전에 다시 본다.

### 🔴 재제출 정책 — **`last-write-wins`** (2026-09-02 재정의)

🔴 **`전면 거부` 는 폐기됐다.** 아래가 현행이다.

| 상황 | 서버 |
|---|---|
| `PENDING` 에서 제출 | ✅ 저장 + `VERIFIED` 전이 + **알림 발송** |
| 이미 `VERIFIED` (재제출) | ✅ **사진 교체** + `verified_at` 갱신 + **이전 파일 삭제**. 🔴 **알림을 보내지 않는다** |

🔴 **마지막에 올린 사진이 최종본이다.** `IN_PROGRESS` 인 동안 몇 번이든 바꿀 수 있고, 상대와
판정 배치가 보는 것도 마지막 사진이다. **응답 shape 은 첫 제출과 완전히 같다.**

⚠️ **거부 하나가 사라졌을 뿐, 나머지 검사는 교체 경로에도 그대로 적용된다** — 당사자 검사,
`IN_PROGRESS` 검사, JPEG 매직 넘버, 5 MiB 상한, `photo` part 존재. 거부되면 **이전 사진도
지워지지 않는다.**

#### 🔑 왜 뒤집었나 — **정책 뒤집기가 아니라 전제 소멸이다**

거부를 택했던 진짜 근거는 *"판별 수단이 없다"* 가 아니라 **"올린 사진이 조용히 버려진다"** 였다.
`photoKey` 왕복이 사라지면서 서버가 *같은 촬영본의 재시도* 와 *다른 사진으로 교체* 를 구분할
수단을 잃었고, 그 상태에서 멱등 성공으로 두면 **사용자가 다시 찍어 올린 사진이 버려지는데 앱은
성공이라고 답한다.** *"상대가 보는 것"* 과 *"내가 올렸다고 믿는 것"* 이 갈라지는 그 실패를
막으려던 것이다.

🔑 **`last-write-wins` 는 올린 사진을 저장한다. 버려지는 사진이 0 이므로 그 실패 모드가 발생하지
않는다.** 두 해석이 갈라지지 않으니 거부해야 할 이유도 함께 사라진다. **원래의 걱정을 우회한
것이 아니라 걱정의 대상이 없어진 것이다.**

증거 보존(기획서 §2.4)은 **여전히 성립한다** — *"마감 시점의 사진이 최종본이고 그 뒤로 불변"*
이며, 마감 후에는 `IN_PROGRESS` 검사가 교체를 막는다.

> 🔵 **부수 효과 하나가 이 결정의 원래 동기다**: 흔들리거나 어둡게 찍힌 사진을 올린 사용자에게
> 지금까지 손쓸 방법이 **하나도 없었다**. 그리고 이 정책은
> [ai-verification](../ai-verification/spec.md) 의 전제이기도 하다 — AI 가 자정에
> 판별하는데 사진을 못 바꾸면 사용자에게 방어 수단이 없다. **다만 AI 판별은 이번 범위가 아니다**
> ([verification-photo-replace spec](../verification-photo-replace/spec.md) §1 제외).

#### 🔵 응답을 유실했으면 — **그냥 다시 올린다**

🔴 **재시도 전에 §4 로 status 를 확인하던 절차는 소멸했다.** 그 절차가 있었던 이유는 재시도가
`code=700` 으로 튕겨서 *"성공했는데 못 받은 것"* 과 *"진짜 실패"* 를 앱이 구분할 수 없었기
때문이다. 이제 **재시도가 그냥 성공**하고 사진은 같은 것으로 덮인다.

| 실패 상황 | 앱이 할 일 |
|---|---|
| `POST §3` 타임아웃 / 네트워크 오류 | **같은 사진으로 다시 POST 한다.** 끝 |

⚠️ **두 번 도착하면 알림은 한 번만 나간다** — 첫 제출이 실제로는 성공했었다면 두 번째는 교체로
처리되고, 교체는 알리지 않는다. 상대에게 중복 알림이 가지 않는다.

### 🔵 클라이언트의 **제출 전 확인** — 필수에서 **권장**으로 (2026-09-02)

*"촬영 → 미리보기 → 확정"* 단계는 **유지할 가치가 있지만 더는 계약이 기대는 방어선이 아니다.**
그 요구가 무거웠던 이유는 *"한 번의 제출이 곧 확정이고 되돌릴 수 없다"* 였는데, **되돌릴 수
있게 됐다.** 잘못 찍었으면 다시 찍어 올리면 된다.

🔴 **그래도 지우지 마라** — 왕복 없이 그 자리에서 확인하는 편이 사용자에게 싸다.
`verif-mobile` 이 이미 넣었고, 이번 개정은 그것을 **제거할 근거가 아니다.**

### 고아 파일 — 경로가 **둘**이다 (2026-09-02 갱신)

저장과 row 기록이 같은 트랜잭션이라 *"업로드는 됐는데 제출 확정이 실패"* 라는 옛 창은 없다.

| 실패 지점 | 결과 |
|---|---|
| 권한·상태·형식 검사 실패 | 파일이 **아예 저장되지 않는다.** 교체 요청이었다면 **이전 사진도 그대로** |
| 파일 저장 실패 | 예외 → 롤백. row 도 남지 않는다 |
| 저장 후 **커밋 실패** | 🟡 **새 파일**만 남는다 |
| 🔴 커밋 후 **이전 파일 삭제 실패** | 🟡 **옛 파일**이 남는다 — **2026-09-02 신설 경로** |

**둘 다 아무것도 지우지 않고 그대로 둔다.** 아무 row 도 가리키지 않는 파일은 읽히지 않으므로
무해하고, 정리는 ADR-0011 이 범위 밖으로 넘긴 **보관 기간 정책** 소관이다.

🔴 **마지막 줄의 실패를 예외로 올리지 않는다.** 삭제는 **커밋 후**라 그 시점에 트랜잭션이 이미
끝났다 — 여기서 에러를 내면 **이미 성공한 교체가 실패로 응답되고**, 사용자는 사진이 안 바뀐 줄
알고 다시 올린다. 그때마다 고아가 하나씩 더 는다. 서버는 **WARN 로그만 남기고 200 으로 답한다.**

🔴 spec 수용 기준 *"업로드 실패가 챌린지 상태를 깨뜨리지 않는다"* 는 그대로 성립한다 —
어느 지점에서 실패하든 `verifications` row 와 사진은 **직전 상태 그대로**이고, 알림도 나가지 않는다.

### 🔵 5 MiB 상한 — 앱은 **자동 재압축 루프를 넣지 않는다** (판단 유지)

상한 초과는 `code=700` `사진 용량이 너무 커요 (최대 5MB)` 다. 🔴 **앱은 이때 재압축해서 다시
보내지 않는다.** 사용자에게 보이는 실패로 두고, **도달 자체를 리사이즈 파이프라인이 깨졌다는
신호**로 본다. 도달하지 않는 상태를 위한 재시도 루프는 **관측되지 않은 가정에 대한 방어 코드**이고
이 프로젝트 규칙에 어긋난다.

<details><summary>도달 불가 근거 — 그리고 그 근거가 <b>매달려 있는 값</b></summary>

앱은 **장변을 1440px 로 고정**해 JPEG 인코딩한다(품질 85 시작, 필요 시 50까지 하향).
실제 산출물이 **~500KB 대**이므로 5 MiB 상한까지 **약 10배 헤드룸**이다.

> 🔴 *"비압축 RGB 조차 5 MiB 에 못 미친다"* 는 논거는 **그대로 쓸 수 없다.** 종횡비에 따라 깨진다:
>
> | 종횡비 (장변 1440) | 픽셀 | 비압축 RGB | 5 MiB 대비 |
> |---|---|---|---|
> | 16:9 (1440×810) | 1,166,400 | 3.34 MiB | ✅ 미만 |
> | 4:3 (1440×1080) | 1,555,200 | 4.45 MiB | ✅ 미만 |
> | **1:1 (1440×1440) — 정사각 크롭** | 2,073,600 | **5.93 MiB** | 🔴 **초과** |
>
> 임계는 **단변 1214px (종횡비 약 1.19:1)**. 폰 원본이 4:3·16:9 라 실무에서는 성립하지만
> **일반 명제가 아니다.** **정본 논거는 JPEG 압축률 쪽**이며, 정사각에서도 상한의 1/10 수준이다.

🔴 **이 판단은 두 값에 매달려 있다 — 오늘의 사실이지 규약이 아니다:**

1. **장변 1440px** — 오르면 픽셀 수가 제곱으로 늘어 재판정이 필요하다
2. **JPEG 품질 상한 85(+하향)** — 무손실이나 고품질 고정으로 바뀌면 헤드룸이 줄어든다

둘 중 하나라도 바뀌면 **이 절을 다시 계산해야 한다.**

#### 🔴 `code=700` 은 사라지지 않았다 — **한 가지 상황만 빠졌다** (mobile-dev 질문, 2026-09-02)

⚠️ **오해 주의**: 2026-09-02 개정이 없앤 것은 **`code` 가 아니라 `이미 인증을 완료했어요` 라는

|---|---|---|

*"응답을 못 받은 경우"* 도 §4 선행 조회를 거쳐야 했는데, 이제 **그냥 다시 POST 하면 된다.**

#### 🔴 `boundary` 누락은 실재하는 함정이다 (`verif-mobile` 실측, 2026-08-18)

**Ktor 의 `DefaultRequest` 가 `Content-Type: application/json` 을 전역으로 실으면, Ktor 는 요청 헤더의
`Content-Type` 을 body 의 `contentType` 보다 우선한다.** 그 결과 **multipart 의 `boundary` 파라미터가
헤더에서 사라지고**, 서버는 part 를 찾지 못한다.

`verif-mobile` 이 앱에서 2겹으로 막았고(`DefaultRequest` 를 `appendIfNameAbsent` 로 + 호출부가
boundary 포함 `Content-Type` 명시), **서버도 이 경우를 700 으로 답하도록 막았다.**

| 확인 방법 | 결과 |
|---|---|
| spring-web 6.2.7 바이트코드(`StandardMultipartHttpServletRequest.handleParseFailure`) | 메시지에 `exceed` 가 없는 파싱 실패는 전부 **`MultipartException`** |
| `javap` 로 상속 확인 | `MaxUploadSizeExceededException` **extends** `MultipartException` |
| 조치 전 거동 | 핸들러 부재 → `handleUncaught` → **HTTP 500 + code 500** |

⚠️ **용량 초과 문구는 가려지지 않는다.** 상위 타입 핸들러가 생겼지만 Spring 이 더 구체적인 핸들러를
고르므로 5 MiB 초과는 여전히 `사진 용량이 너무 커요 (최대 5MB)` 다.
`ExceptionHandlerMethodResolver` 로 **디스패치 선택 자체를 테스트로 고정**했다 — 나중에 상위 타입
핸들러를 건드리는 사람이 용량 문구를 조용히 가리면 그 테스트가 깨진다.

🔴 **권한을 상태보다, 상태를 페이로드보다 먼저 본다.** 제3자에게 *"진행 중이 아니에요"* 라고 답하면
남의 챌린지 상태가 새어나가기 때문이다.

> 🔴 **여기 있던 *"재제출 거부(700)가 형식 오류보다 항상 먼저 나온다"* 는 문장은 삭제됐다
> (2026-09-02).** 재제출이 거부되지 않으므로 **비교 대상 자체가 없다.** 현행 순서는
> **권한 → 상태 → 페이로드 → 저장 → row → (커밋) → 알림 → 이전 파일 삭제** 다.

⚠️ **용량 초과와 part 누락은 컨트롤러가 아니라 `GlobalExceptionHandler` 가 답한다.**
multipart 파싱 실패는 핸들러 호출 전에 일어나기 때문이다. 핸들러가 없으면 **HTTP 500** 이 나가므로
ADR-0002 규약(클라이언트 입력 문제 = HTTP 200 + code 700)에 맞춰 명시적으로 변환한다.

🔴 **업로드 실패가 챌린지 상태를 깨뜨리지 않는다** — 거부 시 `PENDING` 이 유지되고 알림도 안 나간다 (spec 수용 기준).

### 🔴 왜 얹지 않았나의 1번 근거가 사라졌다 — 그래도 분리를 유지한다

아래 1번(*"읽기 URL 에 만료가 있어 상세 전체가 단명 응답이 된다"*)은 **만료가 없어지면서 소멸했다.**

않는다)과, 무엇보다 **`challenger`/`opponent` 객체가 절대 null 이 아니라는 부수 이득**(아래 nullable 표)이
그대로 유효하기 때문이다. 🔵 **근거 하나가 사라졌다고 결론을 뒤집지 않는다** — 남은 근거로도 선다.

### 🔴 왜 `GET /challenges/{id}` 에 얹지 않았나 (세 쟁점 중 하나 — pm-lead 최종 확정)

1. 읽기 URL 에 **만료가 있다.** 상세 응답에 섞으면 **상세 전체가 단명 응답**이 된다 — 10분짜리 URL 을
   계약서·서명이 든 큰 응답에 섞으면 *"만료 후 갱신"*(spec T-M4)이 **계약서 전체 재조회**를 요구한다.
   사진 하나 갱신하려고 계약서를 다시 받는 꼴이다. 분리하면 갱신이 싸다.
2. `GET /challenges/{id}` 는 `PENDING`·계약서 화면에서도 쓰인다. **항상 null 인 필드로 오염시키지 않는다.**
3. 그 계약은 `confirmed` 다. shape 무변경 → **`change-log.md` 등재 불필요.**

> **판정 경위**: `verif-mobile` 은 *"얹으면 만료 URL 갱신이 공짜(재진입=재조회)"* 를 근거로 **얹기**를
> 주장했고 pm-lead 가 한 번 그렇게 확정했다가 **철회했다.** 철회 사유는 두 가지다 —
> (a) 위 1번이 그 방향의 반대임을 보였고, (b) `verif-mobile` 이 얹기를 원한 진짜 이유
> (*"만료를 이미지 로드 실패로만 감지하면 네트워크 오류와 구분이 안 된다"*)는 **`photoUrlExpiresAt` 을
> party 마다 실어 해소**했다 — 앱이 만료 시각을 알므로 실패를 기다릴 필요가 없다.
> **반대 논거를 우회한 것이 아니라 없앤 것이다.**
>
> ✅ **2026-08-18 후일담**: 만료 자체가 사라지면서 이 논쟁의 대상이 **통째로 없어졌다.**
> `photoUrlExpiresAt` 도 함께 제거됐다 — 해소할 문제가 없으면 해소 수단도 남길 이유가 없다.

§4 가 준 `photoUrl` 그대로 연다. 앱은 이미지 로더에 이 경로를 넘기면 된다.

### Path Parameters
| 이름 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | Long | ✓ | `challenges.id` |
| `party` | String enum | ✓ | 🔴 **`challenger` / `opponent` — 소문자.** §4 의 두 객체 이름과 같다 |

> 🔵 **`userId` 가 아니라 `party` 인 이유**: §4 응답이 이미 `challenger`/`opponent` **역할 그대로**
> 주므로, 앱이 그 자리에서 경로를 만들 때 **id 대조가 필요 없다.** 사용자 id 가 경로에 안 나가는
> 부수 효과도 있다.

### 인증
🔴 **Bearer JWT 필수. 당사자만.** 서명 URL 시절의 *"`Authorization` 을 붙이지 마라"* 는 **폐기됐다**(§0.2).

**당사자 검사를 §4 발급 시점이 아니라 이 요청 시점에 한다.** 경로를 추측해도 제3자는 403 이다 —
🔵 예전 서명 방식보다 **강하다**: 서명 URL 은 유출되면 만료 전까지 누구나 열 수 있었지만,
이제는 **URL 이 유출돼도 토큰이 없으면 못 연다.**

### Response — 🔴 **`BaseResponse` 가 아니다 (바이트)**

| HTTP | 의미 | 앱 대응 |
|---|---|---|
| **200** | `Content-Type: image/jpeg` + 바이트 | 표시 |
| **304** | 🔴 **`If-None-Match` 가 현재 ETag 와 같다** (2026-09-02 신설) | 갖고 있는 바이트를 그대로 쓴다 |
| **400** | `party` 가 `challenger`/`opponent` 가 아님 | 앱 버그. 재시도 무의미 |
| **401** | 토큰 없음·만료 | 🔵 **Ktor Authenticator 가 자동 refresh 후 재시도** — 이번 개정의 이득 |
| **403** | **당사자가 아님** | 재시도 무의미 |
| **404** | 챌린지 없음 / 아직 인증 안 함 / 파일 없음 | **상대가 아직 안 올렸을 때가 정상 경로다** |

🔴 **200 외에는 바디가 없다. `code` 를 읽지 말고 HTTP status 로 판단하라.**

⚠️ **401 만 예외적으로 바디가 있다** — `UnauthorizedEntryPoint` 가 `BaseResponse` JSON 을 낸다.
이미지 요청에 JSON 이 오는 셈이지만 **status 가 401 이라 이미지 로더가 실패로 처리**하고,
그 사이 Authenticator 가 갱신을 돈다. **바디를 파싱하려 하지 마라.**

### 🔴 서버는 이 경로에서 `BusinessException` 을 던지지 않는다

던지면 `GlobalExceptionHandler` 가 **HTTP 200 + JSON** 으로 바꾼다. 그러면 앱 이미지 로더가
**JSON 을 이미지로 파싱하려다 깨지고, status 가 200 이라 실패를 감지할 수도 없다.**
서비스가 sealed result 를 돌려주고 컨트롤러가 status 로 매핑한다 — **이 규약을 깨면 조용히 망가진다.**

### 🔴 캐시 — `Cache-Control: private, no-cache` + **ETag** (200 한정, 2026-09-02 개정)

🔴 **`max-age=86400` 은 폐기됐다.** 그 값이 서 있던 근거는 *"사진은 재제출 거부로 불변"* 이었는데,
**교체가 열리면서 그 전제가 사라졌다.** 경로는 그대로인데 바이트가 바뀌므로 길게 캐시하면
**상대가 사진을 바꿔도 최대 하루 동안 옛 사진이 보인다** — 에러도 로그도 남지 않는 조용한 실패다.

| 응답 | 헤더 |
|---|---|
| **200** | `Cache-Control: private, no-cache` + `ETag: "<32자 hex>"` |
| **304** | 같은 두 헤더. 🔴 **바디 0바이트** |
| 403 / 404 | `Cache-Control: no-store` (변경 없음) |

`no-cache` 는 *"저장하지 마라"* 가 아니라 **"쓸 때마다 재검증해라"** 다. 앱이 `If-None-Match` 에
직전 ETag 를 실어 보내면 바뀌지 않았을 때 **304 + 바디 0바이트**라 재진입 비용은 그대로 싸다.
🔵 ETag 는 저장소 key 에서 나오므로 *"사진이 바뀌면 반드시 바뀌고, 안 바뀌면 절대 안 바뀐다"* 가
보장된다. 🔴 **key 자체는 실리지 않는다** (§0.4 — sha256 앞 32자).

> ⚠️ **`W/"..."` 와 목록(`a, b`) 형태의 `If-None-Match` 도 받는다** — 중간 캐시가 붙이는 형태다.
> `*` 는 조건부 **쓰기**용이라 여기서 다루지 않는다.

> 🔴 **앱에 경고 — 이 헤더는 이미지 로더의 *메모리* 캐시에 닿지 않는다.** Coil 처럼 URL 을 키로
> 메모리/디스크 캐시를 따로 두는 로더는 HTTP 캐시 의미를 무시할 수 있다. 그러면 **교체 후에도
> 같은 화면에서 옛 사진이 그대로 보인다.** 앱이 교체·재진입 시점에 **해당 URL 의 캐시 항목을
> 명시적으로 무효화**해야 한다. 서버가 URL 에 버전 쿼리를 붙이는 방식도 가능하지만, 그건
> §4 `photoUrl` 값의 모양을 바꾸므로 **모바일과 합의해야 하는 별건**이다.

🔴 **403 / 404 는 `Cache-Control: no-store` 다.** 같은 URL 의 응답이 **404 → 200 으로 바뀌는 자리**이기
때문이다 — 상대가 아직 인증하지 않았을 때 받은 404 를 캐시하면 **상대가 인증한 뒤에도 사진이 안 보인다.**

### ✅ 캐시 키 — 경로가 곧 캐시 키다

```
/api/v1/challenges/7/photos/challenger    ← 쿼리가 없다. 챌린지 수명 내내 불변
```

쿼리를 떼어내는 처리가 **필요 없어졌다**(예전에는 `exp`/`sig` 를 제외해야 했다).
`challengeId+userId+verifiedAt` 로 우회할 필요도 없다.

> 🔴 **불변인 것은 URL 이지 바이트가 아니다 (2026-09-02).** 교체가 열리면서 **같은 키에 다른
> 사진**이 오게 됐다 — 그래서 신선도는 URL 이 아니라 **ETag** 가 판정한다(위 캐시 절).
> 🔴 **URL 을 키로 삼는 로더 캐시는 이 사실을 모른다.** 앱이 교체 시점에 무효화해야 한다.

  왕복 없이 그 자리에서 확인하는 편이 여전히 싸다 (§3).

  ⚠️ **교체 경로에도 똑같이 필요하다** — 두 번째 사진의 EXIF 를 서버가 지워 주지 않는다.

```
"photoUrl": "/api/v1/challenges/7/photos/challenger"
```

### 🔴 `photoUrl` 은 **`/` 로 시작한다** — 조인할 때 슬래시를 겹치지 마라

```
baseUrl  "http://10.0.2.2:8080/"                        ← trailing slash
photoUrl "/api/v1/challenges/7/photos/challenger"       ← leading slash
단순 접합 "http://10.0.2.2:8080//api/v1/challenges/..."  ← 🔴 // 가 된다
```

**서버는 이것을 관용하지 않는다. 404 다** (backend-dev 실측 — 아래 표).
🔴 **`baseUrl.trimEnd('/') + photoUrl`** 로 조인하거나 URL 빌더를 쓰라.

> ⚠️ **`verif-mobile` 이 짚은 함정 (2026-08-18)**: 이 레포의 기존 조인 관행은
> **`baseUrl`(trailing slash) + 경로(leading slash 없음)** 이다
> (`"${BASE_URL}api/v1/auth/refresh"`, `@POST("api/v1/challenges/{id}/verification")`).
> **그런데 `photoUrl` 은 `/` 로 시작한다** — 즉 **관행을 그대로 따르면 100% `//` 가 된다.**
> 관행을 따르는 것이 곧 버그가 되는 자리라 특히 밟기 쉽다.

#### 실측 (MockMvc, 2026-08-18)

| 요청 | status | 핸들러 도달 |
|---|---|---|
| `/api/v1/challenges/7/photos/challenger` | **200** | ✅ |
| `//api/v1/challenges/7/photos/challenger` | 🔴 **404** | ❌ |
| `/api/v1//challenges/7/photos/challenger` | 🔴 **404** | ❌ |

Spring Security `StrictHttpFirewall` 은 빈 세그먼트를 **통과**시키고(`.`·`..` 만 거부),
**Spring MVC 의 `PathPatternParser` 가 막는다.** 어느 계층에서 죽는지 알아야 디버깅이 빠르다.

#### 🔴 이 404 는 **조용하다** — 이 절의 진짜 위험

§5 는 *"상대가 아직 인증 안 함"* 도 **404** 로 답한다. 조인 버그 404 와 정상 404 가
**앱에서 구분되지 않는다.** 사진이 영원히 안 보이는데 앱은 *"상대가 아직 안 올렸나 보다"* 로 읽고
에러도 로그도 남지 않는다 — **관측 가능한 실패가 아니라 조용히 틀린 결론**이다.

⚠️ 두 404 는 응답 모양이 다르지만(라우팅 404 는 `BaseResponse` JSON 바디 + `no-store` 없음,
정상 404 는 바디 없음 + `no-store`) 🔴 **그걸로 분기하지 마라.** 라우팅 404 의 바디 모양은
**계약이 아니라 프레임워크 사정**이고, 앱이 그걸 읽기 시작하면 Spring 버전을 올릴 때 조용히 깨진다.
**조인을 정확히 하는 것이 유일한 답이다.**

> **서버는 `//` 를 흡수하지 않는다** (backend-dev 판정, `verif-mobile` 동의). 흡수하면
> (a) 잘못된 URL 이 정상 동작해 버그가 숨고, (b) 같은 사진에 **캐시 키가 둘** 생긴다.

> 🔵 **왜 절대 URL 을 버렸나**: 서버가 절대 URL 을 만들려면 host 를 알아야 하는데,
> **Android 에뮬레이터는 `10.0.2.2`, iOS 시뮬레이터는 `localhost`** 로 같은 서버에 닿는다.
> 그래서 서버가 *"요청이 들어온 host"* 를 읽는 조각(`PhotoBaseUrlProvider`)을 두고 있었다.
> **상대 경로로 내리면 그 문제가 통째로 사라지고**, 배포 시 프록시·도메인 설정에도 영향받지 않는다.
> 앱은 이미 인증 `HttpClient` 에 baseUrl 을 갖고 있다.
>
> ⚠️ **앱에서 이 방식이 곤란하면 회신해 달라** — 서버가 절대 URL 로 내리는 것도 설정 하나 차이다.

  검증이 저장보다 앞이라 **거부된 요청은 디스크에 아무것도 남기지 않고 이전 사진도 지우지 않는다.**
- 🔴 **이전 파일 삭제는 반드시 커밋 뒤여야 한다** (`PhotoStorage.delete` KDoc — *"트랜잭션이 아니다.
  롤백돼도 지워진 파일은 돌아오지 않는다"*). 그래서 `VerificationService.submit` 에는
  **`@Transactional` 이 없고** 트랜잭션 경계가 `VerificationSubmitTransactionalWorker` 에 있다
  (`WithdrawalService` 와 같은 구조). ⚠️ **바깥에 `@Transactional` 을 붙이면 삭제가 커밋 전으로
  당겨진다** — 컴파일도 되고 다른 테스트도 통과하므로 구조 테스트로 고정해 뒀다.
- 🔴 **`OPPONENT_VERIFIED` 는 최초 1회만 발행한다.** 판정은 *저장 전* `mine.status` 로 한다 —
  저장 뒤에는 row 가 이미 `VERIFIED` 로 덮여 구분할 수 없다.
- 🔴 **지울 key 는 `status` 가 아니라 직전 `photo_url` 로 판정한다.** 탈퇴가 row 를 남긴 채 key 만
  NULL 로 밀기 때문에(mypage T-B2) status 로 보면 없는 파일을 지우러 간다.
- 🔵 **마이그레이션 0건** — 컬럼 변화가 없다 (2026-09-02 개정).
- `spring.servlet.multipart.max-file-size` 가 크기의 **유일한 강제 지점**이다. `challenge.photo.max-bytes` 와
  `upload-url-ttl-seconds` 는 참조가 사라져 **제거**했다 — 두 곳에 상한을 두면 서로 어긋난다.

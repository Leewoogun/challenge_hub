[api-contract.md](./api-contract.md) 가 `confirmed` 된 **2026-08-14 이후**의 변경을 기록한다.
확정 이전의 협의는 계약서 하단 "협의 이력"에 있다 — **여기와 섞지 않는다.**

## 🔴 다른 feature 의 `confirmed` 계약은 건드리지 않았다

`soul-oath` 의 **`GET /api/v1/challenges/{id}` 는 요청·응답 shape 이 무변경**이다.
인증 조회를 그 응답에 얹는 안이 한때 확정됐다가 **철회**되고 별도 엔드포인트
(`GET /challenges/{id}/verifications`)로 최종 결정됐기 때문이다(계약 §4).

**따라서 `soul-oath/change-log.md` 에 등재할 항목이 없다.** 이 파일은 *이* 계약의 변경만 다룬다.

## 🔴 2026-08-18 (2차) — 조회도 **서명 URL 폐기 → JWT 보호 엔드포인트** (§0.2·§4·§5)

| 항목 | 내용 |
|---|---|
| **분류** | 🔴 **shape 변경** — 응답 필드 제거 + 엔드포인트 경로·인증 교체 |
| **결정자** | **사용자** (2026-08-18, 같은 날 2차 결정) |
| **주체** | backend-dev (계약·구현), `verif-mobile` (앱) |
| **근거 문서** | [ADR-0011](../../decisions/0011-photo-storage.md) §4 **수단 변경** (§3 supersede 블록의 *"조회는 바뀌지 않는다"* 단서 철회) |

### 무엇이 바뀌었나

```
[개정 전] §4 → photoUrl(절대 URL + exp/sig) + photoUrlExpiresAt(10분)
          §5   GET /api/v1/photos/{challengeId}/{userId}/{파일명}?exp=&sig=   ← Bearer 금지, permitAll

[개정 후] §4 → photoUrl(상대 경로, 만료 없음)          ← photoUrlExpiresAt 제거
          §5   GET /api/v1/challenges/{id}/photos/{party}                     ← Bearer 필수
```

| 대상 | 조치 |
|---|---|
| `GET /api/v1/photos/...` (구 §5) | 🔴 **삭제.** 핸들러·permitAll 모두 제거 |
| `GET /challenges/{id}/photos/{party}` | 🔴 **신설.** JWT 당사자 검사 후 `image/jpeg` 바이트 |
| `photoUrlExpiresAt` | 🔴 **필드 제거** — 명백한 shape 변경 |
| `photoUrl` | 🔴 **절대 URL + 서명 → 상대 경로.** `VERIFIED` 아니면 null 인 것은 그대로 |
| `exp`/`sig` 서명 체계 | 🔴 **제거** (`PhotoUrlSigner` 삭제) |
| §3 업로드 · `OPPONENT_VERIFIED` | **무변경** |

### 폐기 사유 — 1차 개정 때의 단서를 사용자가 철회했다

multipart 전환(1차) 때 ADR 에 *"⚠️ 조회는 바뀌지 않는다 — JWT 보호 이미지 엔드포인트로 바꾸면
**앱 이미지 로더에 인증 헤더를 심어야 해서 오히려 복잡해진다**"* 는 단서를 달았다.
**그 전제가 틀린 것으로 확인됐다** — Coil 3 의 `coil-network-ktor3` 는 앱의 기존 인증 `HttpClient` 를
그대로 받으므로 **JWT 첨부·토큰 갱신이 추가 배관 없이 적용된다.**

전제가 무너지자 남는 것은 서명 URL 의 순수 비용뿐이었다: HMAC 발급·검증 코드, 만료 관리,
앱의 전용 `HttpClient`·만료 재조회 로직, host 를 알아내는 조각. **1차 개정과 같은 원리다 —
지금 규모에서 안 쓰는 유연성에 복잡도를 지불하지 않는다.**

### 🔵 오히려 보안이 강해졌다

| | 서명 URL | JWT 엔드포인트 |
|---|---|---|
| URL 이 유출되면 | **만료 전까지 누구나 열 수 있다** | 🔵 **토큰 없이는 못 연다** |
| 당사자 검사 시점 | 발급 시점 (1회) | 🔵 **요청 시점 (매번)** |
| 토큰 만료 시 | 403 → 앱이 §4 재조회 | 🔵 **401 → Authenticator 자동 갱신** |

### 🔴 새로 생긴 규약 — 이 경로에서 `BusinessException` 을 던지면 안 된다

응답이 **바이트**인데 `GlobalExceptionHandler` 는 `BusinessException` 을 **HTTP 200 + JSON** 으로 바꾼다.
그러면 앱 이미지 로더가 **JSON 을 이미지로 파싱하려다 깨지고, status 가 200 이라 실패를 감지할 수도 없다.**
서비스가 sealed result(`Found`/`Forbidden`/`NotFound`)를 돌려주고 컨트롤러가 status 로 매핑한다.

### 캐시 정책이 뒤집혔다

| | 개정 전 | 개정 후 |
|---|---|---|
| 200 | `private, max-age=300` (만료 10분보다 짧게) | 🔵 **`private, max-age=86400`** — 만료가 없고 사진은 불변 |
| 403/404 | (해당 없음) | 🔴 **`no-store`** |

🔴 **404 를 캐시하면 안 되는 이유**: 같은 URL 의 응답이 **404 → 200 으로 바뀌는 자리**다.
상대가 아직 인증하지 않았을 때 받은 404 가 캐시되면 **상대가 인증한 뒤에도 사진이 안 보인다.**
서명 URL 시절에는 URL 이 매번 달라져서 생길 수 없던 문제다.

### 앱이 지워도 되는 구현

§5 전용 `HttpClient`(`PHOTO_SERVING_HTTP_CLIENT`) · 서명 URL 파싱·보관 · `photoUrlExpiresAt` 소비 ·
만료 감지 후 §4 재조회 · 캐시 키에서 쿼리 제외 처리.

⚠️ **1차 개정 때 *"§5 때문에 존치하라"* 고 합의했던 전용 클라이언트가 이번엔 정말로 사라진다.**
`sendWithoutRequest` 의 선제 헤더 주입이 이제 **피해야 할 동작이 아니라 원하는 동작**이다.

### 서버측 부수 변경

- **삭제**: `PhotoUrlSigner` · `SelfHostedPhotoEndpoint`(+`ServeOutcome`) · `LocalPhotoController` · `PhotoBaseUrlProvider`
- `PhotoStorage` 포트: `issueReadUrl`/`ReadUrl` 제거 → **`read(key): ByteArray?`** 추가
- 설정 3개 제거(`signing-secret` / `public-base-url` / `read-url-ttl-seconds`) —
  🔵 **환경변수가 2개 줄었다** (`CHALLENGE_PHOTO_SIGNING_SECRET` / `CHALLENGE_PHOTO_PUBLIC_BASE_URL`)
- **마이그레이션 0건**

> 🔵 **`PhotoBaseUrlProvider` 소멸이 부수 이득이다.** 그 조각은 *"Android 에뮬레이터 `10.0.2.2` /
> iOS 시뮬레이터 `localhost`"* 때문에 존재했다 — 서버가 URL 을 만들지 않게 되면서 **문제 자체가 사라졌다.**

## 🔴 2026-08-18 (1차) — 업로드가 **multipart 직접 수신**으로 바뀌었다 (§0·§1·§2·§3)

| 항목 | 내용 |
|---|---|
| **분류** | 🔴 **shape 변경** — 엔드포인트 2개 삭제 + 요청 형식 교체 |
| **결정자** | **사용자** (2026-08-18) |
| **주체** | backend-dev (계약·구현), `verif-mobile` (앱) |
| **근거 문서** | [ADR-0011](../../decisions/0011-photo-storage.md) §3 **supersede** |

### 무엇이 바뀌었나

```
[개정 전] ① POST .../verification/upload-url  → photoKey + 서명 uploadUrl
          ② PUT  uploadUrl (JPEG raw)         → 204/403/409/413/415  ← 바디 없음
          ③ POST .../verification {photoKey}  → { challengeId, status, verifiedAt }

[개정 후] ① POST .../verification  multipart/form-data (part 이름 "photo")
                                   → { challengeId, status, verifiedAt }   ← shape 동일
```

| 대상 | 조치 |
|---|---|
| `POST /challenges/{id}/verification/upload-url` | 🔴 **삭제**. 호출하면 404 |
| `PUT /api/v1/photos/...` | 🔴 **삭제**. `/api/v1/photos` 이하는 **GET 만** permitAll 로 축소 |
| `POST /challenges/{id}/verification` | **요청 형식 교체** (JSON `{photoKey}` → multipart `photo`). **응답 shape 은 무변경** |
| `GET /challenges/{id}/verifications` (§4) | **무변경** |
| `GET /api/v1/photos/...` (§5) | **무변경** — 만료 있는 서명 URL 서빙 그대로 |
| `OPPONENT_VERIFIED` 알림 | **무변경** — 제출 성공 시 `AFTER_COMMIT` |

### 사유 (사용자 결정)

앱이 **릴리즈 전**이라 구버전 호환 제약이 없고, 현재 규모(1:1 챌린지, 하루 1~2장)에서
URL 발급 방식의 이득이 **0** 이다 — 3단계 왕복과 만료·재발급 복잡도만 남는다.

🔴 **인지된 트레이드오프**: 오브젝트 스토리지로 이사할 때 서버가 중계하거나 그 시점에 presigned 로
전환하는 비용을 **감수한다.** ADR-0011 §3 원문이 예고한 바로 그 비용이며, 원문은 ADR 에 박제돼 있다.

### 🔴 재제출 정책을 **다시 정했다** — 이 변경의 가장 무거운 부분

`photoKey` 왕복이 사라지면서 *"같은 key 면 멱등 성공"* 조항이 **성립 근거를 잃었다.**
서버가 받는 것은 바이트뿐이고, **그것이 같은 촬영본의 재시도인지 새로 찍은 사진인지 판별할 수단이 없다.**

| | 개정 전 | 개정 후 |
|---|---|---|
| `PENDING` 제출 | 전이 + 알림 | 동일 |
| 이미 `VERIFIED`, **같은 key** | ✅ 멱등 성공 | — (구분 불가) |
| 이미 `VERIFIED`, **다른 key** | ❌ 700 | ❌ **700 — 재제출 전면 거부** |

**멱등 성공을 남기지 않은 이유**: 판별이 불가능한 채로 성공을 돌려주면 **사용자가 다시 찍어 올린
사진이 조용히 버려지는데 앱은 성공이라고 답한다.** *"상대가 보는 것"* 과 *"내가 올렸다고 믿는 것"* 이
갈라지고, 이는 **원안이 막으려던 바로 그 실패**(기획서 §2.4 증거 보존)다.

**대신 응답 유실 회복을 명시적 절차로 옮겼다** — 앱은 재시도 전에 **§4(`GET .../verifications`)로
내 status 를 확인**한다. `VERIFIED` 면 이미 성공, `PENDING` 이면 재제출.
🔴 **앱이 700 문구를 성공으로 해석하는 설계는 금지**한다. 문구 매칭은 깨지기 쉽고, 같은 700 이
*"진짜로 이미 인증한 상태"* 에서도 나온다.

### 저장소 계층 덮어쓰기 방어(409)를 **제거했다** — 판정 근거

2026-08-14 에 결함 수정으로 넣었던 조항이다(아래 항목). **위협 모델이 소멸해서 내렸다:**

그 방어가 막던 것은 *"앱이 발급받은 key 를 알고 있고, 그 URL 이 제출 뒤에도 만료까지 살아 있어
같은 자리에 다른 바이트를 올릴 수 있다"* 였다. 이제 **key 는 저장 호출마다 서버가 새로 만들고
앱은 key 를 보지도 못하며, 업로드 URL 이라는 것 자체가 없다.** 덮어쓸 대상이 존재하지 않는다.

🔴 **증거 보존은 §3 의 재제출 거부 단일 지점이 진다.** 2계층에서 1계층으로 줄었지만,
남은 한 계층이 **유일한 쓰기 경로**를 지키므로 우회로가 없다 —
설령 검사를 통과하는 버그가 생겨도 새 key 에 쓰이므로 **덮어쓰기 방어로는 어차피 막히지 않았다.**
(원자적 쓰기는 **유지**한다. 쓰기가 끊겨도 잘린 파일이 남지 않는 성질은 여전히 필요하다.)

> ⚠️ **이사 체크리스트 항목도 함께 내렸다** — *"presigned PUT 은 덮어쓰기를 허용하므로 버킷
> 정책으로 옮겨야 한다"* 는 **URL 발급 방식을 되살릴 때만** 유효하다. 계약 §2 의 접힌 블록에
> 원문과 함께 보존했다.

### 앱이 **지워도 되는** 구현

| 사라진 요구 | 이유 |
|---|---|
| 업로드 전용 **별도 `HttpClient`** | 업로드가 Bearer 필수인 평범한 인증 엔드포인트가 됐다 |
| §2 의 **원시 Ktor 호출**(Ktorfit 우회) | 응답이 `BaseResponse` 라 `ApiResultConverterFactory` 를 정상적으로 탄다 |
| `photoKey` **보관 규칙** | 앱은 key 를 받지도 보내지도 않는다 |
| `204`/`409` **fold** | bare status 응답이 없다 |
| `413`/`415` status 분기 | 전부 `HTTP 200 + code=700` |

🔴 **§5(사진 서빙)의 `Authorization` 금지는 잔존한다.** 이미지 로더가 그 URL 을 직접 열고,
Ktor `Auth(bearer)` 가 헤더를 선제 주입하므로 **별도 경로가 여전히 필요하다.**

### 서버측 부수 변경

- `spring.servlet.multipart.max-file-size: 5MB` 신설 — **크기의 유일한 강제 지점**.
  `challenge.photo.max-bytes` / `upload-url-ttl-seconds` 는 참조가 사라져 제거(두 곳에 상한을 두면 어긋난다).
- `GlobalExceptionHandler` 에 `MaxUploadSizeExceededException` / `MissingServletRequestPartException` 핸들러 추가 —
  없으면 **HTTP 500** 이 나간다. multipart 파싱 실패는 컨트롤러 도달 **전**이라 서비스 코드로 잡을 수 없다.
- `SecurityConfig` 의 `/api/v1/photos/**` permitAll 을 **`HttpMethod.GET` 한정**으로 축소.
- `PhotoUrlSigner` 의 `Op`(PUT/GET) 제거 — 허가할 동작이 읽기 하나뿐이라 값이 하나인 enum 은 죽은 추상이다.
  canonical 형식이 바뀌므로 도메인 분리 태그를 `v1` → `v2` 로 올렸다(발급된 URL 무효화, 만료 10분이라 실질 영향 없음).
- **마이그레이션 0건** — `photo_url` 에 key 를 넣는다는 사실이 그대로다.

## 2026-08-14 — `OPPONENT_VERIFIED` 발송 개시 (§0.5)

| 항목 | 내용 |
|---|---|
| **분류** | 동작 변경 (계약 shape 무변경) |
| **주체** | backend-dev (pm-lead 승인, `verif-mobile` 회신 확인) |
| **파일** | `domain/model/.../NotificationMessages.kt` — `OPPONENT_VERIFIED` 분기가 `null` → `Message` |

**`confirmed` 이후 변경으로 기록하는 이유**: 계약 shape 은 그대로지만 **실제 발송이 시작되는 사건**이다.
push-fcm 계약 §0.6.1 이 *"문구 추가 = 발송 개시"* 로 규정했고, 이 한 줄이 **스위치**다 —
지우면 그 타입의 발송이 즉시 멈춘다(dispatcher 가 `null` 을 보고 건너뛴다).

**절차**: ① backend-dev 통지 → ② `verif-mobile` 이 `PushEvent.OpponentVerified` + 딥링크
`Route.Challenge.Detail(challengeId)` 반영 → ③ 회신 → ④ 문구 투입.

**실측 확인** (2026-08-14 11:02 KST, 로컬 기동 + 실 DB):

```
challenge 18 에서 테스터3(userId 16, challenger)이 제출
→ notifications row: user_id=15  type=OPPONENT_VERIFIED  reference_id=18
                     title="증거 도착"  body="테스터3님이 인증 사진을 올렸습니다"
```

🔴 **수신자가 상대(15)이고 제출자(16)가 아니다.** `verif-mobile` 이 *"본인에게 가면 자기 알림을 눌러
자기 사진을 보러 가는 형태가 된다"* 며 확인을 요청한 항목이고, 서버 단위 테스트 2건
(`제출하면 상대에게 OPPONENT_VERIFIED 이벤트가 발행된다` / `상대가 인증하면 챌린저가 받는다`)이
양방향을 고정한다.

문구는 🟡 **초안값**이다 — 사용자 확정 대상이며 기존 3종에 톤을 맞추지 않았다
(`NotificationMessages` KDoc 의 *"임의로 통일하지 마라"* 지시).

> ⚠️ **개시 기준에 단서가 붙는다** (계약 §0.5 각주). 승인 시점에 `verif-mobile` 의 변경은
> **워킹트리에만 있었고 커밋·배포되지 않았다.** *"다음 실기 검증 빌드에 포함"* 으로 갈음한 것이며
> **실사용자가 없는 개발 단계 한정**이다. **릴리스 이후에는 배포 완료가 곧 개시 조건이다.**

## 2026-08-14 — 업로드 `409` 추가 (§2)

| 항목 | 내용 |
|---|---|
| **분류** | 🔴 **결함 수정** — 확정된 정책의 우회로를 닫음 |
| **주체** | backend-dev (`verif-mobile` 의 질문이 발단) |
| **영향** | §2 응답 status 에 **409** 신설. 요청 shape 무변경 |

⚠️ **엄밀히는 `confirmed` **직전**에 들어간 수정이라 협의 이력에도 있다.** 여기 다시 적는 이유는
**앱이 처리해야 하는 새 status** 이고 계약서만 훑어서는 놓치기 쉬운 항목이기 때문이다.

**무엇이 잘못됐었나**: 업로드 URL 이 **제출 확정 뒤에도 자기 만료(10분)까지 살아 있다.**
초기 구현은 같은 key 에 덮어쓰기를 허용했으므로, 상대에게 알림이 나간 뒤 **같은 URL 로 다른 바이트를
올려 상대가 이미 본 사진을 바꿔치기**할 수 있었다. `verifications` row 는 그대로라 **흔적이 남지 않는다.**
§3 의 재제출 거부 정책이 지키려던 것(기획서 §2.4 *"증거 보존"*)이 **한 계층 아래에서 뚫려 있었다.**

**실측**: 수정 전 빌드에서 `1차 PUT 204 / 2차 PUT(다른 바이트) 204` 로 재현.
수정 후 `204 / 409`, 디스크 잔존 크기가 원본 212B 그대로.

**앱 영향**: 🔴 **409 는 실패가 아니다.** 파일은 서버에 있으므로 **그대로 §3(제출 확정)으로 진행**한다.
도달 경로는 *"업로드는 성공했는데 응답을 못 받아 재시도한 때"* 뿐이다.

`verif-mobile` 은 매핑 계층에서 **204 와 409 를 같은 도메인 결과로 접기로** 했다(호출부마다
`|| AlreadyUploaded` 를 빠뜨릴 자리를 없애려고). 그 접기의 전제(**409 ⟹ 온전한 바이트가 있다**)는
서버 구현으로 성립을 확인했고 계약 §2 에 표로 등재했다 — 원자적 이동, 검증 통과분만 저장,
그리고 **서명 검증이 exists 검사보다 먼저**라 409 가 키 존재를 누설하지 않는다.

🔴 **단서**: 409 는 *"먼저 올라간 바이트가 이긴다"* 는 뜻이다. **사용자가 다시 찍었다면 §1 부터
새 key 를 받아야 한다** — 옛 key 로 보내면 새 사진이 조용히 버려진다.

> 🔴 **이사 시 옮겨야 한다.** 오브젝트 스토리지의 presigned PUT 은 대개 덮어쓰기를 허용하므로,
> 이 방어는 **버킷 정책(버저닝·오브젝트 잠금)** 으로 이전해야 한다.

## 2026-08-14 — §2 `413` 대응 지침 정정

| 항목 | 내용 |
|---|---|
| **분류** | 문서 정정 (코드·shape 무변경) |
| **주체** | `verif-mobile` 제기, backend-dev 반영 |

초안 표가 413 을 *"리사이즈 강도를 높여 재시도"* 로 적었으나 **앱은 자동 재압축을 넣지 않는다.**
표의 "앱 대응" 열을 **실제 동작으로 정정**했다 — 재압축하지 않고, **413 도달 자체를 리사이즈
파이프라인이 깨졌다는 신호**로 본다. 도달하지 않는 상태를 위한 재시도 루프는 **관측되지 않은
가정에 대한 방어 코드**라 프로젝트 규칙에 어긋난다.

> ⚠️ **문서를 고친 이유가 "권고였으니 넘어간다"가 아니다.** 문서와 구현이 어긋난 채 남으면
> 이 프로젝트가 반복해 겪은 드리프트가 된다(계약 §3 문구 확정 표기 선례). *"권고였다"* 는
> 다음 사람에게 전달되지 않는다 — pm-lead 판정.

## 🔴 그 과정에서 `verif-mobile` 의 근거 하나를 정정했다

`verif-mobile` 은 *"비압축 RGB 조차 5 MiB 에 못 미치므로 413 은 구조적으로 불가능"* 이라고 했다.
**계산해 보니 종횡비에 따라 깨진다:**

| 종횡비 (장변 1440) | 픽셀 | 비압축 RGB | 5 MiB 대비 |
|---|---|---|---|
| 16:9 (1440×810) | 1,166,400 | 3.34 MiB | ✅ 미만 |
| 4:3 (1440×1080) | 1,555,200 | 4.45 MiB | ✅ 미만 |
| **1:1 (1440×1440) — 정사각 크롭** | 2,073,600 | **5.93 MiB** | 🔴 **초과** |

임계는 **단변 1214px (종횡비 약 1.19:1)**. 폰 원본이 4:3·16:9 라 실무에서는 성립하지만
**일반 명제가 아니다.** **결론(413 도달 불가)은 유지되나 정본 논거는 JPEG 압축률 쪽이다** —
실제 산출물 ~500KB 대로 상한의 1/10 수준이다.

🔴 **이 판단이 매달린 값을 계약에 명시했다 — 오늘의 사실이지 규약이 아니다:**
**장변 1440px** 과 **JPEG 품질 상한 85(+하향)**. 둘 중 하나라도 바뀌면 재계산이 필요하다.

⚠️ **서버의 `maxBytes` 상한은 그대로 유지한다.** 앱이 아닌 클라이언트가 이 URL 로 올 수 있으므로
앱을 신뢰해서 없앨 수 있는 값이 아니다.

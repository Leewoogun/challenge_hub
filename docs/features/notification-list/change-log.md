### 1. §5 인라인 경고 — **왜 별도 절이 아니라 인라인인가**

§5 는 wire shape 논증으로는 완결돼 있었지만, 읽은 사람이 **"모르는 타입이 끝까지 열려 있다"** 로
이해하게 된다. 실제로는 **오늘 서버가 모르는 값을 내보낼 수 없고, 있었다면 *틀린 아는 값*을
낸다**(`toDomain()` 강등, 실측 재현). 그 사실이 `backend-report.md` 미해결 1번에만 있었는데
🔴 **계약을 읽는 사람은 report 를 안 읽는다.**

🔴 **접기(`<details>`)나 하위 절로 분리하지 않고 논증 바로 다음 줄에 인라인으로 넣었다.** 이
프로젝트에서 경고를 별도 절·접기로 분리했다가 안 읽혀 사고 난 것이 **3회**다(에이전트는 grep
으로 읽는다).

경고의 **마지막 문장이 핵심**이다 — *"앱의 폴백을 «쓸모없는 방어»로 읽지 마라."* 이 문장이
없으면 누군가 *"어차피 서버가 아는 값만 주는데 폴백이 왜 있냐"* 며 design §3.2 폴백을 걷어내고,
그러면 트리거(롤링 배포·수동 삽입)가 왔을 때 **막을 것이 하나도 없다.**

🔵 **논증 자체는 그대로 성립한다는 것도 함께 적었다** — 대기 중인 4종
(`REMIND`/`RESULT`/`TAUNT`/`FRIEND_REQUEST`)은 **이미 enum 에 있어 원문 그대로 도착한다**
(실측: `FRIEND_REQUEST` round-trip 확인). 즉 **앱이 방어해야 할 실제 케이스는 전부 앱까지
도달한다.**

### 2. §5 — "앱은 미지 타입을 숨기지 않고 표시한다"

noti-design(§3.2.2)과 noti-mobile 이 **각각 따로** 요청한 조항이다. 계약이 *"목록이 깨지지
않아야 한다"* 만 말하고 있어 **숨기는 것도 만족처럼 읽혔다.** 숨기면 **푸시로 본 알림이
목록에 없고**, 안 읽은 개수와 목록 길이가 어긋난다.

표(숨기지 않음 / 무채색 아이콘 / `body` 그대로 / 탭 비활성)로 명시했다. 🔵 `body` 를 박제로
저장한 push-fcm 결정이 여기서 값을 한다 — 앱이 타입별로 문구를 조립하는 구조였다면 모르는
타입은 **그릴 문구조차 없었다.**

### 3. §2 — 커서 비소비성 명시

noti-design 이 §6.3 에서 *"부분 실패 시 재시도는 **같은 커서로 다시 호출**하는 형태여야 한다 —
커서가 소비되어 무효해지는 설계면 알려 달라"* 고 물었다. **소비되지 않는다.**

`cursor` 는 서버가 상태로 들고 있는 토큰이 아니라 **`id` 비교값**(`WHERE id < :cursor`)이다.
같은 커서를 몇 번 보내도 같은 페이지가 오고, 없는 id 를 보내도 에러가 아니며(실측
`cursor=99999` → 200), 만료도 없다. **계약이 답하지 않으면 앱이 재시도 설계를 추측하게 되므로**
명시했다.

## 2026-09-01 — `NotificationEntity.toDomain()` KDoc 정정 (backend-dev) — 🔵 **계약 무관**

계약 문서 변경이 아니라 **서버 코드 주석**이지만, §5 인라인 경고와 **같은 사실을 다루는 쌍**
이라 함께 기록한다.

그 KDoc 이 *"(현재 `notifications` 는 0행이라 실제로 그런 row 는 없다.)"* 로 끝나고 있었다.
🔴 **낡았다** — push-fcm 이 4종을 발송하며 row 를 쌓고 있고 **실측 dev DB 14행**
(`CHALLENGE_REQUEST` 7 / `ACCEPTED` 3 / `REJECTED` 2 / `OPPONENT_VERIFIED` 2).

⚠️ **문구 오류가 아니라 위험도 오독을 부르는 문장이었다.** 그 괄호가 **강등 로직을 "이론상
안전"으로 보이게 하는 유일한 근거**인데 근거가 사라졌는데 문장만 남아 있으면 다음 사람이
위험도를 낮게 읽는다(pm-lead 지적).

**"0행이라 안전"을 진짜 이유로 교체했다** — 오늘 강등이 안 터지는 이유는 행이 없어서가 아니라
**쓰기가 제약돼 있어서**다(`fromDomain` 이 `type.name` 을 쓰므로 DB 에 들어가는 값은 enum 8종의
name 뿐이고 8종은 전부 round-trip). 함께 적은 것:

- 🔴 **읽기 경로가 생기면서 이 fallback 의 성격이 바뀌었다** — 이제 결과가 **사용자 화면에
  렌더되고 탭 목적지가 된다.** `CHALLENGE_REQUEST` 는 **실재하고 탭되는 타입**이라 모르는
  알림이 *"도전장이 왔다"* 로 **없던 사실을 찍고**, 앱이 가진 *"모르는 타입 → 비탭"* 폴백을
  **서버가 그 앞에서 무력화한다.**
- ⚠️ **`VerificationEntity.toDomain()` 과 "같은 방침"이라는 문장의 한계** — 거기서 type 은
  **내부 분기용**이라 틀리면 눈에 띄게 깨지지만, 여기서는 **렌더되는 값**이라 조용히 틀린다.
  **같은 코드 모양, 다른 위험 등급.**
- **고치지 않는 이유와 트리거 2개**(다중 인스턴스 배포 / enum 밖 타입 유입).

> 🔴 **pm-lead 의 최초 지시는 실행 불가능했고 그 사실도 기록한다.** *"목록 조회는 `toDomain()`
> 을 밟지 말고 컬럼에서 바로 프로젝션해 원문 String 을 내려라"* 였는데,
> `NotificationRepositoryImpl.findPageByUserId` 가 **`List<Notification>`(도메인)을 반환**하고
> `Notification.type` 이 enum 이라 **거기가 병목이라 "컬럼에서 바로"라는 길이 없다.**
> 하려면 도메인 모델을 String 으로 바꾸거나(발송부·문구·테스트로 번진다) 계층을 우회하는 별도
> 읽기 경로를 만들어야 한다. pm-lead 가 *"엔티티에 값이 있는 것과 그 값이 응답까지 갈 길이
> 있는 것은 다른 문제인데 후자를 안 봤다"* 로 정정했다. **지시를 그대로 따르지 않고 실측해
> 미해결로 올린 것이 맞는 처리**로 승인됐다.

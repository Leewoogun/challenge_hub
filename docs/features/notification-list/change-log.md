목록의 탭 규칙이 **타입 → 상태**로 바뀌면서(spec 2차 개정 §1) 앱이 판단할 정보가 필요해졌다.

### 🔴 원시 상태값 안이 **실측으로 기각됐다** — 이 개정의 핵심 판단

pm 제약(*"서버는 사실을 내리고 앱이 UI 정책을 갖는다"*)만 보면
**`referenceStatus: "PENDING"` 같은 원시 상태값이 더 «사실»** 이고, `type` 을 원문 String 으로 낸
것과 같은 결로 읽힌다. **그 안을 먼저 검토했고 실측이 기각했다.**

```sql
-- 홈 '받은 도전장' 실측 (ChallengeJpaRepository.findReceivedPending)
WHERE c.opponent_id = :me AND c.status = 'PENDING' AND c.deadline > :now
```

`ChallengeCommandService` KDoc: ***"마감 지난 row 는 DB 에서 `PENDING` 인 채로 남고 응답에서만
빠진다 (lazy expiry)"*** — 🔴 **«PENDING 이면서 이미 만료된» 챌린지가 정상적으로 존재한다.**

상태값을 내렸다면 앱은 *"PENDING = 탭 가능"* 으로 읽었을 것이고, 만료된 신청을 탭 → **홈의
'받은 도전장'이 비어 있다.** 🔴 **사용자가 신고한 증상이 원인만 바꿔 그대로 재발한다.**

**규칙의 소유자로 갈린다** — *"어떤 챌린지가 아직 응답 대기인가"* 는 **챌린지 도메인 규칙**이라
서버가, *"응답 대기인 신청만 탭 가능"* 은 **UI 정책**이라 앱이 갖는다. 앱이 앞의 것을 encode 하면
**챌린지 도메인이 바뀔 때 알림 화면이 조용히 틀리고 아무도 거기를 안 본다.**
🔵 **pm 제약을 어긴 게 아니라, «사실» 이 원시 컬럼값이 아니라 도메인 술어라는 것**이다.

**실측이 이 판단을 증명했다** ([§8.1](./api-contract.md)): 만료된 `PENDING` → `false`, 그리고
같은 계정의 `GET /challenges/received` 가 **정확히 같은 1건만** 반환. 두 술어가 일치한다.

### `null` 의 의미를 계약이 못박았다 (§9.2)

pm 이 *"«모르면 탭 가능» 과 «모르면 비탭» 은 반대 결과"* 라고 지적한 자리.
🔴 **둘 다 틀렸다 — `null` 은 «이 필드를 보지 마라»** 다. 이건 **결정자가 아니라 추가 조건**이고,
타입이 기본 규칙을 정한 뒤 *"조건부"* 인 타입에서만 값을 요구한다.
`null` 을 비탭으로 읽으면 **증거 도착이 안 눌리고**(spec 은 "항상"), 탭 가능으로 읽으면
**수락·거절이 눌린다.**

### 이름을 `tappable`/`actionable` 로 하지 않았다

pm 이 피하라고 한 이름이고 근거에 동의한다 — *"탭 가능한가"* 는 화면 판단이라 서버로 넘어오면
UI 가 바뀔 때 서버를 고치게 된다. `reference*` 접두는 `referenceId` 와 짝이고 **참조 대상이
타입마다 다르다는 중립성**을 승계한다(push-fcm 오픈이슈 3) — `FRIEND_REQUEST` 가 `users.id` 를
가리켜도 *"그 친구 요청이 아직 응답 대기인가"* 로 **의미가 그대로 성립한다.**

### join 을 쓰지 않는다 — **성능이 아니라 정합성** (§9.5)

pm 이 N+1 을 우려한 자리. **타입으로 거른 뒤 `IN` 절 배치 1회**로 해결했고 **페이지 크기와
무관하게 총 2쿼리**다(COUNT 없음, 빈 컬렉션 가드는 호출부 — 레포 선례).

🔴 **join 이 위험한 진짜 이유는 성능이 아니다.** `reference_id` 는 **FK 가 아니고 타입마다 참조
대상이 다르다.** `reference_id = challenges.id` 로 조인하면 **`FRIEND_REQUEST` 가 열리는 순간
`users.id` 를 `challenges.id` 에 조인한다** — 숫자가 겹치면 **엉뚱한 챌린지 상태가 친구 요청
알림에 붙고**, 아니면 행이 사라진다. **조용히 틀린다.**

### spec 오픈 이슈 3 — **부분 해소** (§9.6)

신청은 `false` 로 **사전 차단**돼 705 에 도달하지 않는다. **증거 도착은 여전히 705**(*"항상 탭"*).
증거 도착까지 차단하려면 이 필드가 *"대상이 존재하는가"* 로 넓어져야 하는데 그건
*"응답을 기다리는가"* 와 **다른 질문**이고, 두 뜻을 한 필드에 담으면 `false` 가 무엇을 뜻하는지
알 수 없게 된다.

### 1. §5 인라인 경고 — **왜 별도 절이 아니라 인라인인가**

§5 는 wire shape 논증으로는 완결돼 있었지만, 읽은 사람이 **"모르는 타입이 끝까지 열려 있다"** 로
이해하게 된다. 실제로는 **오늘 서버가 모르는 값을 내보낼 수 없고, 있었다면 *틀린 아는 값*을
낸다**(`toDomain()` 강등, 실측 재현). 그 사실이 `backend-report.md` 미해결 1번에만 있었는데
🔴 **계약을 읽는 사람은 report 를 안 읽는다.**

🔴 **접기(`<details>`)나 하위 절로 분리하지 않고 논증 바로 다음 줄에 인라인으로 넣었다.** 이
프로젝트에서 경고를 별도 절·접기로 분리했다가 안 읽혀 사고 난 것이 **3회**다(에이전트는 grep
으로 읽는다).

경고의 **마지막 문장이 핵심**이다 — *"앱의 폴백을 «쓸모없는 방어»로 읽지 마라."* 이 문장이
없으면 누군가 *"어차피 서버가 아는 값만 주는데 폴백이 왜 있냐"* 며 design §3.2 폴백을 걷어내고,
그러면 트리거(롤링 배포·수동 삽입)가 왔을 때 **막을 것이 하나도 없다.**

🔵 **논증 자체는 그대로 성립한다는 것도 함께 적었다** — 대기 중인 4종
(`REMIND`/`RESULT`/`TAUNT`/`FRIEND_REQUEST`)은 **이미 enum 에 있어 원문 그대로 도착한다**
(실측: `FRIEND_REQUEST` round-trip 확인). 즉 **앱이 방어해야 할 실제 케이스는 전부 앱까지
도달한다.**

### 2. §5 — "앱은 미지 타입을 숨기지 않고 표시한다"

noti-design(§3.2.2)과 noti-mobile 이 **각각 따로** 요청한 조항이다. 계약이 *"목록이 깨지지
않아야 한다"* 만 말하고 있어 **숨기는 것도 만족처럼 읽혔다.** 숨기면 **푸시로 본 알림이
목록에 없고**, 안 읽은 개수와 목록 길이가 어긋난다.

표(숨기지 않음 / 무채색 아이콘 / `body` 그대로 / 탭 비활성)로 명시했다. 🔵 `body` 를 박제로
저장한 push-fcm 결정이 여기서 값을 한다 — 앱이 타입별로 문구를 조립하는 구조였다면 모르는
타입은 **그릴 문구조차 없었다.**

### 3. §2 — 커서 비소비성 명시

noti-design 이 §6.3 에서 *"부분 실패 시 재시도는 **같은 커서로 다시 호출**하는 형태여야 한다 —
커서가 소비되어 무효해지는 설계면 알려 달라"* 고 물었다. **소비되지 않는다.**

`cursor` 는 서버가 상태로 들고 있는 토큰이 아니라 **`id` 비교값**(`WHERE id < :cursor`)이다.
같은 커서를 몇 번 보내도 같은 페이지가 오고, 없는 id 를 보내도 에러가 아니며(실측
`cursor=99999` → 200), 만료도 없다. **계약이 답하지 않으면 앱이 재시도 설계를 추측하게 되므로**
명시했다.

### 4. §2 — ADR-0012 승격 링크

pm-lead 판정으로 §2 의 결정이 **[ADR-0012](../../decisions/0012-list-pagination-cursor.md)** 로
승격됐다. §2 본문은 **지우지 않고 그대로 둔다** — 링크 한 줄만 머리말에 붙였다.

**둘의 역할이 다르다**: ADR 은 **프로젝트 규약의 정본**(다른 목록에 적용할 때 보는 곳),
§2 는 **알림에 적용한 구체 근거**(이 엔드포인트가 왜 이렇게 생겼는지). 🔴 **§2 를 ADR 로
대체하고 지우면 안 된다** — 계약을 읽는 사람이 ADR 까지 따라가지 않는다(§5 인라인 경고를 넣은
것과 같은 이유다).

> 🔵 **왜 CLAUDE.md 규칙 줄이 있는데도 ADR 인가** (pm-lead 승격 사유): 규칙 파일의 한 줄은 다음
> 사람이 다듬고 줄이고 옮기는데, 그때 **살아남는 것은 결론이고 사라지는 것은 근거**다. 이
> 결정에서 값이 큰 쪽은 결론(`?cursor=&size=`)이 아니라 근거 셋이고, 셋 다 **잃으면 다시 못
> 만드는 종류**다 — 특히 *"왜 `created_at` 이 아니라 `id` 인가"*.

### 5. 🔴 §2 숫자 정정 — "나머지 4종" → "기존 6종". **내가 낸 오류이고 번졌다**

§2 가 처음부터 *"나머지 4종(친구 목록·받은 요청·랭킹·보관함)"* 이라고 적고 있었다. **오답이다** —
`GET /challenges/active` 와 `GET /challenges/received` 를 빠뜨렸고, 실측 기존 목록 엔드포인트는
**6개**다.

⚠️ **이 숫자가 계약에서 나가 CLAUDE.md 규칙 줄과 백로그로 퍼졌다.** pm-lead 가 ADR 작성 중
실측표를 보고 CLAUDE.md 를 6으로 고쳤고, 백로그에도 *"여기 적힌 «5종»은 부정확했다"* 를 달았다.
🔴 **그 출처가 내 계약이었다** — 백로그의 "5종"(2026-08-26 실측분)과 내 "4종"은 **서로 다른 두
개의 틀린 숫자**였고 우연히 둘 다 6이 아니었다.

🔵 **정정하면서 원문을 지우지 않고 인라인 정정 주석으로 남겼다** — *"계약에 적은 미검증 숫자가
어떻게 번지는지"* 의 사례라서다. ADR §맥락이 **엔드포인트를 숫자가 아니라 이름으로 나열**하는
것이 이 사고의 대응이다.

> ⚠️ **ADR-0012 자신도 같은 실수를 한 번 했다.** §맥락에서는 숫자를 피하고 이름으로 나열해
> 놓고, §적용 범위 제목에는 *"나머지 5종"* 이라고 썼다(표에는 6개가 들어 있었다). 제출 직후
> 자체 검산에서 발견해 **6종**으로 고치고, 그 자리에 *"백로그의 «5종»을 이 ADR 은 쓰지 않는다"*
> 를 명시했다. **숫자를 피하기로 결정한 문서 안에서도 숫자는 다시 새어 나온다.**

## 2026-09-01 — `NotificationEntity.toDomain()` KDoc 정정 (backend-dev) — 🔵 **계약 무관**

계약 문서 변경이 아니라 **서버 코드 주석**이지만, §5 인라인 경고와 **같은 사실을 다루는 쌍**
이라 함께 기록한다.

그 KDoc 이 *"(현재 `notifications` 는 0행이라 실제로 그런 row 는 없다.)"* 로 끝나고 있었다.
🔴 **낡았다** — push-fcm 이 4종을 발송하며 row 를 쌓고 있고 **실측 dev DB 14행**
(`CHALLENGE_REQUEST` 7 / `ACCEPTED` 3 / `REJECTED` 2 / `OPPONENT_VERIFIED` 2).

⚠️ **문구 오류가 아니라 위험도 오독을 부르는 문장이었다.** 그 괄호가 **강등 로직을 "이론상
안전"으로 보이게 하는 유일한 근거**인데 근거가 사라졌는데 문장만 남아 있으면 다음 사람이
위험도를 낮게 읽는다(pm-lead 지적).

**"0행이라 안전"을 진짜 이유로 교체했다** — 오늘 강등이 안 터지는 이유는 행이 없어서가 아니라
**쓰기가 제약돼 있어서**다(`fromDomain` 이 `type.name` 을 쓰므로 DB 에 들어가는 값은 enum 8종의
name 뿐이고 8종은 전부 round-trip). 함께 적은 것:

- 🔴 **읽기 경로가 생기면서 이 fallback 의 성격이 바뀌었다** — 이제 결과가 **사용자 화면에
  렌더되고 탭 목적지가 된다.** `CHALLENGE_REQUEST` 는 **실재하고 탭되는 타입**이라 모르는
  알림이 *"도전장이 왔다"* 로 **없던 사실을 찍고**, 앱이 가진 *"모르는 타입 → 비탭"* 폴백을
  **서버가 그 앞에서 무력화한다.**
- ⚠️ **`VerificationEntity.toDomain()` 과 "같은 방침"이라는 문장의 한계** — 거기서 type 은
  **내부 분기용**이라 틀리면 눈에 띄게 깨지지만, 여기서는 **렌더되는 값**이라 조용히 틀린다.
  **같은 코드 모양, 다른 위험 등급.**
- **고치지 않는 이유와 트리거 2개**(다중 인스턴스 배포 / enum 밖 타입 유입).

> 🔴 **pm-lead 의 최초 지시는 실행 불가능했고 그 사실도 기록한다.** *"목록 조회는 `toDomain()`
> 을 밟지 말고 컬럼에서 바로 프로젝션해 원문 String 을 내려라"* 였는데,
> `NotificationRepositoryImpl.findPageByUserId` 가 **`List<Notification>`(도메인)을 반환**하고
> `Notification.type` 이 enum 이라 **거기가 병목이라 "컬럼에서 바로"라는 길이 없다.**
> 하려면 도메인 모델을 String 으로 바꾸거나(발송부·문구·테스트로 번진다) 계층을 우회하는 별도
> 읽기 경로를 만들어야 한다. pm-lead 가 *"엔티티에 값이 있는 것과 그 값이 응답까지 갈 길이
> 있는 것은 다른 문제인데 후자를 안 봤다"* 로 정정했다. **지시를 그대로 따르지 않고 실측해
> 미해결로 올린 것이 맞는 처리**로 승인됐다.

# 알림 목록 (notification-list) — Spec

- **feature-id**: notification-list
- **owner**: pm-lead
- **상태**: draft
- **생성**: 2026-09-01
- **선행**: [push-fcm](../push-fcm/summary.md)(발송·row 저장) · [push-deeplink](../push-deeplink/summary.md)(목적지 매핑)
- **해소 대상**: 백로그 🟢 *"알림 목록 화면 미구현"*

## 배경

**알림은 오는데 볼 곳이 없다.** `notifications` row 는 push-fcm 부터 쌓이고 있고(4종 발송 운용 중),
홈 상단 벨 아이콘도 이미 `Route.Notifications` 로 연결돼 있는데 **그 화면이 `PlaceholderScreen`** 이다.
기획서 §4 IA 가 정의한 진입 경로가 빈 화면으로 끝난다. 🔵 **푸시를 놓치면 그걸로 끝**인 현재 상태를
메우는 것이 이 feature 의 값이다(RESULT·REMIND 푸시를 제외한 판정 feature 결정 이후 더 중요해졌다).

## §0 사전 실측 — 배선은 다 있고 조회 API + 화면만 없다

| | 상태 |
|---|---|

| 발송 4종 (`CHALLENGE_REQUEST`/`ACCEPTED`/`REJECTED`/`OPPONENT_VERIFIED`) | ✅ 운용 중 (RESULT·REMIND 는 [판정 feature 결정](../challenge-result/summary.md)으로 제외) |
| 홈 벨 → 알림 화면 진입 | ✅ 이미 연결(`HomeRoute.onBellClick`) — **화면만 placeholder** |
| 푸시 탭 → 목적지 매핑 (`PushEvent` → `Route`) | ✅ push-deeplink 완성 — **목록 탭에서 재사용 가능** |
| **조회 API** | ❌ **0건** — 이 feature 의 신규 |
| Lovable `notifications.tsx` | ✅ 51줄 존재 — 타입별 아이콘·색 + 메시지 + 상대 시각. ⚠️ mock 6종 중 **taunt·reminder·result·lost 는 아직 발송되지 않는 타입** |

## 사용자 시나리오

1. 홈 상단 벨을 눌러 알림 목록을 본다 — 최신순으로 *"누가 무엇을 했는지"* 와 시각.
2. 알림을 탭하면 **그 알림이 가리키는 화면으로 이동**한다(푸시를 탭한 것과 같은 목적지).
3. 알림이 없으면 빈 상태를 본다.

## 수용 기준

- [ ] 홈 벨 → 알림 목록(최신순). placeholder 교체

- [ ] 알림 탭 → **push-deeplink 와 같은 목적지**로 이동 (규칙 사본을 만들지 않는다)
- [ ] 🔴 **발송되지 않는 타입이 화면에 자리를 갖지 않는다** — Lovable mock 의 taunt·reminder·result·lost 는
  현재 서버가 만들지 않는다. 미래 타입을 미리 그리지 않되, **모르는 타입이 와도 목록이 깨지지 않아야 한다**
- [ ] 빈 상태 화면
- [ ] 홈 벨 뱃지가 `unreadCount > 0` 일 때 점등된다(현재 `false` 하드코딩 2곳)
- [ ] 🔴 **목록에서 뒤로 나온 홈에 점이 없다** — (B)가 만드는 유일한 화면 리스크(design §4.5.1).
  읽었는데 점이 남으면 **뱃지를 켠 것이 오히려 신뢰를 깎는다.** 수단은 mobile 판단, 결과만 고정.
  ⚠️ 반대 방향(홈 체류 중 푸시 도착 시 실시간 점등)은 **요구하지 않는다** — 푸시가 이미 알렸고,
  요구하면 홈이 알림을 구독해야 해서 이 feature 가 살 이유 없는 비용이다
- [ ] 다음 쪽 로딩·부분 실패 처리(design §6.3) — 하단 인디케이터, 실패 시 그 자리에 `"다시 시도"`.
  🔴 스낵바만 띄우면 사라진 뒤 더 볼 수단이 없다. 끝 도달은 **무표시**

## 🔴 실측 하자 2건 (2026-09-01, mobile 발견 · pm 확인)

두 건 다 **조용히 틀린다** — 화면에 거짓이 찍히는데 앱이 알 방법이 없다는 점에서 같은 종류다.

### 1. 서버가 모르는 `type` 을 `CHALLENGE_REQUEST` 로 강등한다

`NotificationEntity.kt` L61-62 `runCatching { NotificationType.valueOf(type) }.getOrDefault(CHALLENGE_REQUEST)`.
L53-54 KDoc 이 이를 **의도된 방침**으로 명시(`VerificationEntity.toDomain()` 과 동일 방침). 컬럼은 `var type: String`
(L32-33)이라 **원문은 DB 에 살아 있고, 잃는 건 매핑 단계다.**

**정책이 맞는 자리와 틀린 자리가 갈린다** — verification 에서 type 은 내부 분기용이라 잘못 떨어지면 눈에 띄게 깨진다.
목록에서 type 은 **사용자에게 그대로 렌더되는 값**이라, 폐기된 `SIGN_REQUEST` row 가 화면에 **"도전장 도착"** 이라는
없던 사실로 찍히고 탭하면 엉뚱한 곳으로 간다.

→ **판정**: 목록 조회는 `toDomain()` 을 밟지 말고 **컬럼에서 바로 프로젝션**해 원문 String 을 내린다.
🔴 `toDomain()` **자체는 고치지 않는다**(다른 경로가 의존). **이것이 `type` 을 String 계약으로 정한 이유다** —
원문을 보존해야 앱이 모르는 타입을 모르는 타입으로 취급할 수 있다.

### 2. `toRelativeKoreanString` 을 알림에 쓰면 **모든 행이 "마감"** 으로 찍힌다

그 함수는 마감까지 **남은** 시간 전용이라 과거 시각에 `"마감"` 을 반환한다(`RelativeTimeFormat.kt:27`).
**알림 시각은 전부 과거다.** → 신규 포맷터(T-D2). 🔴 **재발 방지는 네이밍으로** — 두 함수가 나란히 있으면
다음 사람이 또 가까운 걸 집는다. 이름에 방향(남은/지난)을 드러내고 KDoc 에 서로 교차로 금지를 박는다.

## 🔴 2차 개정 (2026-09-01) — 목록 탭 규칙 + 날짜 그룹핑

**사용자 실사용 피드백**: *"알림 화면에서 이동하니까 이미 지난 챌린지도 이동이 되어서 어색하다."*

### 1. 탭 규칙이 "타입"에서 "상태"로 바뀐다

| 알림 | 목록에서 탭 | 목적지 |
|---|---|---|
| 신청 (`영혼의 맹세`) | 🔴 **챌린지가 아직 대기 중일 때만** | 홈 (받은 도전장) |
| 증거 도착 | ✅ 항상 | 챌린지 상세 |
| 수락 (`계약 완료.`) | ❌ | — |
| 거절 (`ㅠㅠ`) | ❌ | — |

🔵 **푸시 트레이 탭은 무변경** — 4종 모두 지금 그대로 이동한다. 바뀌는 것은 **앱 안의 목록**뿐이다.

**왜 신청만 조건부인가.** 홈의 '받은 도전장' 섹션은 **처리되면 비워지는 자리**다. 그래서 지난 신청
알림을 탭하면 *"거기 뭔가 있다"* 고 말해놓고 아무것도 안 보여준다. **이동이 무의미해지는 조건을
그대로 탭 조건으로 뒤집었다** — 처리되기 전에만 보내면 그 실패가 애초에 안 생긴다.

**왜 증거 도착은 무조건인가.** 인증 사진은 **상세에만 있고 챌린지가 끝나도 사라지지 않는다.**
지난 알림에서 눌러도 헛걸음이 아니다.

**왜 수락·거절은 아닌가.** 수락은 계약서가 남지만 그건 홈·보관함에서도 닿는다. 거절은 **대상 자체가
없다**(계약서가 만들어지지 않는다).

### 2. 🔴 계약 개정이 따른다 — 앱이 "대기 중"을 알 방법이 없다

현재 응답은 `notificationId` · `type` · `body` · `referenceId` · `createdAt` 다섯 개뿐이다.
**서버가 신청 알림의 대상 상태를 함께 내려야 한다.**

🔴 **shape 은 backend 가 정한다**(계약 소유). pm 이 거는 제약 둘:
1. **서버는 사실을 내리고 앱이 UI 정책을 갖는다** — `type` 을 원문 String 으로 낸 것과 같은 결.
   *"탭 가능한가"* 는 화면의 판단이지 서버가 알 일이 아니다.
2. 신청 외 타입에는 의미가 없는 값이다. **nullable 을 어떻게 읽을지 계약에 명시**할 것.

⚠️ **부수 효과 — 같은 카드의 모양이 시간에 따라 바뀐다.** 어제 탭되던 신청 알림이 오늘은 안 된다.
의도된 동작이지만 **사용자에겐 "왜 안 눌리지"로 보일 수 있어** 아래 3번 구분 표현이 그만큼 중요하다.

### 3. 탭 가능/불가 시각 구분

🔴 **기존 "탭 비활성"에 이미 다른 뜻이 있다** — design §3.2 가 **모르는 타입**을 *무채색 아이콘 +
탭 비활성* 으로 명세했다. 여기에 신청·수락·거절을 그대로 태우면 **정상 알림이 고장난 알림처럼 보인다.**

→ 방향: **비탭을 낮추지 말고 탭에 어포던스를 더한다.** 탭 가능한 카드에만 이동 신호(화살표 등)와
눌림 효과를 주고, 비탭 카드는 색을 그대로 둔다. 구체 명세는 design 판정.

### 4. 날짜 그룹핑

목록을 날짜로 묶어 표시한다. ⚠️ **커서 페이지네이션과 맞물리는 지점**: 한 날짜 그룹이 페이지 경계에
걸치면 **같은 헤더가 두 번 찍히기 쉽다.** 헤더는 서버가 아니라 **앱이 이어붙인 전체 목록 기준으로**
붙인다(mobile 확인: `Data.items` 가 이미 이어붙인 전체 목록이라 재료는 있다. 단 **그룹 결과를 `get()`
으로 내면 매번 새 List 라 하위 Composable skipping 이 깨진다** — 생성 시점 `val` 로 고정).

#### 🔴 정정 (mobile 실측) — "중복되지 않는지"가 아니라 **비-오늘 구간은 전부 동어반복이다**

내가 위 문단을 *"경과 시각 표기와 중복되지 않는지 design 판정"* 이라고 열어 뒀는데, **실측하면
열어 둘 여지가 없다.** 그룹 단위와 `toElapsedKoreanString` 의 가지 4·5 가 **글자 단위로 같은 어휘**다:

| 그룹 | 헤더 | 그 아래 행들의 시각 | |
|---|---|---|---|
| 오늘 | `오늘` | `방금 전` · `3분 전` · `5시간 전` | ✅ 서로 보완 |
| 어제 | `어제` | **전부 `어제`** | ❌ 100% 동어반복 |
| 그 이전 | `8월 30일` | **전부 `8월 30일`** | ❌ 100% 동어반복 |

어제 알림이 12건이면 화면에 `어제` 가 **13번** 찍힌다. **부분 중복이 아니라 비-오늘 구간 전체다.**

🔵 **`toElapsedKoreanString` 을 고치는 문제가 아니다.** 그 함수는 **그룹핑이 없다는 전제**에서 확정됐고
그 전제 아래서는 여전히 맞다. 그룹핑이 붙으면서 **같은 값이 한 화면의 두 자리에 그려지게 된 것**이라,
고칠 자리는 함수가 아니라 **이 화면의 표현**이다 → design 판정.

⚠️ **pm 관측**: 어느 안을 택하든 **오늘 그룹과 비-오늘 그룹의 시각 표기 형식이 갈릴 수 있다**(예:
오늘은 `3분 전`, 어제는 `14:30`). 그건 결함이 아니라 **최근 것은 상대 시각이, 지난 것은 절대 시각이
더 쓸모 있다**는 정합이다 — 갈리는 것 자체를 문제로 보고 통일하지 마라.

| 항목 | 내용 |

| **대상** | `GET /api/v1/challenges/history` (§1). §2 탈퇴 · §3 로그아웃 **무변경** |

| **서버 변경** | 🔴 **코드 0.** 계약 문서 + 회귀 방지 단언 1건뿐 |

### 왜 바뀌었나 — 🔴 **정확한 동작이 고장으로 보였다**

실기 DB 의 종료 챌린지가 전부 이번 달이라 **하한(최초 기록월) = 상한(이번 달)** 이 되어
양쪽 화살표가 동시에 비활성됐다. **카드는 보이는데 아무것도 안 움직여 사용자가 "고장"으로 읽었다.**

🔴 **설계도 계약도 정확히 동작했다.** v3 의 하한은 *"확정적으로 빈 달의 사막으로 걸어 들어가지
않게 한다"* 를 정확히 이행한 것이고, 기록이 이번 달뿐이면 갈 곳이 없는 게 참이다.
**문제는 참인 상태를 화면이 고장처럼 말했다는 것**이고, 사용자는 *"이게 네 기록 전부다"* 라는
주장보다 **"화면이 반응한다"** 를 우선했다.

### 🔴 서버 코드가 안 바뀌는 이유 — 하한은 **앱이 스스로 걸던 규칙**이었다

이 엔드포인트는 **애초에 하한을 강제한 적이 없다.** 거부하는 것은 **미래 달 하나뿐**이고,
과거는 어느 달이든 빈 목록으로 정상 응답해 왔다(v3 계약 문면: *"하한보다 이전 달은 에러가
아니다"*). 하한은 서버가 준 `firstArchivedMonth` 를 **앱이 경계로 해석**해서 생긴 것이라,
그 해석을 걷어내면 개정이 끝난다.

⚠️ 그래서 이 항목은 v3 의 *"하한 아래도 빈 달 정상 응답"* 이 **예외 경로에서 정상 경로의 주력
동작으로 승격**된 것이기도 하다.

### 무엇이 바뀌었나

| 대상 | 조치 |
|---|---|
| 응답 필드 | ✅ **무변경** (`month` · `firstArchivedMonth` · `histories`) |
| `firstArchivedMonth` **용도** | 🔴 **축소** — 경계 → ① 빈 상태 2종 판별 ② 빈 달 고지 기준 |
| 앱의 `canPrev` | 🔴 **폐기** — 항상 true |
| `canNext`(상한 = 이번 달) · 카드 7필드 · `challengeDate` 축 · code 700 2종 | ✅ **무변경** |
| DB 마이그레이션 | **없음** |

### ⚠️ `가입월` 안은 검토 후 폐기됐다 — 🔴 **참인 것과 쓸모 있는 것은 다르다**

pm-lead 초기 선호가 가입월이었고 **논리는 참이었다** — 챌린지 생성엔 인증이 필요하고
`challengeDate` ∈ {오늘, 내일}이라 `challengeDate >= created_at` 이 구조적으로 성립하므로,
가입월은 상한과 **같은 구조의 데이터 사실**이다. 🔴 **그런데 이번 사고를 못 고친다:**

| 계정 (실기 DB 실측) | 가입월 | 기록 | 가입월 안 | 무제한 안 |
|---|---|---|---|---|
| 이우건 | 2026-05 | 2026-08 전부 | ✅ | ✅ |
| 테스터1·2·3 | **2026-08** | 2026-08 전부 | 🔴 **양쪽 비활성 유지** | ✅ |

가입 첫 달 사용자는 정의상 `가입월 = 이번 달` 이라 **하한 = 상한**이 되어 증상이 재현된다.
**가입월 안은 계정이 오래됐을수록 잘 듣고 신규일수록 안 듣는데**, spec 이 이 문제를 *"신규
서비스에서 가장 흔한 초기 상태"* 로 규정했다 — **문제가 가장 자주 나는 집합에서 해법이 가장
약하다.** backend·mobile·design 이 **독립적으로 같은 실측**에 도달했고 pm-lead 가 선호를 철회했다.

🔴 **여기서 배운 것**: *"대칭성은 **이 경계가 참인가**를 증명하지 **경계를 두는 것이 바람직한가**를
증명하지 않는다."*

### 🔴 `firstArchivedMonth` 를 지우지 않은 이유

pm-lead 가 *"안 읽는 필드 네 종류 비용"* 정식화를 적용하라고 지시했는데 **적용 대상이 아니다 —
여전히 읽힌다.** 하나만 죽고 둘이 남았다:

| 역할 | v4 |
|---|---|
| ① `<` 경계(하한) | 🔴 **소멸** |
| ② 빈 달 vs 기록 전무 판별 (CTA 유무) | ✅ **존치** — 대체 출처 없음 |
| ③ 🔴 **빈 달 고지** — design §2.5.1a-⑤ *"첫 기록은 YYYY년 M월이에요"* | ✅ **신규 용도** |

③이 특히 중요하다 — 🔴 **1차 하한 논거는 폐기가 아니라 수단이 바뀐 것**이다.
*"보관함은 '이게 네 기록 전부다'라고 주장하는 화면인데 하한이 없으면 그 주장을 할 수 없다"* 의
요구는 **차단이 아니라 주장할 수단**이었고, design 이 그것을 **차단 → 고지**로 옮겼다.
사용자는 계속 갈 수 있지만 **더 가도 없다는 걸 안다.**

⚠️ 대신 계약·KDoc 에 🔴 *"이 값으로 `<` 를 막지 마라"* 를 박고, 컨트롤러 테스트에
**하한 필드가 wire 에 되살아나면 실패**하는 단언을 넣었다(pm-lead 의 "되살림 유혹" 대응).

### 감수하는 것

이론상 끝없이 과거로 갈 수 있다. 실사용 유인이 없고 각 화면이 빈 달로 일관되므로 수용한다
(spec 명시).

### 🔴 3자 협의로 뒤집힌 것 — 경계 신호의 형태

backend v2 초안은 `hasPrevious`/`hasNext` **불리언 2개**였다. archive-month-design(§2.1.2·§7.1)과
archive-month-mobile 이 **독립적으로 같은 반례**를 들고 기각했고 **그쪽이 옳다.**

확정 사항 둘이 맞물려 상대 불리언을 구현 불가능하게 만든다:
- 사용자 확정 *"빈 달도 건너뛰지 않는다"* → 하한까지 가려면 `<` 를 여러 번 눌러야 하므로
  **연타가 예외가 아니라 정상 사용**이다.
- design §2.5.4.3-① *"월 라벨은 탭 즉시 바뀌고 화살표는 계속 눌린다"* → 응답을 기다리며 입력을
  잠그면 *"하나씩 지나간다"* 가 **매 칸 네트워크 왕복만큼 느려져 사실상 불가능**해진다.

불리언은 **그 달의 응답이 와야** 그 달의 경계를 안다:

```
하한 5월, 사용자는 6월
  탭 ①  →  5월 요청 (in flight). 5월이 하한인지 아직 모른다
  탭 ②  →  🔴 4월. 존재할 수 없는 달에 사용자가 서 있다
  (4월 응답) →  hasPrevious=false 로 그제서야 "여기가 끝"
```

**경계를 넘은 뒤에 경계를 통보받는다** — 하한을 만든 목적(*"확정적으로 빈 달의 사막으로 걸어
들어가지 않게 한다"*)을 한 탭 늦게 이행한다. 대칭으로 `>` 연타는 **미래 달 요청 → code 700**
을 만들어 **정상 조작이 오류 화면**이 된다.

절대값이면 `canPrev = month > firstArchivedMonth` 가 **왕복 없이 아무 달에서나** 계산돼 그 탭이
애초에 거부된다.

⚠️ **backend 초안의 오류를 기록해 둔다** — *"불리언이 신호가 하나라 더 적다"* 며
`result`+`myResult` 유추(*"신호 둘이 한 결정을 놓고 경쟁"*)를 걸었는데, **여기서 불리언은
절대값의 손실 있는 투영**이지 경쟁하는 두 표현이 아니다. 절대값 하나만 주므로 경쟁도 없다.
그래서 design 은 별도 `earliestMonth` 필드를 **명시적으로 금지**했다 — `firstArchivedMonth` 가
곧 그 값이다.

### 🔴 병존안(불리언 유지 + 절대값 추가)도 검토됐고 기각됐다

*"이미 검증됐으니 불리언을 남기고 `firstArchivedMonth` 만 추가하자"* 는 안이 한때 확정 직전까지
갔다. 근거는 *"안 읽는 필드의 비용은 0"* 이었는데 **그게 틀렸다. 비용이 네 종류다** (pm-lead 정리):
① 계약 표면에 남아 문서가 설명해야 한다 ② 같은 사실의 두 표현이라 **어긋남 고정 테스트**가 필요해진다
③ 앱이 *"왜 이 필드를 버리는지"* 를 문서로 남겨야 한다 ④ 🔴 **다음 사람이 되살릴 유혹을 받는다.**

🔴 **이 논거가 "두 소비자가 반대했다"보다 오래 버틴다** — 합의는 사람이 바뀌면 약해지지만
비용은 남는다. 계약 §1 에도 같은 절을 뒀다.

✅ **design 도 자기 근거 하나를 정정했다** — 초판의 *"불리언은 빈 달 2종을 구분 못 한다"* 는
과장이었고(`histories=[] && !hasPrevious && !hasNext` 로 구분은 된다), backend 지적으로 §2.1.2 에
정정 주석을 달았다. **형태 판정은 연타 논거만으로 선다.**

### 모바일에 걸리는 지점

- 🔴 **1차에 없던 표면 하나**: `<`/`>` 연타로 **요청이 여러 개 나가고 응답 순서가 보장되지
  않는다.** 늦게 온 옛 응답이 현재 월 표시 아래 다른 달 카드를 그릴 수 있다 —
  `data.month` 에코가 그 폐기 판정의 근거다(앱은 `flatMapLatest` + 에코 대조).
- 조회 실패 시 재시도 대상이 **"지금 보고 있던 월"** 이고, 실패 응답에는 `month` 가 없다
  (`BaseResponse` 3필드뿐) — 앱이 마지막 성공 응답의 에코를 들고 있어야 한다.
- ⚠️ **`month` 는 zero-padding 필수** — `2026-8` 은 code 700 이다 (실측).
- 🔴 **`firstArchivedMonth` 는 null 이어도 키가 실린다** — 이 레포 Jackson 에
  `@JsonInclude(NON_NULL)` 이 없다(실측). 앱이 키 존재를 전제해도 되고, 그 전제를
  `WireShapeContractTest` 가 원문으로 고정한다.
- 부분 매핑 실패 스낵바(design §2.5.4.2)는 유지되지만 **"일부"의 모수가 전체가 아니라 한 달치**다.

### 무엇이 바뀌었나

```
[개정 전]  GET /challenges/history                       (파라미터 없음)
           data: { histories: [...전체 최신순...] }
           월 그룹핑 = 앱이 challengeDate 앞 7글자로

[개정 후]  GET /challenges/history?month=2026-08          (optional, 생략 시 서버 KST 이번 달)
           data: { month, firstArchivedMonth, histories: [...그 달...] }
           월 그룹핑 = 개념 자체가 사라짐 (응답 하나가 한 달치)
```

| 대상 | 조치 |
|---|---|
| 요청 `month` (`yyyy-MM`) | 🔴 **신설.** optional — 생략 시 **서버 KST 이번 달** |
| `data.month` | 🔴 **신설** (non-null). 요청 값의 에코 = 앱의 **상한** + stale 응답 폐기 |
| `data.firstArchivedMonth` | 🔴 **신설** (`yyyy-MM`, **nullable**). 앱의 **하한** + "기록 전무" 신호 |
| `data.histories` | 🔴 **의미 변경** — 전체 → **그 달치**. 타입·요소 shape 은 그대로 |
| 카드 7필드 | ✅ **무변경.** `challengeId`·`challengeDate`·`opponentNickname`·`myMission`·`opponentMission`·`bet`·`myResult` |
| `challengeDate` 축 · `id DESC` · `EXPIRED` 제외 · `myResult` 서버 뒤집기 | ✅ **유지** (근거도 그대로 선다) |
| DB 마이그레이션 | **없음.** 스키마 변경 0 — 기존 컬럼에 범위 조건이 붙었을 뿐이다 |

⚠️ **초안(v2)은 경계를 `hasPrevious`/`hasNext` 불리언 2개로 줬다가 철회했다** — 사유는 아래
"3자 협의로 뒤집힌 것" 절. 계약 문서에는 v3 만 남고, 뒤집힌 근거는 그 절과 협의 이력에 있다.

### 왜 바뀌었나 — 1차가 사용자 문면을 해석으로 덮었다

사용자 원래 지시는 **"월별로 조회해서 카드 형식"** 이었다. design 이 그것을 *"월별로 정리"* 로
읽어 전체 스크롤 + 월 섹션 헤더로 갔고(design §2.1), backend 제안과 일치해 `confirmed` 가 됐다.
2026-08-28 확인 시점에 사용자가 **문면대로 월 이동**으로 정정했다.

사용자 확정 4개는 협상 대상이 아니다: **월 1칸씩 순차 이동 · 빈 달도 건너뛰지 않는다 ·
첫 진입은 항상 이번 달 · 미래 달로 가지 않는다.**

### 🔴 1차 확정 근거 중 무효가 된 것 2개

계약 §1 과 design §2.1 이 조회 단위를 정할 때 쓴 근거다. **결정이 뒤집혔으므로 근거도 같이
치운다** — 남겨 두면 다음에 읽는 사람이 폐기된 결정을 되살린다.

1. *"월 이동 UI 는 빈 월을 계속 만나게 하는 UI다"* → **사용자가 그 동작을 선택했다.**
   대신 **빈 달 표시의 완성도**가 새 요구사항이 된다 (spec §후속 개정 명시).
2. *"최신순 전체 목록은 첫 화면 최상단이 가장 최근 종료 건이라 spec 수용 기준
   (홈 7일 노출이 지난 결과에도 도달)이 **아무 조작 없이** 충족된다"* → **이번 달에 기록이
   없으면 깨진다.** pm-lead 판정: 도달 경로가 존재하고 조작이 1~2회면 충족으로 본다.

### 🔴 부수 효과 — 백로그 항목 하나가 **철회된다**

1차는 *"보관함이 프로젝트 최초의 무한히 자라는 목록"* 이라 페이지네이션 도입 1순위로
백로그에 올렸다(계약 §5 · backend-report). **월 단위가 되면서 그 전제가 사라졌다** — 한 응답의
상한이 한 달치로 고정된다.

전 엔드포인트 페이지네이션 통일 논의는 그대로 남지만 **보관함은 그 1순위에서 빠진다.**
백로그 항목 문면 정정 대상 (pm-lead).

### 형태 결정 (사용자 확정의 하위 — 3자 협의로 확정)

| 쟁점 | 결정 | 한 줄 근거 |
|---|---|---|
| 파라미터 형식 | `?month=2026-08` 단일 (`yyyy-MM`) | 연·월이 어긋날 수 없다. `WIRE_DATE` 앞 7글자와 같은 축 |
| 첫 진입 | **파라미터 생략 → 서버가 이번 달로** | 앱이 기기 시계를 읽지 않게 한다. 기기 타임존이 KST 가 아니면 월말·월초에 한 달 어긋난다 (`DeadlineType` 선례) |
| 과거 하한 **값** | **최초 `COMPLETED` 기록의 월.** 0건이면 `null` | 그 아래는 0건이 보장된다. 무한이면 화면이 *"이게 전부다"* 를 주장할 수 없다 |
| 🔴 과거 하한 **형태** | **절대값 `firstArchivedMonth: String?`** | 아래 "3자 협의로 뒤집힌 것" |
| 상한 | 이번 달 (앱은 **첫 응답의 `month` 에코**로 안다) | UI 규칙이 아니라 **데이터 사실** — `COMPLETED` 의 `challengeDate` 는 구조상 오늘 이하 |
| 미래 달 요청 | **code 700 (HTTP 200)**. clamp 안 함 | clamp 하면 `month` 에코와 요청이 어긋나 월 표시와 카드가 다른 말을 한다. 앱이 안 보내므로 **안전망** |
| 하한 아래 요청 | **에러 아님** — 빈 달 정상 응답 | 미래는 데이터가 **존재할 수 없는** 구간, 과거는 **없을 뿐인** 구간 |
| 빈 달 표현 | `histories: []`. 전용 플래그 없음 | "이 달만 비었다" vs "기록 전무"는 `firstArchivedMonth == null` 로 구분된다 |

### 🔴 3자 협의로 뒤집힌 것 — 경계 신호의 형태

backend v2 초안은 `hasPrevious`/`hasNext` **불리언 2개**였다. archive-month-design(§2.1.2·§7.1)과
archive-month-mobile 이 **독립적으로 같은 반례**를 들고 기각했고 **그쪽이 옳다.**

확정 사항 둘이 맞물려 상대 불리언을 구현 불가능하게 만든다:
- 사용자 확정 *"빈 달도 건너뛰지 않는다"* → 하한까지 가려면 `<` 를 여러 번 눌러야 하므로
  **연타가 예외가 아니라 정상 사용**이다.
- design §2.5.4.3-① *"월 라벨은 탭 즉시 바뀌고 화살표는 계속 눌린다"* → 응답을 기다리며 입력을
  잠그면 *"하나씩 지나간다"* 가 **매 칸 네트워크 왕복만큼 느려져 사실상 불가능**해진다.

불리언은 **그 달의 응답이 와야** 그 달의 경계를 안다:

```
하한 5월, 사용자는 6월
  탭 ①  →  5월 요청 (in flight). 5월이 하한인지 아직 모른다
  탭 ②  →  🔴 4월. 존재할 수 없는 달에 사용자가 서 있다
  (4월 응답) →  hasPrevious=false 로 그제서야 "여기가 끝"
```

**경계를 넘은 뒤에 경계를 통보받는다** — 하한을 만든 목적(*"확정적으로 빈 달의 사막으로 걸어
들어가지 않게 한다"*)을 한 탭 늦게 이행한다. 대칭으로 `>` 연타는 **미래 달 요청 → code 700**
을 만들어 **정상 조작이 오류 화면**이 된다.

절대값이면 `canPrev = month > firstArchivedMonth` 가 **왕복 없이 아무 달에서나** 계산돼 그 탭이
애초에 거부된다.

⚠️ **backend 초안의 오류를 기록해 둔다** — *"불리언이 신호가 하나라 더 적다"* 며
`result`+`myResult` 유추(*"신호 둘이 한 결정을 놓고 경쟁"*)를 걸었는데, **여기서 불리언은
절대값의 손실 있는 투영**이지 경쟁하는 두 표현이 아니다. 절대값 하나만 주므로 경쟁도 없다.
그래서 design 은 별도 `earliestMonth` 필드를 **명시적으로 금지**했다 — `firstArchivedMonth` 가
곧 그 값이다.

### 🔴 병존안(불리언 유지 + 절대값 추가)도 검토됐고 기각됐다

*"이미 검증됐으니 불리언을 남기고 `firstArchivedMonth` 만 추가하자"* 는 안이 한때 확정 직전까지
갔다. 근거는 *"안 읽는 필드의 비용은 0"* 이었는데 **그게 틀렸다. 비용이 네 종류다** (pm-lead 정리):
① 계약 표면에 남아 문서가 설명해야 한다 ② 같은 사실의 두 표현이라 **어긋남 고정 테스트**가 필요해진다
③ 앱이 *"왜 이 필드를 버리는지"* 를 문서로 남겨야 한다 ④ 🔴 **다음 사람이 되살릴 유혹을 받는다.**

🔴 **이 논거가 "두 소비자가 반대했다"보다 오래 버틴다** — 합의는 사람이 바뀌면 약해지지만
비용은 남는다. 계약 §1 에도 같은 절을 뒀다.

✅ **design 도 자기 근거 하나를 정정했다** — 초판의 *"불리언은 빈 달 2종을 구분 못 한다"* 는
과장이었고(`histories=[] && !hasPrevious && !hasNext` 로 구분은 된다), backend 지적으로 §2.1.2 에
정정 주석을 달았다. **형태 판정은 연타 논거만으로 선다.**

### 모바일에 걸리는 지점

- 🔴 **1차에 없던 표면 하나**: `<`/`>` 연타로 **요청이 여러 개 나가고 응답 순서가 보장되지
  않는다.** 늦게 온 옛 응답이 현재 월 표시 아래 다른 달 카드를 그릴 수 있다 —
  `data.month` 에코가 그 폐기 판정의 근거다(앱은 `flatMapLatest` + 에코 대조).
- 조회 실패 시 재시도 대상이 **"지금 보고 있던 월"** 이고, 실패 응답에는 `month` 가 없다
  (`BaseResponse` 3필드뿐) — 앱이 마지막 성공 응답의 에코를 들고 있어야 한다.
- ⚠️ **`month` 는 zero-padding 필수** — `2026-8` 은 code 700 이다 (실측).
- 🔴 **`firstArchivedMonth` 는 null 이어도 키가 실린다** — 이 레포 Jackson 에
  `@JsonInclude(NON_NULL)` 이 없다(실측). 앱이 키 존재를 전제해도 되고, 그 전제를
  `WireShapeContractTest` 가 원문으로 고정한다.
- 부분 매핑 실패 스낵바(design §2.5.4.2)는 유지되지만 **"일부"의 모수가 전체가 아니라 한 달치**다.

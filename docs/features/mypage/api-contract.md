|---|---|---|---|---|---|

🔴 **§1 은 `confirmed` 계약의 개정이다.** 사용자 확정 사항(월 1칸 이동 · 빈 달 통과 · 첫 진입
이번 달 · 미래 달 금지)은 협상 대상이 아니었고, 그 위의 형태는 3자 협의로 정해졌다:

**절대값 `firstArchivedMonth: String?`** 으로 수렴. 양쪽이 요구한 shape 이 필드명까지 동일했고
그대로 구현·검증했다 ([backend-report.md](./backend-report.md)).

프로필 카드는 기존 `GET /record` + `GET /users/me` 재사용 — **계약 변경 0.**

([ADR-0010](../../decisions/0010-datetime-model-localdatetime.md)). `T`·`Z`·offset·밀리초 없음.

## 1. 보관함 — `GET /api/v1/challenges/history` 🔴 **2026-08-28 월 단위 개정 (v2)**

> 🔴 **1차 확정(`전체 최신순 반환 + 클라 월 그룹핑`)을 폐기하고 월 단위 조회로 바꾼다.**
> 사용자 확정(2026-08-28, spec §후속 개정): **월 1칸씩 순차 이동, 빈 달도 건너뛰지 않는다,
> 첫 진입은 항상 이번 달, 미래 달로 가지 않는다.** 협상 대상이 아니다.
> 이력은 [change-log.md](./change-log.md) 참조.

### 요청

```
GET /api/v1/challenges/history?month=2026-08
Authorization: Bearer {accessToken}
```

| 이름 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| `month` | string `yyyy-MM` | ✗ | **서버 KST 이번 달** | 조회할 월. zero-padding 필수(`2026-8` 은 거부) |

🔴 **생략 가능한 것이 설계다 — 앱의 첫 진입은 파라미터 없이 부른다.** *"첫 진입은 항상 이번 달"*이
**기기 시계 계산 없이** 성립한다. 앱이 이번 달을 직접 만들어 보내면 상한(이번 달)과 하한이
**서로 다른 시계**에서 나오게 된다. 이 프로젝트는 이미 `DeadlineType`(챌린지 생성)에서
*"기기 시계 조작·타임존 불일치를 차단하고 마감 기준을 서버로 일원화"* 를 규약으로 정했고
(`KstDeadlineCalculator` KDoc), 같은 판단이 여기 걸린다.

`?month=` (빈 문자열)도 미지정과 같이 다룬다.

### 응답 — 성공

```json
{
  "error": false, "code": 200, "message": "",
  "data": {
    "month": "2026-08",
    "firstArchivedMonth": "2026-08",
    "histories": [
      {
        "challengeId": 42,
        "challengeDate": "2026-08-14",
        "opponentNickname": "준혁",
        "myMission": "헬스장 가기",
        "opponentMission": "금주",
        "bet": "치킨 한 마리",
        "myResult": "WIN"
      }
    ]
  }
}
```

| 필드 | 타입 | null | 설명 |
|---|---|---|---|
| `month` | string `yyyy-MM` | non-null | 실제로 조회한 월. 요청 값의 **에코** |
| `firstArchivedMonth` | string `yyyy-MM` | 🔴 **nullable** | 가장 오래된 `COMPLETED` 기록의 월. **기록 0건이면 `null`**. 🔴 **경계가 아니라 빈 상태 2종 판별 + 빈 달 고지 기준** |
| `histories` | array | non-null (**빌 수 있다**) | 그 달의 카드 |

⚠️ **`firstArchivedMonth` 가 `null` 이어도 키는 항상 실린다** — 이 프로젝트 Jackson 에
`@JsonInclude(NON_NULL)` 설정이 없다(실측, `WireShapeContractTest` KDoc). 원문 확인:
`{"data":{"month":"2026-08","firstArchivedMonth":null,"histories":[]},...}`.
`WireShapeContractTest` 가 이 원문을 고정한다 — 나중에 누가 전역 `NON_NULL` 을 켜면 키가 조용히
사라지고 **앱이 "기록 전무" 를 판정할 신호를 잃는데, 목록은 멀쩡히 `[]` 라 다른 단언은 못 잡는다.**

⚠️ SpringDoc 은 OpenAPI **3.1** 로 낸다 — nullable 은 `required` 배열에서 빠지는 것으로 표현된다
(실측: `required: ["histories", "month"]` — `firstArchivedMonth` 만 빠진다).

### 🔴 앱이 쓰는 두 경계 — **둘 다 서버 값이다. 앱은 기기 시계를 읽지 않는다**

| | 어디서 오나 | 앱의 계산 |
|---|---|---|
| **상한** (= 이번 달) | 🔴 **파라미터 없이 부른 첫 응답의 `month` 에코** | `canNext = 선택월 < 이번달` |
| **하한** | 🔴 **없다** | `canPrev` 는 **항상 true** — `<` 가 비활성되지 않는다 |

**왜 앱이 이번 달을 직접 계산하면 안 되나**: 기기 타임존이 KST 가 아니면 서버와 한 달 어긋나고,
하필 어긋나는 순간이 월말·월초 자정 근처다. 증상은 **`>` 가 잠긴 채 이번 달 기록이 안 보이는**
형태다. ADR-0010 이 프로젝트 전체를 KST 로 고정했지만 **사용자 기기 시계는 그 규약 밖**이다.
`DeadlineType` 이 *"기기 시계 조작·타임존 불일치를 차단하고 마감 기준을 서버로 일원화"* 한 것과
같은 판단이며, `month` 를 optional 로 둔 것이 그 실행 수단이다.

**`month` 에코의 두 번째 일 — 응답 경합 방어**: 빈 달을 건너뛰지 않는 확정 때문에 **화살표
연타가 정상 사용**이고 따라서 요청 겹침도 정상이다. 늦게 도착한 옛 응답이 현재 월 표시 아래
다른 달 카드를 그리는 것을 앱이 이 값으로 막는다(`flatMapLatest` + 에코 대조). 1차(1회 조회)에는
없던 표면이다.

### 🔴 하한이 **절대값**인 것이 결정이다 — `hasPrevious`/`hasNext` 불리언은 기각됐다

> 🔴 **[폐기 2026-08-28(2차) — 이 절의 "하한 = 최초 기록월"을 따르지 마라. 🔴 하한 자체가 없다.]**
> 아래 **불리언 기각 논거는 그대로 유효**하다(절대값이어야 한다는 것 — 그리고 `firstArchivedMonth`
> 가 살아남은 이유이기도 하다). 무효가 된 것은 *`<` 를 막는다*는 것뿐이다 — 살아남은 것과 죽은
> 것이 한 절에 섞여 있으므로 둘 다 표시한다.

~~**하한 자체는 "최초 `COMPLETED` 기록의 월"** 이다~~ (후보 ① 무한 ② 가입월 ③ 최초 기록월 중 ③):

- ~~하한의 목적은 *"확정적으로 빈 달의 사막으로 걸어 들어가지 않게 한다"* 이다. ③ 아래의 모든
  달은 **0건인 것이 보장**된다. ②(가입월)는 가입~첫 기록 사이의 빈 달을 열어 두는데 그것도
  보장된 사막이라 목적을 절반만 이룬다.~~
- ~~①(무한)은 화살표가 영원히 살아 있어 사용자가 *"더 뒤에 있나"* 를 확인할 방법이 없다.
  🔴 **보관함은 *"이게 네 기록 전부다"* 라고 주장하는 화면**인데(design §2.5.4.2), 하한이 없으면
  **화면이 그 주장을 할 수 없다.**~~
  → 🔴 **이 논거가 2차 개정의 직접 대상이다.** 사용자가 그 주장보다 **"화면이 반응한다"** 를
  우선했다 — 실기에서 기록이 전부 이번 달이라 **하한 = 상한 = 이번 달**이 되어 양쪽 화살표가
  동시에 죽었고, 카드는 보이는데 아무것도 안 움직여 **"고장"으로 읽혔다.** 설계도 계약도 정확히
  동작했지만 **그 정확함이 신규 사용자에게 고장으로 보였다.**
- ✅ **살아남음**: `challengeDate` 가 소급 생성되지 않아 **값이 과거로 밀리지 않는다**는 성질은
  그대로다. 이제 경계가 아니라 **빈 달 고지 기준**의 안정성을 보장한다 — 고지 문구가 세션 중에
  흔들리면 안 된다.
- ✅ **살아남음(용도만 이동)**: `firstArchivedMonth` 가 **`COMPLETED` 만** 세고 남의 챌린지를
  세지 않는다는 규칙은 그대로다 — 이제 하한이 아니라 **빈 상태 2종 판별**에 쓰인다.

### 🔴 과거 하한 **폐기** — `<` 는 항상 활성 (2026-08-28 2차 확정)

```
canPrev = 항상 true      // 어느 과거 달이든 열린다
canNext = 선택월 < 이번달  // 상한만 남는다
```

🔴 **서버 코드 변경이 0이다.** 이 엔드포인트는 **애초에 하한을 강제한 적이 없다** — 거부하는
것은 **미래 달 하나뿐**이고 과거는 어느 달이든 빈 목록으로 정상 응답해 왔다(v3 계약 문면:
*"하한보다 이전 달은 에러가 아니다"*). 하한은 처음부터 **앱이 `firstArchivedMonth` 로 스스로
걸던 규칙**이라, 그 규칙을 앱에서 걷어내는 것으로 개정이 끝난다.

**`가입월` 안은 검토 후 폐기됐다** (pm-lead 초기 선호 → 철회). 논리는 참이었다 — 챌린지 생성엔
인증이 필요하고 `challengeDate` ∈ {오늘, 내일}이라 `challengeDate >= created_at` 이 구조적으로
성립하므로, 가입월은 상한과 **같은 구조의 데이터 사실**이다. 🔴 **그런데 이번 사고를 못 고친다:**

| 계정 (실기 DB 실측) | 가입월 | 기록 | 가입월 안 | 무제한 안 |
|---|---|---|---|---|
| 이우건 | 2026-05 | 2026-08 전부 | ✅ | ✅ |
| 테스터1·2·3 | **2026-08** | 2026-08 전부 | 🔴 **양쪽 비활성 유지** | ✅ |

가입 첫 달 사용자는 정의상 `가입월 = 이번 달` 이라 **하한 = 상한**이 되어 신고된 증상이 그대로
재현된다. **가입월 안은 계정이 오래됐을수록 잘 듣고 신규일수록 안 듣는데**, spec 이 이 문제를
*"신규 서비스에서 가장 흔한 초기 상태"* 로 규정했다 — **문제가 가장 자주 나는 집합에서 해법이
가장 약하다.** backend·mobile·design 이 독립적으로 같은 실측에 도달했다.

🔴 **여기서 배운 것**: *"대칭성은 **이 경계가 참인가**를 증명하지 **경계를 두는 것이 바람직한가**를
증명하지 않는다."* 가입월이 유효한 경계라는 것과 그 경계가 쓸모 있다는 것은 다른 명제다.

⚠️ **감수하는 것**: 이론상 끝없이 과거로 갈 수 있다. 실사용 유인이 없고 각 화면이 빈 달로
일관되므로 수용한다(spec 명시).

🔴 **형태를 정한 것은 연타다.** v2 초안은 `hasPrevious`/`hasNext` 불리언 2개였고,
archive-month-design(§2.1.2)·archive-month-mobile 이 **같은 반례**로 기각했다. 확정 사항 둘이
맞물려 상대 불리언을 구현 불가능하게 만든다 — 사용자 확정 *"빈 달도 건너뛰지 않는다"* 때문에
**연타가 정상 사용**이고, design §2.5.4.3-① 때문에 **월 전환 중에도 화살표는 계속 눌려야 한다**
(응답을 기다리며 입력을 잠그면 *"하나씩 지나간다"* 가 매 칸 네트워크 왕복만큼 느려져 사실상
불가능해진다). 불리언은 **그 달의 응답이 와야** 그 달의 경계를 안다:

```
하한 5월, 사용자는 6월
  탭 ①  →  5월 요청 (in flight). 5월이 하한인지 아직 모른다
  탭 ②  →  🔴 4월. 존재할 수 없는 달에 사용자가 서 있다
  (4월 응답) →  hasPrevious=false 로 그제서야 "여기가 끝"
```

**경계를 넘은 뒤에 경계를 통보받는다** — 하한을 만든 목적 자체를 한 탭 늦게 이행한다.
대칭으로 `>` 연타는 **미래 달 요청 → code 700** 을 만들어 **정상 조작이 오류 화면**이 된다.
절대값이면 `canPrev` 가 **왕복 없이 아무 달에서나** 계산돼 그 탭이 애초에 거부된다.

⚠️ **초안이 이걸 놓친 이유를 기록해 둔다** — backend 는 *"불리언이 신호가 하나라 더 적다"* 고
봤는데, `result`+`myResult` 처럼 **두 표현이 경쟁하는** 경우와 혼동한 것이다. 여기서 불리언은
절대값의 **손실 있는 투영**이지 더 적은 신호가 아니다. 절대값 하나만 주므로 경쟁하는 신호도
없다. (design 은 `earliestMonth` 를 **별도 필드로 추가하지 말라**고 명시했다 —
`firstArchivedMonth` 가 곧 그 값이다.)

#### 🔴 불리언을 **남겨 두는** 안(병존)도 검토했고 기각됐다 — 되살리려는 사람이 먼저 읽을 것

한때 *"이미 검증됐으니 불리언을 남기고 `firstArchivedMonth` 만 추가하자"* 는 안이 있었다.
근거는 *"안 읽는 필드의 비용은 0"* 이었는데 **그게 틀렸다. 비용이 네 종류다** (pm-lead 정리):

1. **계약 표면에 남는다** — 이 문서가 설명해야 할 필드가 는다.
2. **어긋남 고정 테스트가 필요해진다** — 같은 사실의 두 표현이라 기록 0건·하한 월 자신·경계 월에서
   갈리지 않는지 서버가 증명해야 한다.
3. **앱이 *"왜 이 필드를 버리는지"* 를 문서로 남겨야 한다** — 안 읽는 필드는 그 자체로 설명 부채다.
4. 🔴 **다음 사람이 되살릴 유혹을 받는다** — *"안 쓰는 필드가 있네"* 로 시작해서 위 연타 반례를
   다시 밟는다.

🔴 **이 논거는 합의와 무관하게 선다.** *"design·mobile 이 둘 다 반대했다"* 는 사실도 맞지만,
그건 사람이 바뀌면 약해진다. **안 읽는 필드에 네 종류의 비용이 있다**는 것이 더 오래 버티는 근거다.
그래서 이 절을 지우지 말고, `hasPrevious` 를 다시 넣고 싶어진 사람이 여기부터 읽게 하라.

🔴 **상한이 이번 달인 것은 UI 규칙이 아니라 데이터 사실이다.** `challengeDate` 는 생성 시점의
오늘 또는 내일이고(`DeadlineType`), `deadline` 은 그 날의 끝이며, `COMPLETED` 는 마감이 지나야
되는 상태다 — 따라서 **`COMPLETED` 인 챌린지의 `challengeDate` 는 항상 오늘 이하**이고 미래
달에는 카드가 **존재할 수 없다.**

### 빈 달 — `histories: []` 로 정상 응답

별도 표현(null · 전용 플래그)을 만들지 않는다. 이 feature 는 *"한 신호가 두 사건을 나른다"*
는 사고를 이미 세 번 겪었고(design §2.5.4.2 표), 새로 하나 만들 이유가 없다.

🔴 **다만 빈 배열 하나로는 두 사실이 구분되지 않는다 — `firstArchivedMonth` 가 그 구분자다:**

| 응답 | 뜻 | 화면 |
|---|---|---|
| `histories=[]` + `firstArchivedMonth == null` | **기록이 하나도 없다** | 기록 전무 (design §2.5.1) — *"챌린지 만들기"* CTA **있음** |
| `histories=[]` + `firstArchivedMonth != null` | **이 달만 비었다** | 빈 달 (design §2.5.1a) — CTA **없음** |

🔴 **이 판정이 `firstArchivedMonth` 의 유일한 용도다** — 경계로 쓰지 않는다(§하한 폐기 참조).

🔴 **후자에 CTA 를 띄우면 안 된다** — 기록을 찾는 중인 사용자를 **보관함 밖으로 내보낸다.**

### 실패 응답

| code | HTTP | 언제 | message |
|---|---|---|---|
| 700 | **200** | 미래 달 요청 (`?month=2026-09`, 오늘이 8월) | `"아직 오지 않은 달이에요"` |
| 700 | **200** | 형식 오류 (`2026-8` · `2026-08-24` · 임의 문자열) | `"조회할 월 형식이 올바르지 않아요"` |
| 401 | 401 | 토큰 없음/만료 | 기존 흐름 그대로 |

- **미래 달은 정상 경로에서 발생하지 않는다** — 앱은 첫 응답의 `month` 에코를 상한으로 삼아
  `>` 를 비활성화한다. 계약 위반에 대한 **안전망**이다. (v2 초안의 `hasNext` 였다면 연타 중에
  실제로 발생해 *"정상 조작이 오류 화면"* 이 됐다 — 절대값 채택 사유 중 하나다.)
- 🔴 **조용히 이번 달로 clamp 하지 않는다.** clamp 하면 응답의 `month` 에코가 요청과 달라져
  **앱 화면의 월 표시와 카드 내용이 어긋난다.**
- 🔴 **어느 과거 달도 에러가 아니다** — `histories: []` 로 정상 응답하고 `firstArchivedMonth` 는
  평소와 같은 값이 실린다(사용자 전역 값이라 요청 월과 무관하다). 하한이 폐기되면서 이건
  **예외 경로가 아니라 정상 경로의 주력 동작**이 됐다 — 앱이 계속 뒤로 가면 서버는 매번 이 응답을 낸다.
  미래와 비대칭인 이유: **미래는 데이터가 존재할 수 없는 구간(좌표계 밖)** 이고,
  **과거는 존재할 수 있었지만 없는 구간(정상적인 빈 달)** 이다. 앱은 절대값 덕에 애초에
  여기까지 오지 않지만 안전망으로 유지한다.
- ⚠️ **형식 오류가 HTTP 500 이 아닌 것이 의도된 구현이다.** `@RequestParam month: YearMonth?` 로
  선언하면 Spring 이 `MethodArgumentTypeMismatchException` 을 던지는데
  `GlobalExceptionHandler` 에 그 핸들러가 **없어서** `handleUncaught` → **HTTP 500** 이 나간다.
  클라이언트가 잘못 보낸 쿼리 파라미터 하나가 서버 장애로 보고되는 것을 막으려고 문자열로
  받아 컨트롤러에서 파싱한다 (ADR-0002: 5xx 는 인프라 장애 전용). 전역 핸들러를 추가하면
  **다른 모든 엔드포인트의 타입 불일치 응답까지 바뀌므로** 이 개정이 열 범위가 아니다.

### 카드 7필드 — **1차에서 하나도 바뀌지 않았다**

🔴 필드 7개가 전부이고 전부 non-null 이다 (design §7-④). 넣지 않은 것 둘:

- **역할 기준 `result` 원본을 넣지 않는다.** `/challenges/active` 는 `result` + `myResult` 를
  둘 다 주지만 여기는 `myResult` 뿐이다. 카드는 *"내가 이겼나"* 만 그리는데 **둘 다 내려가면
  앱이 어느 쪽을 믿을지 고르게 되고, 그 선택이 화면마다 갈린다.** `Outcome` 에 `BOTH_LOSE` 가
  이미 있어 "양쪽 다 졌다" 도 `myResult` 만으로 표현된다.
- **인증 상태 2필드를 넣지 않는다.** 판정 규칙상 4개 결과가 양측 인증 상태를 **유일하게
  결정**한다(승=나만 인증 / 패=상대만 / 무=양쪽 / 양패=양쪽 미인증). 즉 결과 하나가 인증
  상태 두 개의 정보를 전부 담고 있어 **정보량이 0**이다.
- **탈퇴 여부 플래그(`isWithdrawn`)도 없다** — design 이 명시적으로 거부했다(증거 보존 화면에서
  *"이 기록은 무효"* 로 읽힌다). 탈퇴자는 `opponentNickname = "탈퇴한 사용자"` 로 non-null 이다.

그 외 유지되는 것:

- **월 경계·정렬 키는 `challengeDate`** — `completed_at` 이 아니다. 판정이 **자정 직후 배치**라
  7월 31일 챌린지의 `completed_at` 은 8월 1일 00:05 다. `completed_at` 으로 자르면 **7월 마지막
  날 챌린지가 8월 응답에 들어가서**, 카드에 적힌 날짜(7/31)와 화면 상단의 월 표시(8월)가
  한 화면에서 서로 다른 말을 한다. 홈 피드가 `completed_at DESC` 인 건 *"판정이 방금 났다"* 를
  보여주는 다른 목적이다.
- **2차 정렬 키 `id DESC`** — 같은 날 여러 건이 가능하고, 동률 순서가 흔들리면 같은 목록을 두 번
  불러올 때 카드 순서가 바뀐다.
- **대상 상태는 `COMPLETED` 만. `EXPIRED` 제외** (design §2.5.3). `EXPIRED` 는 *"성립조차 못 한
  신청"* 이라 계약서·서명·사진·결과가 **전부 없다** — 증거가 0인 카드다.
- **`myResult` 는 서버가 뒤집어 준다** (`ChallengeVerdict.outcomeFor`). 앱은 *"내가 challenger
  인가"* 를 알 필요가 없다. `BOTH_LOSE` 는 `LOSE` 로 접지 않고 그대로 내려간다.
- **월 범위는 반개구간** `[해당 월 1일, 다음 달 1일)`. 말일 계산이 없어 2월·윤년 분기가 생길
  자리가 아예 없다.
- 카드 탭 → 기존 `GET /challenges/{id}` 로 상세 진입. 기한 없이 열린다 — **신규 API 불필요.**

### 🔴 폐기 — 페이지네이션 논거 전체

1차는 *"보관함이 프로젝트 최초의 무한히 자라는 목록"* 이라 페이지네이션 도입 1순위로 백로그에
올렸다. **월 단위가 되면서 그 전제가 사라졌다** — 한 응답의 상한이 한 달치로 고정된다(같은
상대와는 하루 한 판이 상한이고, 한 달에 담기는 카드 수는 사실상 유계다).

다른 엔드포인트의 페이지네이션 통일 논의는 그대로 남지만 **보관함은 그 목록에서 빠진다.**
→ §5 백로그 항목 정정 대상.

### 🔴 함께 폐기되는 1차 근거 2개 (기록용)

1. *"월 이동 UI 는 빈 월을 계속 만나게 하는 UI다"* → **사용자가 그 동작을 선택했다.** 대신
   빈 달 화면이 자주 보이므로 **빈 달 표시의 완성도가 중요해진다**(design 소관).
2. *"최신순 전체 목록은 첫 화면 최상단이 가장 최근 종료 건이라 spec 수용 기준이 아무 조작 없이
   충족된다"* → **이번 달에 기록이 없으면 깨진다.** pm-lead 판정: 도달 경로가 존재하고 조작이
   1~2회면 충족으로 본다(spec §후속 개정).

## 2. 회원탈퇴 — `DELETE /api/v1/users/me` ✅ 확정

### 요청

```
DELETE /api/v1/users/me
Authorization: Bearer {accessToken}
```
body 없음.

### 응답 — 성공

```json
{ "error": false, "code": 200, "message": "" }
```

🔴 **`data` 키가 없다.** `DELETE /auth/logout`·`PUT /users/me/fcm-token` 과 같은 shape 이며
`WireShapeContractTest` 가 고정한다. non-nullable 로 선언하면 `MissingFieldException`.

### 응답 — 실패

| code | HTTP | 언제 | 앱 처리 |
|---|---|---|---|
| 701 | 200 | 카카오 연결 해제(unlink) 실패 | 다이얼로그. *"일시적인 문제로 탈퇴하지 못했어요. 잠시 후 다시 시도해주세요"* — **재시도 가능** |
| 401 | 401 | 토큰 없음/만료 | 기존 흐름 그대로 |

🔴 **탈퇴는 로그아웃과 달리 "언제나 성공" 이 아니다.** 로그아웃은 실패해도 클라이언트를
로그인 상태에 가두면 안 되므로 멱등 성공이지만, 탈퇴는 **카카오 연결 해제가 이행되지
않았는데 성공이라고 답하면 안 된다.**

### 멱등성

이미 탈퇴한 계정으로 다시 호출하면 **아무 것도 하지 않고 200**. (아래 토큰 항목 때문에
실제로 발생 가능한 경로다.)

### 서버가 하는 일 — 실행 순서

```
1. 카카오 unlink            ← 🔴 DB 보다 먼저
2. [한 트랜잭션] 사진 key 수집 → verifications.photo_url NULL
                            → friendships 물리 삭제 → users 익명화
3. [커밋 후] 인증 사진 파일 삭제
```

**왜 unlink 가 먼저인가**: DB 를 먼저 하고 unlink 가 실패하면 계정은 이미 되돌릴 수 없게
익명화됐는데 카카오 연결은 살아 있고, `kakao_id` 를 지워서 **재시도할 대상조차 잃는다**.
반대 순서면 카카오 연결만 끊기고 row 는 ACTIVE 로 남아, 재로그인 시 같은 row 로 돌아와
**다시 탈퇴를 누르면 된다.** 복구 가능한 쪽을 택했다.

### 익명화 범위 (spec 정책표 이행)

| 컬럼 | 값 |
|---|---|
| `kakao_id` | NULL |
| `nickname` | **"탈퇴한 사용자"** |
| `profile_image_url` / `phone_number` / `fcm_token` / `refresh_token_hash` | NULL |
| `phone_verified` | false |
| `status` | `DELETED` |

보존: `challenges`(`PENDING` 제외 — 아래), `contracts`, `verifications` **row**, `user_stats`,
`friend_records`, `taunt_messages`.
삭제: `friendships` 전부 · **`notifications`(수신함) 전부** · 탈퇴자가 **보낸 `PENDING` 챌린지** ·
인증 사진 **파일** + `verifications.photo_url`(=key).

### 🔴 탈퇴자가 상대 화면에 어떻게 보이는가 — 타 응답 계약 변경 **0**

`nickname` 이 **non-null 을 유지**하므로 기존 응답이 하나도 깨지지 않는다. 실측 확인:

| 응답 | 탈퇴자 표현 | 계약 변경 |
|---|---|---|
| `GET /challenges/active` | `opponentNickname = "탈퇴한 사용자"` | 없음 |
| `GET /challenges/{id}` | `challenger/opponent.nickname = "탈퇴한 사용자"` | 없음 |
| `GET /challenges/history` | `opponentNickname = "탈퇴한 사용자"` | 없음 |
| `GET /rankings/losers` | **목록에서 사라짐** — 랭킹은 `friendships` JOIN 이고 그게 삭제된다 | 없음 |
| `GET /friends` | **목록에서 사라짐** — 같은 이유 | 없음 |

### 🔴 신규 계약 사실 — `GET /challenges/{id}/verifications` 에 필드 1개 추가

탈퇴자 쪽은 **`status = "VERIFIED"` 인데 `photoUrl = null`** 인 조합이 나온다.
row 는 보존하되(그 사람이 그날 인증했다는 사실은 상대의 기록이다) 사진 파일과 key 만 지우기
때문이다. 지금까지 서버가 만들지 않던 조합이다.

**`photoUrl == null` 만으로는 부족하다** — 그 자리는 앱에서 이미 *"인증은 됐는데 URL 이 없는
비정상"* 이라는 **다른 뜻**으로 쓰이고 있다(`VerificationPhoto.kt` 실측:
`photoUrl == null -> PhotoMessage(LOAD_FAILED_TEXT)`). 삭제된 사진이 그 문구를 빌려 쓰면
(1) 영구 상태를 *"불러오지 못했어요"* 라는 일시적 실패의 어휘로 말하고,
(2) 🔴 **진짜 데이터 이상이 탈퇴자 뒤에 숨는다.**

→ **`photoDeleted: Boolean` 을 party 객체에 추가한다** (additive, non-null, 기본 false).
design §7-⑤ 요구이며 backend 가 실측 정정 후 채택했다.

```json
"challenger": {
  "userId": 7, "status": "VERIFIED", "photoUrl": null,
  "photoDeleted": true,
  "verifiedAt": "2026-08-12 21:30:00"
}
```

서버 판정: `status == VERIFIED && photoUrl == null && 그 사람이 탈퇴 상태`.

| status | photoUrl | photoDeleted | 앱 표시 |
|---|---|---|---|
| VERIFIED | non-null | false | 사진 |
| VERIFIED | null | **true** | **"탈퇴한 사용자의 사진은 삭제됐어요"** — 재시도 버튼 없음 |
| VERIFIED | null | false | 기존 그대로 (진짜 데이터 이상) |
| PENDING / FAILED | null | false | 기존 그대로 |

🔴 **`isWithdrawn` 이 아니라 `photoDeleted` 인 것이 의도다.** 앱이 *"왜"* 가 아니라
*"뭘 그릴지"* 만 받게 한다 — design 이 보관함 카드에서 `isWithdrawn` 을 **명시적으로 거부**한
이유(받으면 특별 표시를 넣게 되고, 증거 보존 화면에서 그건 *"이 기록은 무효"* 로 읽힌다)가
여기도 그대로 걸린다. `photoDeleted` 는 사진 자리 하나만 바꾸고 다른 데 쓸 수 없다.

⚠️ **challenge-verification 의 confirmed 계약 변경(additive)** — 그쪽 `change-log.md` 등재 대상.

사진 직접 요청 `GET /challenges/{id}/photos/{party}` 는 **HTTP 404** 다.
기존 404(아직 인증 안 함 / 챌린지 없음)와 **구분되지 않는다** — 구분할 필요가 없다는 것이
결정이다. 앱은 위 `photoDeleted` 로 이미 알 수 있으므로 사진 요청 자체를 하지 않는 것이
정상 경로이고, 404 는 그 뒤의 안전망이다.

### 🔴 `GET /users/me` — shape 은 그대로, **동작이 바뀐다**

**탈퇴한 계정이 부르면 401 이다.**

탈퇴 시 `kakao_id` 를 NULL 로 만드는데 `UserInfoData.kakaoId` 는 non-null 계약이다.
nullable 로 바꾸면 모바일 wire 계약이 깨지고(kotlinx.serialization 이 터진다), `0L` 로 채우면
거짓말이므로 **탈퇴자를 401 로 답한다.**

이건 새 규칙이 아니라 **원래 문서화돼 있던 동작의 유지**다 — `UserService.getMe` 의 KDoc 이
원래 *"토큰의 userId 가 DB 에 없으면(회원탈퇴/삭제) 401"* 이었다. **탈퇴가 row 를 지운다는
전제**였고 이번에 그 전제가 바뀌었으므로(row 를 남긴다) status 검사를 더해야 같은 답이 나온다.

부수 효과로 아래 "access token 1시간 잔존" 구멍이 **이 엔드포인트 하나에서는 닫힌다.**

### 토큰 처리 — ⚠️ 정직하게 적는다

- **`refresh_token_hash` 는 즉시 NULL** → 재발급 불가. `POST /auth/refresh` 는 401.
- ⚠️ **access token 은 남은 유효기간(최대 1시간, `jwt.access-token-expiration-ms=3600000`)
  동안 형식상 유효하다.** `JwtAuthenticationFilter` 가 요청마다 계정 상태를 다시 조회하지
  않기 때문이다 (그렇게 하려면 **모든 인증 요청에 DB 조회가 1회씩 붙는다** — 전역 성능·회귀
  비용이 커서 이번 범위에 넣지 않았다).
  - 예외: **`GET /users/me` 는 401 이다** (위 항목). `DELETE /users/me`(탈퇴 재호출)는
    멱등 200 이다. 그 외 엔드포인트는 열려 있다.
- 따라서 **앱은 탈퇴 성공 즉시 로컬 토큰·캐시를 삭제하고 로그인 화면으로 보낸다.**
  실사용 경로에서 그 1시간이 노출되지 않는 것은 **앱의 이 동작이 보장**한다.
- 백로그 등재 대상 (§5 참조).

### 진행 중 챌린지 — **막지 않는다. 자연 판정.** ✅ 확정

탈퇴자는 로그인이 불가능하므로 인증을 올릴 수 없고, 자정 배치가 **기존 판정 규칙 그대로**
처리한다(상대만 인증 → 상대 승 / 양쪽 미인증 → 양패). 탈퇴 시점에 즉시 포기 처리하면
**판정 규칙의 사본이 하나 더 생긴다** — 그게 나중에 본 규칙과 갈린다.

### ✅ `PENDING` 챌린지 — **보낸 것은 삭제, 받은 것은 방치** (pm-lead 확정)

탈퇴자가 **보낸 채 아직 수락되지 않은** 도전장이 남으면, 상대가 그걸 수락해 **탈퇴자와의
챌린지를 새로 시작**할 수 있다. 시작하자마자 탈퇴자는 인증 불가라 **결과가 이미 정해진**
챌린지다.

- 탈퇴자가 **challenger** 인 `PENDING` → **물리 삭제.** `PENDING` 에는 계약서·서명·사진·결과가
  하나도 없어 **보존할 증거가 0** 이고, 처리가 **챌린저가 직접 취소한 것과 정확히 같다**
  (`ChallengeRepository.deleteById` 가 이미 그 용도다).
- 탈퇴자가 **opponent** 인 `PENDING` → **그대로 둔다.** 수락될 수 없으므로 자연 만료된다.

🔴 **`IN_PROGRESS` / `COMPLETED` 는 삭제 대상이 아니다.** 그건 증거가 있는 챌린지이고
"자연 판정" 정책이 적용된다.

⚠️ **모바일에 걸리는 지점**: 상대에게 이미 발송된 `CHALLENGE_REQUEST` 알림 row 는 **상대
것이라 보존**되는데 그 챌린지는 사라진다. 즉 **상대가 그 알림을 탭하면 없는 챌린지로
딥링크한다.** 서버는 `GET /challenges/{id}` 에 **code=705 `"챌린지를 찾을 수 없어요"`** 로
답한다 — 이미 설계된 정상 경로라 서버가 새로 할 일은 없다. push-deeplink 쪽에서 그 코드를
무난히 그리는지만 확인 대상.

### ✅ `notifications` — **삭제** (pm-lead 확정)

수신함은 **본인 전용 개인 데이터**라 *"양자 기록 보존"* 원칙의 대상이 아니고 **개인정보 삭제
축**에 속한다. 아무도 읽을 수 없는 채로 *"누가 나에게 무엇을 했는지"* 를 담은 row 를 남길
이유가 없다.

(backend 는 *"남기는 쪽이 되돌릴 수 있다"* 를 근거로 보류를 제안했으나, pm-lead 판정은
**가역성 문제가 아니라 분류 문제**라는 것이었고 그쪽이 맞다.)

🔴 **상대의 `notifications` 는 건드리지 않는다** — 탈퇴자가 보낸 알림이라도 그건 **받은
사람의 데이터**다.

### ⚠️ 운영 전제 — `KAKAO_ADMIN_KEY`

카카오 unlink 는 **서비스 앱 어드민 키** 방식이다
(`POST https://kapi.kakao.com/v1/user/unlink`, `Authorization: KakaoAK {키}`,
body `target_id_type=user_id&target_id={kakaoId}` — 공식 문서 확인 완료).

사용자 access token 방식을 쓰지 않은 이유: **서버는 카카오 access token 을 저장하지 않는다**
(로그인 때 `/v2/user/me` 한 번 쓰고 버린다). 토큰 방식이면 앱이 탈퇴 시점에 카카오 토큰을
새로 받아 보내야 하고, 기기의 카카오 세션이 만료돼 있으면 **탈퇴 자체가 불가능**해진다.
admin key 는 `users.kakao_id` 만으로 동작한다.

🔴 **`KAKAO_ADMIN_KEY` 가 미설정이면 unlink 를 건너뛰고 DB 익명화만 수행한다**(WARN 로그
2회 — 기동 시 + 호출 시). 로컬 개발에서 탈퇴 플로우를 테스트할 수 있게 하기 위한 것이며
(`NotificationSenderConfig` 의 FCM 키 선례와 같은 판단), **운영 배포 전 필수 설정 항목이다.**
사용자가 카카오 콘솔에서 발급해야 한다 — 서버가 만들 수 없는 값이다.

## 3. 로그아웃 — `DELETE /api/v1/auth/logout` ✅ 확정 (기존)

서버 구현·검증 완료. 앱 연동만 남았다.

- **Bearer 필수.** `SecurityConfig` 의 `permitAll` 목록에 없고 `.anyRequest().authenticated()`
  에 걸린다. → `sendWithoutRequest` 술어를 줄일 때 **`/auth/kakao`·`/auth/refresh` 는 공개,
  `/auth/logout` 만 인증 필수**로 갈라야 한다.
- 응답: `BaseResponse` 3필드. **`data` 없음.**
- 서버 동작: `refresh_token_hash = NULL` + `fcm_token = NULL` 을 한 트랜잭션에.
  둘을 묶는 것이 설계 의도다 — 하나만 끊으면 *"로그아웃했는데 알림은 계속 온다"* 또는
  *"알림은 끊겼는데 세션은 살아 있다"* 가 남는다.
- **멱등.** 이미 로그아웃된 상태도, 해당 row 가 없어도 200. 재시도를 자유롭게 넣어도 된다.
- 호출 순서: `clearTokens` **앞**에 서버 호출.

### 🔴 `WWW-Authenticate` 실측 결과 (2026-08-26, 로컬 :8080) — **헤더 없음**

```
GET    /api/v1/challenges/active   -> HTTP 401 | WWW-Authenticate: (absent)
DELETE /api/v1/auth/logout         -> HTTP 401 | WWW-Authenticate: (absent)
GET    /api/v1/users/me            -> HTTP 401 | WWW-Authenticate: (absent)
```

토큰 미첨부와 쓰레기 토큰(`Bearer not.a.jwt`)의 응답이 **바이트 단위로 동일**하다.
401 body 는 `{"error":true,"code":401,"message":"토큰이 만료되었거나 유효하지 않습니다"}`.

코드 근거: `UnauthorizedEntryPoint` 가 status + JSON body 만 쓰고, `SecurityConfig` 가
`httpBasic` 을 disable 해서 Spring Security 쪽에도 그 헤더를 붙일 진입점이 없다.
**우연이 아니라 구조적으로 없다.**

#### ✅ 판정 — **헤더를 추가하지 않는다. 서버 변경 0건**

mobile 이 Ktor `MockEngine` 으로 프로덕션 인증 설정을 그대로 태운 특성화 테스트 9건
(Android/iOS 각각 9 tests / 0 failures)으로 답을 냈다. 결정적인 것:

> `401 에 WWW-Authenticate 헤더가 없어도 갱신이 시도된다` → **pass**

즉 지금 서버가 보내는 그 응답(헤더 없음)에도 `/auth/refresh` 가 나가고 토큰이 갱신된다.
코드 근거도 일치한다 — `ktor-client-auth 3.3.1` 의 `Auth.kt` `findProvider` 에
`authHeaders.isEmpty() && candidateProviders.size == 1 -> candidateProviders.first() to null`
분기가 있고, 이 앱은 프로바이더가 `bearer` **하나뿐**이라 이 분기를 탄다.

🔴 **다만 그 전제를 계약으로 기억해 둔다: 앱의 인증 프로바이더가 1개인 동안만 성립한다.**
프로바이더가 하나 더 붙으면 이 분기가 깨지고 그때는 서버가 헤더를 보내야 한다.
mobile 이 위 테스트 2건을 그 순간 빨갛게 터지도록 박제해 뒀다.

⚠️ RFC 9110 §15.5.2 는 401 에 `WWW-Authenticate` 를 MUST 로 요구하므로 **현재 서버는 규격
위반 상태로 남는다.** 지금 고치면 얻는 것 없이 모든 401 이 바뀌므로 백로그로 넘긴다.

#### ⚠️ 만료된 access token 으로 `/auth/logout` 을 부르면 — **401, 그리고 루프는 없다**

토큰 미첨부 · 쓰레기 토큰 · 만료 토큰의 응답이 **바이트 단위로 동일**하다(위 401 전문).
컨트롤러에 **도달조차 하지 않는다.**

루프가 안 생기는 이유: `/auth/refresh` 의 401 은 **결정적이고 영구적**이다 —
`refresh_token_hash` 가 NULL 이거나 불일치면 몇 번을 불러도 같은 401 이고, **서버가 나중에
성공시킬 여지가 0** 이라 "재시도하면 될지도" 가 성립하지 않는다.

🔴 **그리고 세션 만료 경로에서는 서버 logout 호출이 실패해도 안전하다.** logout 이 끊는 서버
상태는 `refresh_token_hash` 와 `fcm_token` 둘인데,
- 세션 만료 = `refresh_token_hash` 는 **이미 무효** — 첫 목적은 달성돼 있다.
- 남는 `fcm_token` 은 그대로여도 **그 계정 본인에게 가던 푸시가 계속 갈 뿐**이고, 재로그인하면
  같은 토큰이 재등록된다. **그 기기에서 다른 계정으로 로그인하는 경우**만 위험한데 그건
  `clearFcmTokenOwnedByOthers` 가 **등록 시점에** 막는다 (push-fcm 계약 §0.2 가 정확히
  *"logout 이 아예 호출되지 않는 경로"* 를 위해 만든 장치다).

→ 앱은 세션 만료 경로에서 서버 호출을 **건너뛰거나 실패를 삼켜도 된다.**

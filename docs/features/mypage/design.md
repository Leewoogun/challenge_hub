# §1 마이페이지

## §1.0 골격

Lovable 은 `app-container`(max-width 430px) 안에 sticky header + 본문 + `<BottomNav />` 를 둔다.
네이티브에서는:

- **컨테이너 폭 제약은 무시**한다 (tokens.md §6 — 웹 프리뷰용).
- 🔴 **`<BottomNav />` 와 `pb-24` 를 옮기지 않는다.** `MainScreen.kt:158` 이
  `BottomNavItem.find(currentRoute) != null` 로 탭 화면을 판별해 `Scaffold` 의 `bottomBar` 에 직접 그리고,
  하단 인셋도 `consumeWindowInsets(innerPadding)`(`MainScreen.kt:196-201`)으로 이미 처리된다.
  화면이 또 그리면 바가 두 개가 되고 인셋이 이중 적용된다.
- 좌우 gutter 는 `px-5` = **20dp**. 홈·친구·랭킹과 같은 값이라 변경 없음.

```
ChallengeScaffold(statusBarColor = surface)
├── topBar: ChallengeTopBar("마이페이지", titleStyle = bold20)   §1.1
└── content: Column(verticalScroll)
    ├── ProfileCard                        §1.2
    ├── (캘린더 없음 — §1.3)
    ├── MyPageMenuCard "계약서 보관함"      §1.4   ← 이번엔 1행뿐이다
    ├── 로그아웃 (ghost full-width)         §1.5.1
    └── 회원탈퇴 (작은 텍스트, 최하단)      §1.5.2
```

🔴 **`LazyColumn` 을 쓰지 않는다.** 항목이 고정 5개 이하다. 랭킹이 `LazyColumn` 을 쓴 이유
(*"명단이 나 + accepted 친구 전원이라 상한이 없다"*, [loser-ranking §1.0](../loser-ranking/design.md))가
여기엔 없다. `Column(verticalScroll)` 로 충분하고, 큰 폰트 스케일에서만 스크롤이 생긴다.

- 항목 간격 12dp(`space-y-4` 는 16dp 지만 캘린더가 빠져 항목이 줄었다 — §1.3 참조), 상단 16dp(`mt-4`).
- **컨텐츠 하단 여백 32dp** — `Column` 의 마지막 요소 아래. T-M4 전에는 로그아웃이 최하단이고,
  탈퇴가 붙으면 §1.5.2 의 위치가 그 여백 위에 들어간다(값이 겹치지 않는다). mypage-mobile 질의 반영 —
  **임의값을 넣지 않고 비워 뒀다고 보고받아 여기서 확정한다.**

## §1.2 프로필 카드

- **참조**: `mypage.tsx:38-49`
- **의도**: 내가 누구고, 지금까지 얼마나 이겼나. 이 화면에서 **유일하게 데이터가 있는 카드**다.

```
Surface(radius 16dp, surface + 1dp outline, 패딩 20dp)
└── Row(CenterVertically, spacedBy 16dp)
```

| Row | `gap-4` | `spacedBy(16.dp)`, `Alignment.CenterVertically` |
| 아바타 | `w-16 h-16 rounded-2xl bg-secondary` + 이모지 `text-3xl` | 🔴 `ProfilePlaceholder(size = 64.dp, shape = RoundedCornerShape(20.dp), textStyle = medium24)` — §1.2.1 |
| 닉네임 | `text-lg font-extrabold` | `typography.bold18` / `colorScheme.onBackground`, 1줄 `Ellipsis` |

### §1.2.1 🔴 아바타 radius 는 **20dp** 다 — 랭킹의 16dp 와 다르다

`rounded-2xl` = `--radius-2xl` = **20px** ([tokens.md §4](../../design-system/tokens.md)).
[loser-ranking §9](../loser-ranking/design.md) 가 정리한 아바타 규격표는 전부 `rounded-xl`(**16dp**)이었다 —
**랭킹 화면의 아바타가 `rounded-xl` 이고, 마이페이지 프로필 아바타는 `rounded-2xl` 이다.** 정본이 다르다.

**정본대로 20dp 로 간다.** 프로필 카드의 아바타는 64dp 로 앱에서 가장 크고(랭킹 1위와 같은 크기),
큰 사각형일수록 모서리가 완만해야 시각적으로 같은 곡률로 읽힌다 — 정본의 분기가 자의적이지 않다.

### §1.2.2 이모지 아바타 → 이니셜 placeholder

Lovable 은 😤 이모지를 아바타로 쓴다(`mypage.tsx:39`). **목데이터다 — 도메인에 이모지 필드가 없다.**
→ **`UserInfo.nickname` 첫 글자 `ProfilePlaceholder`** 로 대체.
홈·친구·친구검색·랭킹이 이미 같은 컴포넌트를 쓴다.

🔴 **`AsyncImage` 로 바꾸지 마라.** `UserInfo.profileImageUrl` 은 계약에 있고 값도 실제로 들어오지만,
`http://` 평문이라 **iOS 에서만 ATS 에 차단된다** — Android 로 확인하면 통과하는 **한쪽만 깨지는 실패**다.
사유 전문과 선결 조건은 [loser-ranking §1.2.3.1](../loser-ranking/design.md) 에 있고,
활성화는 **백로그 "`profileImageUrl` 화면 적용"(기존 화면 일괄)** 소관이다. **여기에 복제하지 않는다.**

### §1.2.3 🔴 닉네임을 `"나"` 로 치환하지 않는다

정본 `mypage.tsx:41` 은 이름 자리에 `"나"` 를 박아 뒀다. 그리고 앱에는 그 관례가 실제로 있다 —
챌린지 상세의 `MY_LABEL = "나"`(`ChallengeDetailState.kt:9`), 랭킹의 `isMe` 행 치환
([loser-ranking §1.3.2](../loser-ranking/design.md)).

**여기서는 승계하지 않는다.** `MY_LABEL` 관례는 **여러 사람이 나열된 자리에서 나를 식별**하기 위한
것이고, 이 카드에는 나 혼자다. `"나"` 라고 쓰면 **정보량이 0**이 되고, 카카오 닉네임을 확인할 수 있는
유일한 자리가 사라진다(프로필 편집이 [spec 비범위](./spec.md) 라 다른 확인 경로가 없다).

→ **`UserInfo.nickname` 을 그대로 그린다.** 정본의 `"나"` 는 목데이터의 표기로 읽는다.

그 통일에는 근거가 있다:

  즉 `medium12`. `bold12` 가 아니다.
- 문구는 정본 그대로 `{n}승` · `{n}패` · `{n}무`.

### §1.2.5 🔴 요약 캡션 — 승률 분모는 **`win + lose + draw`.** 정본의 산수를 따르지 않는다

> 🔴 **2026-08-26 판정 전환.** 이 문서 초판은 *"무를 분모에서 뺀다"*(`win/(win+lose)`)로 썼다.
> **mypage-mobile 의 지적으로 뒤집었고, 서버 소스로 확인했다.** 초판의 사유와 새 사유를 §1.2.5.1 에
> 나란히 남긴다 — 결론만 바꾸고 근거를 지우면 나중에 왜 뒤집었는지 알 수 없다.

정본 `mypage.tsx:42` 는 `"총 12챌린지 · 승률 70%"` 이고, 바로 아래 줄(`:45-47`)이 `7승 3패 2무` 다.
**7 + 3 + 2 = 12 인데 7/12 = 58% 지 70% 가 아니다. 70% 는 7/(7+3) 이다** — 정본은 무를 분모에서 뺐다.

**그럼에도 정본을 따르지 않는다.** 근거는 §1.2.5.1.

**계약 변경 0.** `UserRecord`(`win`/`lose`/`draw`/`currentStreak`)만으로 전부 도출된다.

```
total = win + lose + draw          // 총 챌린지 = 승률 분모
rate  = round(win * 100.0 / total) // 🔴 반올림. 정수 나눗셈(버림) 아니다 — §1.2.5.2
```

| 조건 | 캡션 |
|---|---|
| `total == 0` | **`"아직 기록이 없어요"`** (캡션 전체 대체) |
| 그 외 | `"총 {total}챌린지 · 승률 {rate}%"` |

✅ **분기가 3개에서 2개로 줄었다.** 초판은 *"전부 무승부(`win + lose == 0`)면 0으로 나눈다"* 는
세 번째 행이 필요했는데, **분모가 `total` 이 되면서 그 구멍이 통째로 사라진다** —
`total == 0` 하나가 유일한 0 분모이고 첫 행이 이미 잡는다. `UserRecord.isEmpty` 로 그대로 표현된다.

- **승률은 앱이 계산한다.** [loser-ranking §8-②](../loser-ranking/design.md) 가 *"앱은 `lossRate` 를
  재계산하지 않는다"* 로 정한 것과 모순되지 않는다 — 거기서 재계산을 막은 이유는 **서버가 그 정수를
  정렬 3차 키로도 쓰기 때문**(표시와 정렬이 갈린다)이었다. 여기엔 정렬이 없고, 서버가 승률을 갖고
  있지도 않다(`UserRecord` 에 필드 없음). **계약 신규 0** 을 지키는 쪽이 맞다.

⚠️ 문구 `"아직 기록이 없어요"` 는 제안이다 — §6-②.

#### §1.2.5.1 🔴 왜 정본의 산수를 버렸나 — 랭킹 패율과 분모가 갈린다

**mypage-mobile 실측 제보(2026-08-26)를 서버 소스로 확인했다.**

랭킹의 `lossRate` 분모가 **무를 포함한다**:

```
UserRecord.kt:114   totalChallenges = totalChallenges + 1     ← 무승부에서도 증가한다
LoserRanking.kt:68  Math.round(losses * 100.0 / totalChallenges)
```

`applying()` 이 모든 판정(WIN·LOSE·BOTH_LOSE·DRAW)에서 `totalChallenges` 를 1 늘리므로
**`totalChallenges == wins + losses + draws`** 이고, 그게 패율의 분모다.

**초판대로 갔다면 같은 사용자(7승 3패 2무)에게 앱이 이렇게 말한다**:

| 탭 | 표시 | 분모 |
|---|---|---|
| MY (프로필 카드) | 승률 **70%** | `win + lose` = 10 |
| 랭킹 (수치의 명단) | 패율 **25%** | `totalChallenges` = 12 |

**70 + 25 = 95 고, 무(17%)를 더하면 112% 다.** 하단 4탭 구조라 두 화면을 오가는 것이 기본 동선이다.

**판정: `total` 로 통일.** 위 사용자는 승률 **58%** 가 된다. 근거 4가지:

1. 🔴 **캡션 자체가 오독을 유발한다.** `"총 12챌린지 · 승률 70%"` 는 **12를 먼저 말하고** 비율을
   말한다. 자연스러운 읽기는 *"12판 중 70%"* = 8.4승인데 실제는 7승이다. **정본이 자기 캡션과
   어긋나는 산수를 쓰고 있다** — 무를 뺄 거였다면 캡션이 총 챌린지를 앞세우면 안 됐다.
2. 🔴 **랭킹 패율과 분모가 같아진다.** 같은 앱에서 `승률`·`패율` 이라는 대칭적인 이름표를 달고
   다른 분모를 쓰면 두 화면이 서로를 반증한다.
3. 🔴 **이 방향은 `confirmed` 된 loser-ranking 계약을 건드리지 않는다.** 반대 방향(랭킹 패율에서
   무를 빼는 것)만 계약 개정이고, `lossRateOf` 는 **정렬 3차 키**라 바꾸면 순위가 움직인다.
   *"두 화면 중 하나를 맞춘다"* 면 **비용이 0인 쪽이 마이페이지**다.
4. **초판의 사유는 여전히 참이지만 비대칭이다.** *"무승부는 양측 다 성공이라 패배가 아니다"* 는
   맞는 말인데, **무승부는 승리도 아니다.** 한 화면에만 그 논리를 적용하면 무가 승률에서는 빠지고
   패율에서는 들어가는 비대칭이 남는다.

✅ **모바일 `win + lose + draw` 는 서버 `totalChallenges` 와 정확히 같은 값이다**(위 불변식).
즉 **두 화면이 같은 분모를 쓴다** — 계약에 필드를 추가할 필요 없이.

⚠️ **디자이너 확인 대상 (§6-⑮).** 정본 목데이터(70%)보다 낮은 수(58%)가 나오는 것이 유일한 단점이다.
디자이너가 정본 쪽(무 제외)을 고수하면 **랭킹 패율의 분모도 같이 바꿔야 하고, 그건 confirmed 계약
개정 + 정렬 키 변경**이다. 어느 쪽이든 **한 화면만 정할 수 없다.**

#### §1.2.5.2 🔴 HALF_UP 이다 — 정수 나눗셈도, `kotlin.math.round` 도 아니다

> 🔴 **2026-08-26 정정.** 이 절의 초판은 *"`kotlin.math.round` 를 쓰면 된다, 그건 `Math.round` 와
> 같다"* 로 끝맺었는데 **그 문장이 사실과 반대였다.** 내가 §8 에 넣어 둔 회귀 테스트 케이스를
> mypage-mobile 이 실행하다 잡았다 — 경위는 아래.

`LoserRanking.kt:68` 이 `Math.round(losses * 100.0 / totalChallenges)` 다. 서버와 같은 방향을
쓰려면 앱도 그 규칙이어야 하는데, **후보 셋이 전부 다른 답을 낸다**:

| | `62.5` 에서 | |
|---|---|---|
| `win * 100 / total` (Int 나눗셈) | **62** | 버림 |
| `kotlin.math.round(62.5)` | 🔴 **62.0** | **ties-to-even** — `.5` 를 가장 가까운 **짝수**로 보낸다 |
| `Math.round(62.5)` = `floor(x + 0.5)` | **63** | HALF_UP — 서버가 쓰는 것 |

**초판은 가운데 줄을 세 번째 줄과 같다고 적었다. 정반대다** — `kotlin.math.round` 는 `Math.rint`
계열이라 `.5` 를 짝수로 보내고, 하필 `62.5` 는 짝수 쪽이 **버림과 같은 62** 라 Int 나눗셈과도
구분이 안 된다.

→ **`floor(win * 100.0 / total + 0.5).toInt()`** 를 쓴다 (mypage-mobile 구현 확정).
KMP `commonMain` 에는 `Math.round` 가 없으므로 **이게 이식 가능한 등가물**이다.

✅ **회귀 테스트가 문서 오류를 잡았다.** §8 체크리스트에 프리뷰 케이스로 `(5,3,0,0) → 63%` 를
*"62 면 버림을 쓰고 있다"* 라는 사유와 함께 박아 뒀는데, 문서가 지시한 `kotlin.math.round` 로
구현하니 **62 가 나왔다.** 기대값이 근거와 함께 고정돼 있어서 *"문서대로 했는데 왜 다르지"* 가
그 자리에서 드러났다 — **케이스만 적고 사유를 안 적었으면 기대값을 62 로 고쳤을 것이다.**

🔴 **다만 그 케이스 하나로는 진단이 틀릴 수 있었다** (mypage-mobile 지적, 2026-08-26).
`62.5` 는 **짝수 쪽이 버림과 같은 62** 라 **버림과 ties-to-even 을 구분하지 못한다** —
탐지는 되지만 *"버림을 쓰고 있다"* 는 **틀린 진단**으로 이어질 수 있고, 실제로 초판 서술이
그 방향이었다. **`.5` 케이스는 정수부가 짝수인 것과 홀수인 것 두 개가 있어야 셋이 완전히 갈린다**:

| 케이스 | 버림 | ties-to-even | **half-up (정답)** |
|---|---|---|---|
| `(5,3,0,0)` → 5/8 = **62.5** (정수부 짝수) | 62 | **62** | **63** |
| `(7,1,0,0)` → 7/8 = **87.5** (정수부 홀수) | **87** | 88 | 88 |

**두 값을 함께 보면 방식이 유일하게 결정된다** — `(62,87)` = 버림 / `(62,88)` = ties-to-even /
`(63,88)` = half-up. 🔴 **어느 한 값도 단독으로는 셋을 가르지 못한다.**

## §1.3 🔴 캘린더 섹션 — **제외 확정**

`mypage.tsx:51-80` 의 "4월 챌린지 캘린더"(7열 그리드 + 성공/실패 범례)를 **옮기지 않는다.**
근거 4가지 — 뒤로 갈수록 강하다:

1. **사용자가 확정했다.** [spec.md 사용자 확정 ②](./spec.md) — *"계약서 보관함 = 월별 조회 + 카드
   목록 (캘린더 아님 — 캘린더는 통계 화면 feature 로 이월)"*.
2. **정본이 `Math.random()` 이다.** `mypage.tsx:24-27` 이 30일치를 난수로 만든다. 목데이터조차
   아니고 **데이터 형태 자체가 정의된 적이 없다.**
3. **데이터 소스가 서버에 없다.** `GET /record` 는 누적 4값(승/패/무/연승)뿐이고, 일자별 성공·실패를
   주는 엔드포인트가 없다. 그리려면 **API 신설이 선행**인데 [spec 수용 기준](./spec.md)이
   프로필 카드에 대해 *"기존 API 재사용, 신규 0"* 을 요구한다.
4. **카탈로그가 이미 그 feature 를 별건으로 예고해 뒀다.**
   [tokens.md §8-5](../../design-system/tokens.md) 가 차트 5색을 닫으면서 *"되살아날 조건: **월별 달성
   캘린더**가 착수되고, 그 디자인이 다색 시각화를 쓸 때"* 라고 적었다. 이 문서가 그 항목을 열지 않는다.

**자리는 비우고 아래를 위로 올린다.** placeholder 나 "준비 중" 카드를 넣지 않는다 — §1.4.2 와 같은 판단.

## §1.4 🔴 메뉴 구성 — 정본 4개 중 **1개만 남긴다**

정본 `mypage.tsx:16-21` 의 메뉴 4개에 대한 판정:

| # | 정본 항목 | 판정 | 사유 |
|---|---|---|---|
| 1 | **통계** (승률, 연승, 월별 기록) | ❌ **미노출** | §1.4.2 |
| 2 | **계약서 보관함** (과거 영혼의 맹세 열람) | ✅ **유지** — 이번 feature 의 본체 | §2 |
| 3 | **개돼지 랭킹** (패배의 왕좌 확인) | ❌ **제외** | §1.4.1 |
| 4 | **설정** (알림, 계정 관리) | ❌ **화면을 만들지 않는다** | §1.4.3 |

### §1.4.1 개돼지 랭킹 — 제외

정본도 `to: "/ranking"` 으로 **하단 탭과 같은 목적지**다(`mypage.tsx:19`, `BottomNav.tsx:6`).
[spec 비범위](./spec.md)에 이미 *"탭과 중복이라 제외 제안"* 이 있고, 디자인 측도 같은 결론이다.

웹에서는 탭바가 뷰포트 하단 고정이라 중복이 덜 느껴지지만, 모바일도 `MainScreen` 이 같은 자리에
같은 바를 그린다. **한 화면에 같은 목적지로 가는 길이 둘이면 하나는 잘못된 길처럼 보인다.**

### §1.4.2 🔴 통계 — **"준비 중" 행조차 만들지 않는다**

이게 [spec T-D1](./spec.md) 이 명시로 요구한 판정이다. **미노출로 정한다.** 근거 3가지:

1. **이 앱에 "준비 중" 메뉴 선례가 0건이다.** 눌러도 아무 일 없는 행은 고장난 화면이고,
   새 방언을 마이페이지에서 만들 이유가 없다. (`PlaceholderScreen` 은 개발 중 스캐폴딩이지
   사용자에게 보이라고 만든 것이 아니다 — `Route.Notifications` 가 그 예다.)
2. **프로필 카드가 통계의 요약을 이미 준다** — 총 챌린지·승률·승/패/무(§1.2). 통계 화면이 **추가로**
   주는 것은 캘린더·기간별 추이인데, 그건 §1.3 에서 봤듯 **API 수준에서 존재하지 않는다.**
   즉 "준비 중"이 가리킬 대상이 아직 없다.
3. **메뉴가 1행으로 줄면 보관함이 이 화면의 주인공이 된다.** 그게 이번 feature 의 실제 내용이다.
   4개 중 하나로 묻히는 것보다 정직하다.

⚠️ **디자이너 확인 대상 (§6-③).** 통계 feature 가 착수되면 이 자리의 **첫 행**으로 들어간다
(정본의 순서를 보존한다 — 통계가 보관함 위다).

### §1.4.3 🔴 설정 — **별도 화면을 만들지 않고, 계정 영역을 본문에 직접 둔다**

[spec](./spec.md) 은 *"설정 골격"* 을 요구하면서 동시에 *"알림 설정(on/off) — 끌 대상이 아직 4종뿐,
설정은 골격만"* 을 비범위로 뒀다. 그러면 **설정 화면에 들어갈 것이 로그아웃·회원탈퇴 둘뿐**이다.

**판정: 설정 route·화면·ViewModel 을 신설하지 않는다.** 근거 3가지:

1. **항목 2개짜리 화면을 위해 route + ViewModel + 네비게이션 + 뒤로가기를 신설하는 비용이 얻는 것보다 크다.**
2. 🔴 **출시된 동선이 깊어진다.** 로그아웃은 **지금도 마이페이지 화면에 직접 있다**
   (`MyPageScreen.kt:22-29`). 설정 화면을 끼우면 사용자가 이미 쓰던 경로가 한 단계 늘어난다 —
   이번 feature 의 목표는 마이페이지를 **채우는 것**이지 한 겹 씌우는 것이 아니다.
3. **정본도 로그아웃을 메뉴에 넣지 않았다.** `mypage.tsx:104-108` 이 메뉴 리스트 **밖**, 본문 하단에
   직접 뒀다. 정본의 "설정" 메뉴는 *"알림, 계정 관리"* 라고 적혀 있는데, **알림이 빠지면 남는 것이
   이미 본문에 있는 것들뿐**이다.

⚠️ **디자이너 확인 대상 (§6-④).** **알림 설정이 붙는 시점**에 설정 화면을 신설하고 계정 영역을
그 안으로 옮긴다 — 그때는 화면에 고유 내용이 생긴다.

**기각한 대안**: *메뉴에 "설정"을 남기고 그 안에 로그아웃·탈퇴를 넣는다.* 기각 사유 —
탈퇴를 한 단계 뒤로 숨기는 효과는 있지만(§1.5.2 의 요구), **로그아웃도 같이 숨겨진다.**
로그아웃은 자주 쓰는 정상 동작이고 이미 노출돼 있다. 숨겨야 하는 건 탈퇴 하나뿐이라
**화면을 하나 만드는 대신 §1.5.2 의 시각 위계로 푼다.**

## §1.5 계정 영역 — 로그아웃과 탈퇴는 **같은 무게가 아니다**

### §1.5.1 로그아웃

### §1.5.2 🔴 회원탈퇴 — 정본에 없다. **error 색을 쓰지 않는다**

[spec T-D1](./spec.md) 요구: *"탈퇴는 눌리기 어려운 위치 + 경고 확인 필수"*.

| 요소 | 값 |
|---|---|
| 위치 | 로그아웃 **아래**, **24dp 간격**, 화면 최하단 (아래 여백 32dp) |
| 형태 | 버튼이 아니라 **텍스트 1줄**. 배경·보더·아이콘 **없음** |
| 문구 | `"회원 탈퇴"` |
| 타이포 | `typography.medium12` |
| 색 | 🔴 **`colorScheme.onSurfaceVariant`** — **`error` 아니다** |
| 정렬 | 가운데. **`fillMaxWidth()` 를 주지 않는다** |
| 터치 타깃 | 텍스트 폭 + `padding(horizontal = 16.dp, vertical = 16.dp)` 로 **높이 48dp 확보** — 🔴 산수 정정, 아래 |

🔴 **탈퇴에 `error` 색을 쓰지 않는 이유** — 이 화면에서 `error` 는 **로그아웃이 이미 쓰고 있다**(§1.5.1,
정본 `text-destructive`). 더 위험한 행위에 **덜 위험한 행위와 같은 색**을 주면 위계가 서지 않고,
둘 중 무엇이 더 무거운지 화면이 말하지 못한다.

**대신 시각적으로 낮춘다.** 작은 글자 + muted 색 + 좁은 터치 폭이 *"눌리기 어려운 위치"* 의 실체다.
🔴 **위험 경고는 색이 아니라 §1.6 다이얼로그가 한다** — 우발적 탭을 줄이는 것과 의도적 탭에
경고하는 것은 서로 다른 일이고, 두 번째는 다이얼로그가 확실히 처리한다.

⚠️ **접근성과의 절충**: 세로 패딩으로 **48dp 최소 터치 타깃을 지키되 가로 폭은 텍스트 크기로 한정**한다.
높이를 줄여서 누르기 어렵게 만들지 마라 — 그건 스크린리더·운동 장애 사용자에게만 어려워진다.

🔴 **산수 정정 (2026-08-26, Lovable 프리뷰 제작 중 발견).** 초판은 `vertical = 14.dp` 라고 썼는데
**그 값으로는 48dp 가 안 나온다** — `medium12` 의 lineHeight 는 **16sp**([tokens.md §5.2](../../design-system/tokens.md)
`text-xs` = 12/16)이므로 `16 + 14 + 14 = 44dp` 다. **`vertical = 16.dp` 여야 `16 + 16 + 16 = 48dp`** 다.
*"높이를 줄이지 마라"* 라고 써 놓고 **문서가 스스로 4dp 를 줄이고 있었다.**
프리뷰(`archive`/`mypage` route)를 만들며 `py-3.5`(14px)로 옮겼다가 계산이 어긋나 발견했다.

⚠️ **디자이너 확인 대상 (§6-⑥)** — 문구·색·배치 전부 제안이다(정본에 없다).

## §1.6 🔴 탈퇴 확인 다이얼로그 — 신규 `ConfirmDialog`

[spec 수용 기준](./spec.md): *"탈퇴는 **경고 확인 단계**를 거친다 (되돌릴 수 없음 고지)"*.

**1단계 다이얼로그로 충분하다.** 문구 입력 재확인(`"탈퇴"를 입력하세요`) 같은 2단계는 넣지 않는다 —
개인 프로젝트 규모에서 이탈만 만들고, 되돌릴 수 없다는 사실은 문구가 이미 말한다.

| 요소 | 값 | 토큰 |
|---|---|---|
| 제목 | `"정말 탈퇴하시겠어요?"` | `bold18` / `onBackground` |
| 본문 | 아래 2문단 | `medium14` / `onSurfaceVariant` |
| 확인 | `"탈퇴하기"` | `medium14` / 🔴 **`colorScheme.error`** |
| 취소 | `"취소"` | `medium14` / 🔴 **`colorScheme.primary`** |
| 배경 | | `colorScheme.background` (`PermissionSettingsDialog.kt:27` 과 동일) |

**본문 (제안)**:

> 계정 정보와 인증 사진이 삭제되고 되돌릴 수 없어요.
>
> 지난 챌린지의 계약서와 결과는 **상대방의 기록이라 남아요** — 상대 화면에서 나는
> "탈퇴한 사용자" 로 보여요.

🔴 **두 번째 문단을 빼지 마라.** [spec 탈퇴 정책표](./spec.md)의 핵심이 *"익명화 + **기록 보존** +
사진 삭제"* 인데, 사용자가 *"내 기록이 전부 지워진다"* 로 오해한 채 탈퇴하면 **동의한 내용과 실제가
다르다.** 이 앱의 컨셉이 증거 보존이라 더 그렇다 — 남는다는 사실 자체가 고지 대상이다.

🔴 **취소를 `primary`, 확인을 `error` 로 두는 것은 `PermissionSettingsDialog` 와 반대다**
(`PermissionSettingsDialog.kt:42-59`: confirm=`primary` "설정 열기" / dismiss=`onSurfaceVariant` "나중에").
의도적이다 — 파괴적 액션 다이얼로그에서는 **안전한 쪽이 먼저 눈에 들어와야** 한다.
Material3 `AlertDialog` 는 `confirmButton` 이 오른쪽(기본 강조 위치)이라 **색으로 뒤집는다.**

⚠️ **디자이너 확인 대상 (§6-⑦)** — 문구 전체가 제안이다.

  🔴 위 판정은 그 금지와 어긋나지 않는다 — **카드 안 한 영역의 표현이지 화면 상태가 아니다.**
- **재시도 버튼을 붙이지 않는다.** 마이페이지는 **탭 화면**이라 랭킹과 같이 *"재시도는 탭 재진입"*
  이 성립한다([loser-ranking §3.1](../loser-ranking/design.md)).

### §1.7.1 🔴 초판이 §2.5.4 를 어겼다 — mypage-mobile 발견

**초판 문면**: *"프로필 카드는 그리되 캡션을 §1.2.5 `total == 0` 행(`"아직 기록이 없어요"`)으로
내리고 승/패/무는 muted 톤으로."*

**두 가지가 잘못됐다.**

**① 같은 문서 §2.5.4 가 금지한 거짓말이다.** 보관함에 대해 이렇게 써 놓고:

> 🔴 조회 실패를 `EmptyStateCard` 로 그리지 마라 — **0건과 실패는 다른 사실**이고, 증거 보관 화면에서
> *"기록이 하나도 없다"* 는 **거짓이 가장 나쁘다**

프로필 카드에는 **정확히 그 거짓을 지시**했다. 7승 3패인 사용자에게 서버가 잠깐 죽었다는 이유로
*"아직 기록이 없어요"* 라고 말하는 것이다. **같은 feature 의 두 화면이 정반대 원칙을 따르게 된다.**

⚠️ **§6-⑧ 을 닫는다.** 그 확인 항목은 *"muted 의 정본 의미(신규 사용자)와 여기 원인(조회 실패)을
같은 표현으로 뭉개도 되는지"* 였는데, **§2.5.4 가 이미 "뭉개면 안 된다"로 답했다.**
디자이너에게 물을 것이 아니라 내가 문서 안에서 맞췄어야 했다.

**② 그 상태가 코드에 존재하지 않았다.** `GetMyPageDataUseCase` 가 `combine(record, userInfo)` 인데
전적 Flow 에 폴백이 없어(전적이 이 화면의 필수 데이터라 홈의 판단을 승계) 실패 시 `combine` 이 값을
못 내고 `uiState` 가 **`Loading` 에 머문다.** 사용자가 보는 건 muted 카드가 아니라 **무한 스피너**다.

### §1.7.2 판정 — 세 안 중 어느 것도 그대로 쓰지 않는다

mypage-mobile 이 3안을 제시했다. **어느 것도 그대로 채택하지 않고, 3안을 고쳐서 쓴다.**

| | 안 | 판정 |
|---|---|---|
| **1** | 현행 유지(무한 스피너 + 스낵바) + §1.7 표만 정정 | ❌ **기각.** 거짓말을 안 하는 게 아니라 **다른 거짓말**을 한다 — 실패했는데 화면이 영원히 *"불러오는 중"* 이라고 말한다. 게다가 **스낵바는 사라지고 스피너는 남아서**, 잠시 뒤 화면에 온 사용자는 "느린 건지 고장 난 건지" 구분할 수단이 0이다 |
| **2** | 화면 Error 상태 신설 | ❌ **기각.** 화면 전체를 실패로 덮으면 **성공한 데이터(닉네임·아바타·메뉴·로그아웃)까지 못 쓰게 된다.** 전적 하나 못 받았다고 로그아웃 버튼이 사라지면 안 된다 |
| **3** | `UserRecord.Empty` 폴백 + §1.2.5 에 실패 전용 캡션 행 추가 | ⚠️ **절반만 맞다** — §1.7.3 |

#### §1.7.3 🔴 3안의 구멍 — 캡션은 정직해지지만 **숫자는 여전히 거짓말한다**

3안은 캡션을 `"전적을 불러오지 못했어요"` 로 구분하지만, `UserRecord.Empty` 로 폴백하므로
승/패/무 행에는 **`0승 0패 0무` 가 그대로 그려진다.**

**muted 톤이 그걸 구제하지 못한다.** §6-⑧ 이 지적했듯 muted 의 기존 의미는 정본에서
*"신규 사용자"*(`isFirstUser`)다 — 즉 **"이 0은 진짜 0이다"** 라는 뜻이다. 7승 3패인 사람에게
회색 `0승 0패 0무` 를 보여주면 **회색이라서 덜 거짓인 게 아니라, 회색으로 확신에 차서 거짓말한다.**

🔴 **§2.5.4 의 원칙은 문구가 아니라 사실 주장에 걸린다. 숫자도 사실 주장이다.**

**→ 판정: 3안에서 폴백 숫자를 뺀다.**

전적 조회 실패 시 프로필 카드는:

```
Row(CenterVertically, spacedBy 16dp)
├── ProfilePlaceholder (64dp)        ← UserInfo 캐시. 성공한 데이터다
└── Column
    ├── 닉네임                        bold18 / onBackground     ← 그대로
    └── "전적을 불러오지 못했어요"      medium12 / onSurfaceVariant
        (승/패/무 행 없음)
```

근거 3가지:

1. **닉네임·아바타는 실제로 성공한 데이터다.** `UserInfo` 캐시에서 오고 `GET /record` 와 출처가 다르다.
   지울 이유가 없다 — 초판 §1.7 의 의도(*"화면을 비우지 않는다"*)는 여기서 살아남는다.
2. 🔴 **모르는 것은 그리지 않는다.** 0을 그리는 순간 그건 muted 여도 사실 주장이다.
   **빈 자리가 틀린 자리보다 낫다** — 홈 `ChallengeCard.kt:139` 가 같은 상황(서버가 모르는 결과값)에서
   내린 판단이고, 그 주석이 문장 그대로 그렇게 적혀 있다.
3. **캡션 자리를 쓰므로 레이아웃이 무너지지 않는다.** 승/패/무 행이 빠지면 카드 높이가 줄지만,
   프로필 카드는 화면 최상단 단독 카드라 아래가 밀려 올라올 뿐 깨지지 않는다.

✅ **§1.2.5 표에 행을 추가하지 않는다.** 실패는 **캡션 분기가 아니라 전적 영역 전체의 대체**라
`total == 0` 과 같은 층위가 아니다. §1.2.5 는 2행 그대로 유지된다.

⚠️ **`UiState` 가 실패를 값으로 표현해야 한다** — 이건 3안과 같은 배선 비용이다. 형태
(`win`/`lose`/`draw` 를 nullable 로 vs 별도 플래그)는 mobile-dev 판단이되, 🔴 **`0` 을 그리는
경로가 남아 있으면 안 된다.**

⚠️ 문구 `"전적을 불러오지 못했어요"` 는 제안이다 — §6-⑯.

# §2 계약서 보관함 (신규 화면)

## §2.0 이 화면은 Lovable 에 없다

`mypage.tsx:18` 의 메뉴 항목이 `to: "/mypage"` — **자기 자신을 가리킨다.** 목적지가 만들어진 적이 없고,
`src/routes/` 에 대응 파일도 없다(`repos.json` 의 `known_routes` 8개에 없다).

**출발점은 사용자 지시 한 줄이다** ([spec.md](./spec.md)):

> **"월별로 조회해서 카드 형식으로 정리"**

그리고 이 화면이 갚아야 할 빚이 둘 있다:
- **백로그 🟡 "결과 히스토리 화면 부재"** — 홈의 7일 노출이 시간벌기였고, 이 화면이 정식 해법이다.
- **기획 §3.3** *"이때 너 이거 걸었잖아"* — 증거 보관의 이행.

이 둘이 §2 의 모든 판정 기준이다: **지난 결과에 도달할 수 있는가**, **증거로 읽히는가.**

## §2.1 🔴 조회 단위 — **전체 목록 + 클라이언트 월 그룹핑.** 월 파라미터를 만들지 않는다

[api-contract.md 쟁점 ①](./api-contract.md)에 대한 디자인 측 확정 입장이다. 두 안:

| | 안 |
|---|---|
| **(a)** | 월 파라미터 `?month=2026-08` + **월 이동 UI**(`< 2026년 8월 >`) |
| **(b)** | ✅ **채택** — 전체(최신순) 1회 조회 + **월 섹션 헤더**로 앱이 그룹핑 |

사용자 지시의 **문면**("월별로 조회")은 (a)에 가깝지만, **의도**("월별로 정리된 카드")는 (b)가 더 잘
충족한다. 근거 4가지:

1. 🔴 **월 이동 UI 는 빈 월을 계속 만나게 하는 UI다.** 1:1 챌린지에 **종료된 것만** 담기므로 월당
   건수가 한 자릿수고, **대부분의 월이 0건**이다. 사용자가 *"이때 너 이거 걸었잖아"* 로 찾으려면
   **몇 월이었는지 먼저 기억**해야 하는데, 기억 못 하면 화살표를 누르며 빈 화면을 넘긴다.
   **화면의 목적을 UI 가 방해한다.**
2. 🔴 **(a)는 첫 진입이 빈 화면이 될 수 있다.** 이번 달 종료 건이 없으면 기본값이 그대로 빈 화면이다.
   반면 최신순 전체 목록은 **첫 화면 최상단이 가장 최근 종료 건**이라,
   [spec 수용 기준](./spec.md)의 *"보관함으로 홈 7일 노출이 지난 결과에도 도달할 수 있다"* 가
   **아무 조작 없이** 충족된다. (a)에서는 그게 "이번 달에 종료 건이 있을 때만" 성립한다.
3. 🔴 **이 화면에서 '월'은 탐색 축이 아니라 그룹핑 라벨이다.** 월이 1급 탐색 축인 UI 가 캘린더인데,
   사용자가 그걸 이번 범위에서 빼고 통계 feature 로 이월했다(§1.3). **같은 판단이 보관함에도 걸린다** —
   보관함에서 월은 *"언제쯤 일이었지"* 를 훑게 해 주는 이정표지, 선택해서 들어가는 서랍이 아니다.
4. **앱의 분기가 하나도 안 는다.** (a)는 선택된 월·이동 가능 범위·경계에서 화살표 비활성 같은 상태를
   앱이나 서버가 들어야 한다. (b)는 스크롤 한 줄기다.

→ **요청 파라미터에 `month` 를 두지 마라.** 서버는 정렬된 전체 목록을 주고, **월 그룹핑은 앱이 한다.**
(랭킹에서 정렬·`rank` 부여를 서버가 쥔 것과 다르다 — 여기 그룹핑은 순수 표시 로직이고,
서버가 그룹을 나눠 주면 응답 shape 에 화면 구조가 박힌다.)

**페이지네이션**: **미적용 권고.** 재검토 임계치를 계약에 숫자로 박아 두는 것까지는 찬성(랭킹 선례).
넣어야 한다면 🔴 **커서 방식** — 월 오프셋 페이지는 위 근거 1·2 를 그대로 되살린다.

✅ **mypage-backend 실측(2026-08-26)이 이 권고를 더 강하게 만든다.** 서버 `controller/src/main` 의
**모든 목록 엔드포인트**(`/friends` · `/friends/requests/received` · `/challenges/received` ·
`/challenges/active` · `/rankings/losers`)에 `Pageable`·`cursor`·`page` 가 **0건**이다.
그런데 [CLAUDE.md](../../../CLAUDE.md) 규칙이 *"페이지네이션은 프로젝트 전체에서 한 방식으로 통일"* 이다 —
🔴 **보관함 하나 때문에 첫 페이지네이션을 도입하면 그 규칙이 금지하는 상태(한 엔드포인트만 다른 방식)를
이 feature 가 만드는 셈이다.** 필요해지는 시점에 전 엔드포인트를 한 번에 결정하는 것이 맞다.

응답 크기도 작다 — 같은 상대와 하루 한 판이 상한이고(`findConflicting` 이 `challenge_date` 로 막는다),
카드 한 장이 닉네임·양측 미션·내기·결과·날짜 정도라 수백 건이어도 수십 KB 수준이다(mypage-backend 실측).

## §2.2 🔴 월 경계 기준 = **`challengeDate`.** `completed_at` 을 쓰면 즉시 어긋난다

판정이 **자정 직후 배치**다(`repos.json` `core_flow`, 기획 §2.6). 그래서 말일 챌린지는
`completed_at` 이 **다음 달 1일 00:0x** 에 찍힌다.

→ `completed_at` 으로 그룹핑하면 **8월 31일 챌린지가 "2026년 9월" 헤더 아래** 들어간다.
카드에 적힌 날짜(8/31)와 그 카드가 속한 헤더(9월)가 **한 화면에서 서로 다른 말을 한다.**

사용자가 기억하는 것은 *"언제 챌린지를 했나"* 지 *"언제 판정됐나"* 가 아니다.
**정렬도 `challengeDate DESC`** 로 맞춘다 — 헤더 순서와 카드 순서가 갈리지 않게.

## §2.3 골격

**탭 화면이 아니다.** 마이페이지에서 push 로 들어가는 하위 화면이다.

```
ChallengeScaffold(statusBarColor = surface)
├── topBar: ChallengeTopBar("계약서 보관함", onBack = ..., titleStyle = bold18)   ← §2.3.1
└── content: LazyColumn(contentPadding = PaddingValues(vertical = 8.dp))   ← 🔴 horizontal 없음
    ├── stickyHeader  MonthHeader "2026년 8월"  §2.3.2
    ├── items         ArchiveChallengeCard × N  §2.4
    ├── stickyHeader  MonthHeader "2026년 7월"
    ├── items         ...
    └── item          EmptyStateCard             §2.5.1  (전체 0건일 때만)
```

- 🔴 **`LazyColumn` 이 맞다.** 종료 챌린지는 **상한이 없고 시간이 갈수록 는다** — §1.0 에서
  `Column(verticalScroll)` 을 고른 것과 반대다.
- 🔴 **바텀바를 그리지 않는다.** `MainScreen.kt:158` 의 `BottomNavItem.find(currentRoute)` 가
  탭 route 가 아니면 `null` 을 주므로 **자동으로 안 그려진다.** 화면이 할 일이 없다.
- 카드 간격 12dp, 월 섹션 사이 24dp.
- 🔴 **좌우 gutter 20dp 를 `contentPadding` 으로 주지 마라** (§3.2.1-②). sticky 월 헤더의 배경이
  gutter 만큼 좁아져 **좌우로 카드가 비친다.** 헤더는 **전폭 배경 + 자체 좌우 패딩 20dp**,
  카드도 **자체 좌우 패딩 20dp** 로 각자 낸다. (Lovable 프리뷰가 `-mx-5 px-6` 으로 gutter 밖까지
  넓혀 덮은 것과 같은 문제다 — §2.3.2)

### §2.3.1 상단바

| 요소 | 토큰 |
|---|---|
| 제목 | `"계약서 보관함"` — `ChallengeTopBar` 기본 `bold18` / `onBackground` |
| 뒤로가기 | `onBack` 을 넘긴다 → `ChallengeTopBarBackButton`(`TopBar.kt:98-113`) 자동 |

🔴 **여기는 `bold20` 을 넘기지 않는다.** §1.1 의 `bold20` 은 **탭 헤더**의 값이고
(정본 4탭이 전부 `text-xl`), 이 화면은 탭이 아니라 하위 화면이다. 하위 화면 상단바는
`ChallengeTopBar` 기본값을 쓴다 — 챌린지 상세·생성·친구검색이 그렇게 돼 있다.

### §2.3.2 월 섹션 헤더

정본이 없으므로 **홈의 섹션 헤더 문법을 승계**한다 (`index.tsx:222-226`,
`ReceivedChallengesSection` — `text-sm font-bold text-foreground` + `mb-2 px-1`).

```
Row(SpaceBetween, CenterVertically, 하단 8dp)
├── "2026년 8월"     bold14 / onBackground
└── "{n}건"          medium12 / onSurfaceVariant
```

- 우측 건수는 홈 "진행 중인 챌린지 / {n}개"(`index.tsx:171-172`, `text-xs text-muted-foreground`)의
  승계다. 단위는 홈이 `개`, 받은 도전장이 `건` 인데 **여기는 `건`** — 챌린지는 세는 물건이 아니라
  일어난 일이다(받은 도전장 쪽 어휘).
- **`stickyHeader` 를 쓴다.** 스크롤 중 지금 보고 있는 카드가 몇 월인지 항상 보인다 —
  월 이동 UI 를 뺀(§2.1) 대가를 이게 갚는다.
  ⚠️ 앱에 `stickyHeader` 선례가 없다. 구현 부담이 크면 **일반 `item` 으로 내려도 된다** —
  그 경우 mobile-report 에 남기고 이 문서를 고쳐라(§8).
- 🔴 **sticky 로 갈 거면 헤더에 자체 배경이 있어야 한다** (2026-08-26 프리뷰 제작 중 확인).
  초판은 타이포·문구만 지정했는데, **배경이 없으면 스크롤되는 카드가 헤더 글자 뒤로 그대로 비쳐서
  두 텍스트가 겹친다.** 프리뷰는 `-mx-5 px-6 py-2 bg-background/80 backdrop-blur-xl` 로 좌우를
  gutter 밖까지 넓혀 덮었다. 모바일은 blur 를 재현하지 않으므로(§1.1 과 같은 판단)
  **`colorScheme.background` 불투명 배경 + 상하 8dp 패딩**을 준다.
  → 그래서 §2.3 의 `contentPadding` 세로값은 **8dp 로 충분하다** — 나머지 여백은 헤더가 자체 패딩으로 낸다.
- 연도 표기: **매 헤더에 연도를 붙인다**(`"2026년 8월"`). 같은 해에는 생략하는 방식은
  스크롤 중간에서 헤더만 보면 연도를 알 수 없다.

## §2.4 🔴 보관함 카드 — 홈 `ChallengeCard` 를 그대로 쓰지 않는다

- **문법 참조**: `ChallengeCard.kt`(홈) · Lovable `components/ChallengeCard.tsx`

```
Surface(radius 16dp, surface + 1dp outline, clickable)
└── Column(패딩 16dp, spacedBy 12dp)
    ├── HeaderRow    { 🔥 "vs {상대}"  ····  ChallengeOutcomePill }
    ├── MissionRow   { "나의 미션" / {myMission} }
    ├── MissionRow   { "{상대}의 미션" / {opponentMission} }
    └── BetStrip     "내기: {bet}"
```

**카드 문법(16dp radius · `surface` + 1dp `outline` · 패딩 16dp · 12dp 간격 · `"vs {상대}"` 헤더 ·
내기 띠)은 홈 카드를 그대로 승계한다.** 두 화면이 같은 사물을 그리므로 같은 문법이어야 한다.

### §2.4.1 🔴 인증 상태 pill 2개를 **뺀다**

홈 `ChallengeCard` 는 미션 행마다 `VerificationStatusPill` 을 그린다(`ChallengeCard.kt:197`).
**보관함 카드에서는 뺀다.** 근거:

**판정 규칙상 4개 결과가 양측 인증 상태를 각각 유일하게 결정한다** (기획 §2.5):

| 결과 | 나 | 상대 |
|---|---|---|
| 승리 | 인증 ✅ | 미인증 ❌ |
| 패배 | 미인증 ❌ | 인증 ✅ |
| 무승부 | 인증 ✅ | 인증 ✅ |
| 양측 패배 | 미인증 ❌ | 미인증 ❌ |

→ **결과 pill 하나가 인증 pill 두 개의 정보를 전부 담고 있다.** 그리면 **정보량 0인 요소가 두 개**
늘어나고, 카드가 세로로 길어져 한 화면에 담기는 카드 수가 준다. 훑는 화면에서 그건 손해다.

**즉 보관함 카드 = 홈 카드에서 인증 pill 2개를 뺀 형태다.** 계약에서도 그 두 필드를 요구하지 않는다(§7).

### §2.4.2 헤더 우측은 항상 `ChallengeOutcomePill`

홈 카드의 헤더 우측은 `outcome` → `remainingText` → 빈 자리 순으로 분기한다(`ChallengeCard.kt:140-159`).
**보관함은 `COMPLETED` 만 담으므로**(§2.5.3) `outcome` 이 **항상 non-null** 이고 분기가 없다.

- 🔴 **`ChallengeOutcomePill`(`:core:ui`)을 그대로 쓴다.** 승패무 표현의 **단일 출처**이고,
  홈 카드·상세 헤더가 이미 이걸 쓴다. **보관함이 자기 매핑을 만들면 같은 전적이 세 화면에서 다른 색이 된다.**
- 🔴 **남은 시간·마감 표기를 넣지 마라.** 끝난 챌린지에 시계를 그리는 것이 홈 카드가 이미 피한 함정이고
  (`ChallengeCard.kt:131-139` 주석), 여기선 아예 해당이 없다.
- 대신 **날짜**가 필요하다 — §2.4.3.

### §2.4.3 🔴 날짜를 어디에 넣나

홈 카드에는 날짜 자리가 없다(진행 중이라 "3시간 남음"이 그 자리를 쓴다). 보관함은 **언제 일이었는지가
카드의 핵심 정보**다. 월 헤더가 월까지는 말해 주지만 **며칠인지는 카드가 말해야 한다.**

**판정: 헤더 Row 의 `"vs {상대}"` 바로 뒤에 날짜를 붙인다.**

```
Row(CenterVertically, spacedBy 6dp)
├── Icon 🔥 LocalFireDepartment 18dp, primary
├── "vs {상대}"        medium12 / onSurfaceVariant
├── "·"                medium12 / onSurfaceVariant
└── "{M}월 {d}일"      medium12 / onSurfaceVariant
```

- 형식은 **`"8월 31일"`** — 월 헤더가 연도·월을 이미 말했으므로 연도를 반복하지 않는다.
  ⚠️ 월 헤더와 카드 날짜의 월이 중복되지만, **카드만 떼어 봐도 읽히는 쪽**이 낫다(스크롤 중에는
  헤더가 화면 밖일 수 있다 — `stickyHeader` 를 못 쓰게 되면 특히).
- 🔴 **결과 pill 옆에 두지 않는다.** 우측은 pill 이 쓰고, 날짜와 결과가 붙으면 *"이날 졌다"* 보다
  *"이 날짜의 결과"* 라는 표 같은 읽기가 되어 카드의 서술 톤이 깨진다.
- 상대 닉네임이 길면 날짜가 밀린다 → **닉네임에 `weight(1f, fill = false)` + `Ellipsis`**,
  날짜는 자르지 않는다.

⚠️ **디자이너 확인 대상 (§6-⑨)** — 정본에 없는 요소다.

### §2.4.4 탭 → 기존 상세

카드를 탭하면 `Route.Challenge.Detail(challengeId)` 로 간다. **신규 상세 화면을 만들지 않는다** —
[spec §0 사전 실측](./spec.md)이 *"`GET /challenges/{id}` 가 기한 없이 열린다 (계약서·서명·사진·결과) —
목록만 만들면 된다"* 로 이미 확인했다. 계약서 원문·양측 서명·인증 사진이 거기 다 있다.

🔴 **이게 *"이때 너 이거 걸었잖아"* 가 완성되는 지점**이다. 보관함 카드는 목록이고,
증거 원문은 상세다. 카드에 계약서 본문을 미리보기로 넣지 않는다 — §4.

## §2.5 상태 매트릭스

### §2.5.1 빈 상태 — 종료 챌린지 0건

`EmptyStateCard`(`:core:ui`)를 쓴다. **loser-ranking 이 이미 `:core:ui` 로 승격해 뒀다**
(`EmptyStateCard.kt` — `icon`·`ctaIcon`·`inviteLabel` 전부 파라미터로 열려 있다). 신규 제작 0.

| | 값 |
|---|---|
| 아이콘 | `Icons.Filled.Description`, 32dp, `primary` (배경 `primary.copy(alpha = 0.10f)` — 컴포넌트 내장) |
| 제목 | `"아직 끝낸 챌린지가 없어요"` |
| 부제 | `"챌린지가 끝나면 계약서가 여기 쌓여요"` |
| CTA | `"챌린지 만들기"` + `ctaIcon = Icons.Filled.SportsKabaddi` → `Route.Challenge.Create` |
| 보조 CTA | 없음 (`onClickInvite = null`) |

- `ctaIcon` 은 홈 빈 상태와 같은 값이다(`HomeEmptyState.kt:111`) — 같은 행동에 같은 아이콘.
  🔴 **기본값(`PersonAdd`)을 그대로 두면 안 된다**, 명시로 넘겨라.
- 🔴 **진행 중 챌린지가 있는데 종료 건이 0 인 경우가 흔하다**(첫 챌린지 진행 중). 그때도 이 빈 상태가
  맞다 — *"끝낸"* 이라는 단어가 그 구분을 하고 있다. CTA 가 "챌린지 만들기"인 것이 어색하다면
  §6-⑩ 에서 다룬다.

⚠️ 문구는 제안이다 — §6-⑩. 톤은 담담하게 잡았다. 보관함은 도발조(랭킹)가 아니라 **기록 보관소**의 어휘다.

### §2.5.2 🔴 탈퇴한 상대 — **특별 표시를 넣지 않는다**

[api-contract §2](./api-contract.md) 권고대로 서버가 `nickname` 을 **non-null 유지한 채
`"탈퇴한 사용자"`** 로 내려주면 **계약 변경 0**으로 끝난다. 디자인 측 찬성이다.

카드에서는 이렇게 읽힌다:
- 헤더: `vs 탈퇴한 사용자 · 8월 12일`
- 미션 행 라벨: `탈퇴한 사용자의 미션`

**어색하지만 성립하고, 뜻이 정확하다.**

🔴 **뱃지·톤다운·회색 처리 같은 특별 표시를 넣지 않는다.** 근거 3가지:

1. **보관함은 증거 보존 화면이고, 상대가 탈퇴했다는 사실이 그 증거를 약화시키지 않는다.**
   내가 그날 이겼다는 것은 상대의 계정 상태와 무관하다.
2. **특별 표시는 *"이 기록은 무효"* 로 읽힌다.** 톤다운한 카드는 화면 안에서 *"덜 유효한 항목"* 의
   자리를 차지한다 — 정반대의 뜻이 전달된다.
3. **닉네임 자체가 이미 사실을 말한다.** 표시를 하나 더 얹으면 같은 말을 두 번 한다.

→ **앱에 `isWithdrawn` 같은 플래그를 요구하지 않는다**(§7). 받으면 쓰게 되고, 쓰면 위 문제가 생긴다.

- 이니셜 아바타는 §2.4 카드에 **없다**(홈 카드처럼 `"vs {닉네임}"` 텍스트만) — 탈퇴자의 이니셜이
  `"탈"` 이 되는 문제도 함께 사라진다.
- 🔴 **상세 화면에는 아바타가 있다.** 거기서는 `ContractParty.nickname` 이 `"탈퇴한 사용자"` 라
  이니셜이 `"탈"` 이 된다. **이번에 고치지 않는다** — 깨지지 않고, 상세는 이 feature 의 화면이 아니다.
  ⚠️ §6-⑪.

#### §2.5.2.1 🔴 탈퇴자의 인증 사진 — 삭제가 **"로드 실패"의 어휘를 빌려 쓴다**

> 🔴 **2026-08-26 정정.** 이 절의 초판은 *"절대 성공하지 않는 '다시 시도' 버튼이 영구히 뜬다"* 로
> 썼는데, **그 결론은 서버가 `photo_url` 을 non-null 로 남긴다는 내 가정 위에 서 있었다.**
> mypage-backend 가 *"파일과 함께 `verifications.photo_url` 도 NULL 로 만든다"* 로 정정했고,
> 실측하면 그 경로에는 **재시도 버튼이 붙지 않는다.** 정정 경위는 §2.5.2.2.

[spec 수용 기준](./spec.md)의 *"탈퇴한 사용자의 인증 사진 요청은 깨지지 않는 실패로 처리되고
화면이 대체 표시를 낸다"* — **깨지지는 않는다.** 남는 문제는 **어휘**다.

`VerificationPhoto.kt:68-79` 의 분기는 `status` 와 `photoUrl` **둘만** 본다. 서버가 `photo_url` 을
NULL 로 만들면 `:78` 로 떨어진다:

```kotlin
// 인증은 됐는데 URL 이 없는 건 정상 경로가 아니다. (…)
photoUrl == null -> PhotoMessage(LOAD_FAILED_TEXT)      // "사진을 불러오지 못했어요"
```

문제 2가지:

1. 문구가 **일시적 오류의 어휘**(*"불러오지 못했어요"*)인데 실제로는 **영구·정상 종결 상태**다.
2. 🔴 **그 자리는 이미 다른 뜻으로 쓰이고 있다** — 주석이 *"정상 경로가 아니다"* 라고 못박은
   **진짜 데이터 이상**의 자리다. 두 사건이 같은 문구를 공유하면 **진짜 이상이 탈퇴자 뒤에 숨는다.**

**2번이 이 요구의 진짜 근거다.** 1번만이면 문구 교체로 끝나지만, 2번은 **신호를 나누지 않으면
풀리지 않는다.** 그리고 이 컴포넌트의 KDoc 이 정확히 그 축을 지키려고 쓰여 있다 —
*"실패를 조용히 빈 칸으로 삼키면 그 사고가 QA 를 그대로 통과한다."*

→ **계약 요구 (§7-⑤).** 등급은 **blocking 이 아니라 문구·신호 정확성**이다(초판의 blocking 표기는
재시도 버튼 전제와 함께 철회). 앱이 그릴 문구는 **`"탈퇴한 사용자의 사진은 삭제됐어요"`**(제안, §6-⑫)이고
**재시도 버튼이 붙지 않는다** — 이건 초판과 같다.

⚠️ **이건 보관함이 아니라 상세 화면의 표시다.** 보관함 카드에는 사진이 없다(§2.4).
이 feature 가 만든 상태이므로 이 문서가 정의하지만, 구현은 `:feature:challenge:detail` 에서 일어난다
(pm-lead 판정: **T-M4 범위 포함** — 탈퇴 수용 기준의 일부다).

#### §2.5.2.2 🔴 해법 — **`photoDeleted` 필드 추가.** 조합 재정의를 채택하지 않는다

두 안이 있었다. **pm-lead 가 조합 재정의를 우선 검토하라고 지시**했고, 검토한 결과 **채택하지 않는 쪽을
권고**한다. 근거는 아래다.

| | 안 | 성격 |
|---|---|---|
| **(A)** | **조합 재정의** — `VERIFIED + photoUrl == null` 의 뜻을 계약에서 *"인증 유효, 사진 삭제됨"* 으로 다시 정의. 신규 필드 0 | 기존 조합의 **의미**를 바꾼다 |
| **(B)** | ✅ **권고** — `photoDeleted: Boolean` **추가**(non-null, 기본 `false`). mypage-backend 제안 | **필드**를 더한다. 기존 필드 의미 변화 0 |

🔴 **(A)를 채택하지 않는 이유 — 진짜 데이터 이상이 삭제로 위장된다.**

(A)로 가면 `VERIFIED + photoUrl == null` 이 **두 사건을 동시에** 가리킨다:
- 탈퇴로 사진이 지워졌다 (정상)
- 인증은 기록됐는데 URL 이 유실됐다 (버그)

그런데 **후자를 위해 이 분기가 만들어졌다.** `VerificationPhoto.kt:76-77` 주석이
*"인증은 됐는데 URL 이 없는 건 정상 경로가 아니다. 빈 칸으로 두면 원인 없는 공백이 되므로 로드 실패와
같은 문구로 드러낸다"* 라고 그 의도를 명시한다. (A)는 **그 감지기를 끄고 그 자리에 정상 상태를 놓는 것**이다.
그 뒤로 URL 유실 버그는 *"탈퇴한 사용자의 사진은 삭제됐어요"* 로 표시되어 **아무도 눈치채지 못한다.**

이건 이 문서가 이미 두 번 내린 판단과 같은 축이다 — §2.5.4(*"조회 실패를 빈 상태로 그리면
'기록이 하나도 없다'는 거짓을 보여준다"*), §1.7(*"실패 시 화면을 비우지 않는다"*).
**mypage-backend 도 독립적으로 같은 결론에 도달했다**(*"두 사건이 같은 문구를 공유하면 진짜 데이터
이상이 탈퇴자 뒤에 숨는다"*).

🔴 **`confirmed` 계약 관점에서도 (B)가 더 안전하다.** 둘 다 challenge-verification 계약을 건드리지만
성격이 다르다:
- **(A) 는 의미 변경**이다. 응답 shape 이 그대로라 **기존 소비자(현재 앱 코드)가 아무 신호 없이 계속
  틀린 뜻으로 읽는다.** 컴파일도 통과하고 스키마 검증도 통과한다.
- **(B) 는 additive** 다. 모르는 소비자는 필드를 무시하고 **기존 동작을 그대로 유지**한다.

*"신규 필드 0"* 이 비용이 낮아 보이지만, **(A)의 비용은 계약이 아니라 관측 가능성에서 나간다.**

**확정 분기표** (mypage-backend 회신 그대로 — 디자인 측 이견 없음):

| `status` | `photoUrl` | `photoDeleted` | 표시 |
|---|---|---|---|
| `VERIFIED` | non-null | `false` | 사진 |
| `VERIFIED` | `null` | **`true`** | **`"탈퇴한 사용자의 사진은 삭제됐어요"`** — 재시도 없음 |
| `VERIFIED` | `null` | `false` | **기존 그대로** `"사진을 불러오지 못했어요"` — 🔴 **진짜 데이터 이상의 자리를 살려 둔다** |
| `PENDING` / `FAILED` | `null` | `false` | 기존 그대로 |

✅ **필드 이름이 `isWithdrawn` 이 아니라 `photoDeleted` 인 것이 중요하다.** §2.5.2 에서 탈퇴 플래그를
거부한 이유(*"받으면 쓰게 되고, 쓰면 카드에 특별 표시가 된다"*)가 여기도 그대로 걸리는데,
`photoDeleted` 는 **사진 자리 하나만 바꾸고 카드·아바타·톤에는 쓸 데가 없다.** 앱이 *"왜"* 가 아니라
*"뭘 그릴지"* 만 받는다. mypage-backend 가 같은 근거를 명시했고, 디자인 측이 동의한다.

⚠️ challenge-verification 의 `confirmed` 계약 변경이므로 그쪽 `change-log.md` 등재 필요
(mypage-backend 소관).

### §2.5.3 🔴 `EXPIRED` — **제외 확정.** 대상은 `COMPLETED` 단일

[api-contract 쟁점](./api-contract.md)은 *"기본 제외 제안"* 이었다. **디자인 측이 확정으로 올린다.**

`EXPIRED` 는 **성립하지 않은 신청**(상대가 수락하지 않아 만료)이라, 이 화면의 카드 문법으로
**그릴 것이 없다**:

| 카드의 칸 | `EXPIRED` 일 때 |
|---|---|
| 상대 닉네임 | ✅ 있다 |
| 내 미션 | ✅ 있다 |
| **상대 미션** | ❌ **없다** — `ContractParty.mission` 이 null (*"아직 맹세하지 않았으면 null — `PENDING` 구간의 정상 상태"*) |
| 내기 | ✅ 있다 |
| **결과 pill** | ❌ **없다** — `result == null` |
| **계약서** | ❌ **없다** — `ChallengeDetail.contract` 가 null |

**네 칸 중 둘이 비고, 화면 이름인 "계약서"가 아예 없다.** 그리고 탭해서 들어간 상세도 계약서가 없다.
*"이때 너 이거 걸었잖아"* 의 증거가 성립하지 않는다 — **아무도 걸지 않았다.**

→ **대상 상태 = `COMPLETED` 단일.** 이 판정이 §2.4.2(결과 pill 항상 non-null)의 전제이기도 하다.

⚠️ 취소·만료된 신청의 이력이 필요하다는 요구가 나오면 **별도 화면**이다(축이 다르다 — 여기는 결과,
그쪽은 시도). §4.

### §2.5.4 화면 상태 3종

> 🔴 **2026-08-26 개정.** 초판의 *"실패 = 스낵바 + 로딩 직전 상태 유지"* 는 **첫 진입에서 성립하지
> 않는다** — 유지할 "로딩 직전 상태"가 없어서 **스낵바 1회 + 무한 스피너**가 되는데, 그건
> **§1.7.2 가 마이페이지에서 기각한 바로 그 상태**다. mypage-mobile 발견. 판정은 §2.5.4.1.

| 상태 | 표현 |
|---|---|
| 로딩 | 중앙 `CircularProgressIndicator(color = primary)` — `FriendsScreen.kt:74-81` 패턴 |
| 정상 | §2.3 골격 |
| **실패** | 🔴 **목록 자리에 인라인 실패 카드 + "다시 시도" CTA.** 스피너를 멈추고, **스낵바는 띄우지 않는다** — §2.5.4.1 |

- 🔴 **`EmptyStateCard` 를 빈 상태 문구로 실패에 재사용하지 마라.** 0건과 조회 실패는 다른 사실이고,
  실패를 빈 상태로 그리면 *"기록이 하나도 없다"* 는 **거짓**을 보여준다 — 증거 보관 화면에서
  가장 나쁜 실패 형태다. **골격(카드 레이아웃)은 공유하되 문구·아이콘·CTA 가 전부 다르다.**

#### §2.5.4.1 🔴 네 번째 상태가 필요하다 — 그리고 **앱에 선례가 이미 있다**

세 가지가 전부 막혀 있었다: 빈 상태로 그리기(위 금지) / 화면 전체 Error(§1.7.2 기각) /
스낵바 + 스피너 유지(§1.7.2 기각). **셋을 다 피하면 남는 것이 인라인 실패 카드다.**

**§1.7.3 의 원칙(성공한 데이터는 살리고 실패 영역만 대체)을 보관함에 적용하면 이렇게 된다**:
🔴 **보관함에는 성공한 데이터가 없다.** 화면이 그 목록 하나다(상단바는 데이터가 아니다).
→ **실패 영역 = 목록 영역 전체.** 그래서 마이페이지와 달리 카드 하나가 화면을 채우는 형태가 되지만,
**이건 "화면 Error 상태"와 다르다** — §1.7.2 가 2안을 기각한 사유(*"성공한 데이터까지 못 쓰게 된다"*)가
**여기서는 성립하지 않는다.** 잃을 성공 데이터가 애초에 없다.

✅ **`FriendPickPlaceholderCard` 가 이미 정확히 이 카드다** (실측, `:feature:challenge:create`):

```
title = "친구 목록을 불러오지 못했어요"   subtitle = "잠시 후 다시 시도해주세요"
ctaLabel = "다시 시도"                  ctaIcon = Icons.Filled.Refresh
```

그 파일 KDoc 이 *"빈 상태는 친구 추가, 실패는 재시도 — 아이콘까지 호출부가 정한다"* 라고
**빈 상태와 실패를 한 컴포넌트로 가르는 설계 의도**까지 적어 뒀다.

⚠️ **그래서 §1.7 의 *"Error 상태 선례가 없다"* 는 절반만 맞았다.** 없는 것은
**목록 탭의 화면 전체 Error** 이고(홈·친구·랭킹이 스낵바), **인라인 실패 카드 + 재시도 선례는 있다.**
§1.7 의 그 문장은 마이페이지에 대해서는 여전히 유효하지만(거기는 성공 데이터가 있다),
**보관함에 그대로 적용하면 안 된다.**

**확정 값** — `EmptyStateCard`(`:core:ui`) 골격 재사용, 값만 교체:

| | 빈 상태 (§2.5.1) | **실패 (신규)** |
|---|---|---|
| 아이콘 | `Icons.Filled.Description` | 🔴 **`Icons.Filled.CloudOff`** — 문서 아이콘을 쓰면 빈 상태와 구분이 안 된다 |
| 제목 | `"아직 끝낸 챌린지가 없어요"` | `"보관함을 불러오지 못했어요"` |
| 부제 | `"챌린지가 끝나면 계약서가 여기 쌓여요"` | `"잠시 후 다시 시도해주세요"` |
| CTA | `"챌린지 만들기"` + `SportsKabaddi` → 생성 화면 | `"다시 시도"` + `Icons.Filled.Refresh` → **재조회** |

- 🔴 **재시도 버튼이 여기엔 반드시 필요하다.** 마이페이지에서 뺀 사유(*"탭이라 재진입이 재시도"*,
  §1.7)가 **보관함에는 성립하지 않는다** — push 된 하위 화면이라 재시도하려면 **뒤로 갔다 다시
  들어와야** 하고, 뒤로 가는 순간 **실패했다는 사실도 화면과 함께 사라진다.**
- 🔴 **스낵바를 띄우지 않는다.** 화면 전체가 이미 실패를 말하고 있어 **같은 말을 두 번** 하게 된다.
  ⚠️ **마이페이지(§1.7)가 스낵바를 유지하는 것과 어긋나지 않는다** — 거기는 실패 표시가 **카드 안
  한 줄**이라 놓치기 쉽고, 나머지 화면이 정상 동작해서 사용자가 실패를 모른 채 지나갈 수 있다.
  **규칙: 실패 표시가 화면의 주 내용을 차지하면 스낵바를 생략하고, 부분 표시면 병행한다.**

🔴 **바로 위 "스낵바를 띄우지 않는다" 는 조회 실패(아무것도 못 받음)에만 걸린다 —
`onError` 전체를 막지 마라.** 이 문장을 통째로 적용하면 **부분 매핑 실패 알림까지 죽는다.**

`ChallengeRemoteDataSourceImpl.getChallengeHistories` 는 `droppedCount > 0` 일 때
**성공 emit 과 함께** `onError` 를 부르므로, **`onError` 한 채널이 두 사건을 나른다**:

| 사건 | 표현 |
|---|---|
| 조회 실패 (아무것도 못 받음) | 실패 카드 — **스낵바 없음** |
| **부분 실패** (목록은 뜨는데 몇 건 드롭) | 목록 + **스낵바 병행** |

**두 번째 행도 위 규칙의 문면 그대로다** — 부분 실패는 화면 표시가 0이라
스낵바가 "병행"이 아니라 **유일한 채널**이다. 판정 근거·문구·지속 표시 여부는 §2.5.4.2.

⚠️ **이 경고를 §2.5.4.2 로 미루지 않고 여기 둔 이유**: 실제로 그 사고가 났다.
mypage-mobile 이 **이 절만 읽고 문면대로 이행해** 부분 실패 알림을 함께 껐다.
**지시가 있는 자리에 예외도 있어야 한다.**

#### §2.5.4.2 🔴 부분 실패에는 스낵바를 **되살린다** — 내 판정이 신호 하나를 죽였다

**mypage-mobile 발견(2026-08-26).** §2.5.4.1 의 *"스낵바를 띄우지 마라"* 를 문면대로 이행했더니,
**부분 매핑 실패 알림까지 같이 사라졌다.**

`ChallengeRemoteDataSourceImpl.getChallengeHistories` 는 매퍼가 항목을 걸렀을 때(`droppedCount > 0`)
**성공 emit 과 함께** `onError("일부 항목을 불러오지 못했어요")` 를 부른다. 즉 `onError` 한 통로가
**두 사건**을 나른다:

| 사건 | 내 판정을 문면대로 적용하면 |
|---|---|
| 조회 실패 (아무것도 못 받음) | ✅ 실패 카드 — 의도대로 |
| **부분 실패 (목록은 뜨는데 몇 건이 드롭)** | 🔴 **아무 표시도 없음** |

**판정: 부분 실패 경로에서만 스낵바를 되살린다.** 규칙을 바꾸는 것이 아니라 **규칙의 전제가 여기서
성립하지 않는다**: §2.5.4.1 의 규칙은 *"실패가 화면에 이미 그려져 있는데 스낵바가 같은 말을 반복하나"*
를 묻는 것이다. **부분 실패는 화면에 표시가 0이라 스낵바가 "병행"이 아니라 유일한 채널이다.**

🔴 **이 feature 에서 같은 실패가 세 번째다 — 한 신호가 두 사건을 나른다:**

| | 신호 | 두 사건 |
|---|---|---|
| §2.5.2.1 | `photoUrl == null` | 탈퇴 삭제 / URL 유실 버그 |
| §1.7·§2.5.4 | "실패" 표현 | 조회 실패 / 빈 상태(0건) |
| **§2.5.4.2** | **`onError`** | **조회 실패 / 부분 실패** |

앞의 둘에서 *"두 사건이 같은 표시를 공유하면 하나가 다른 하나 뒤에 숨는다"* 로 신호를 나눴다.
**같은 판단을 여기에도 적용한다.**

⚠️ **그리고 이건 §3.2.1-⑤ 를 승인한 내 판단과 맞물린다.** 보관함 매퍼가 홈과 반대로 **항목을
드롭**하는 것을 *"날짜와 결과가 카드의 뼈대라 없으면 그릴 자리가 없다"* 로 승인했는데,
**드롭을 정당화한 논리가 곧 "드롭이 실제로 일어난다"는 뜻**이다. 일어나는데 아무도 모르면 안 된다.

**mypage-mobile 이 낸 대안 (b) "현행 유지 + 문서에 *드롭은 조용히 일어난다* 명시" 는 기각한다.**
🔴 **보관함은 *"이게 네 기록 전부다"* 라고 주장하는 화면**이다(백로그 "결과 히스토리 화면 부재"의
해법이고 기획 §3.3 증거 보관의 이행이다). 몇 건이 조용히 빠지면 **그 주장 자체가 거짓**이 되고,
사용자에게는 확인할 방법이 없다. 문서에 적는 것은 **개발자만 아는 사실**로 만들 뿐이다.
§2.5.4 가 *"기록이 하나도 없다는 거짓이 가장 나쁘다"* 로 금지한 것의 부분 판이다.

##### 문구 — 🔴 **기존 `"일부 항목을 불러오지 못했어요"` 를 그대로 쓴다.** 보관함용으로 다듬지 마라

실측: 이 문자열은 데이터소스에 하드코딩돼 있고 **3개 메서드가 공유**한다 —
`getReceivedChallenges` · `getChallengeHistories`(`ChallengeRemoteDataSourceImpl.kt:34,47`) ·
`ActiveChallengeRemoteDataSourceImpl.kt:23`. 테스트도 그 문자열을 고정하고 있다.

→ **보관함만 바꾸면 같은 사건이 화면마다 다른 말을 한다.** 바꾸려면 데이터소스가 문자열을 호출부에서
받아야 하고, 그러면 **홈·active 를 포함한 3개 호출부 + 테스트**가 함께 움직인다 —
보관함 하나 때문에 열 범위가 아니다.
⚠️ *"항목"이 개발자 어휘*라는 지적은 타당하지만 **전 화면 공통 사안**이지 이 feature 의 판정이 아니다.
**백로그로도 올리지 않는다** — 실제로 오독됐다는 근거가 없다.

##### 화면에 지속 표시를 추가하지 않는다 (스낵바만)

목록 어딘가에 *"일부를 불러오지 못했어요"* 를 **상시로 붙이지 않는다.** 근거:
1. **홈·active 가 같은 사건에 스낵바만 쓴다.** 보관함만 UI 를 늘리면 방언이 생긴다.
2. 🔴 **드롭은 정상 상태가 아니라 계약 위반 신호다.** `myResult`·`challengeDate` 는 계약상
   non-null 이므로(§7-④) 드롭이 발생했다는 건 **서버가 계약을 어겼다**는 뜻이다.
   정상이 아닌 것에 영구 UI 자리를 만들면 **그것이 정상처럼 보인다.**
3. §2.5.4.1 의 실패 카드는 *"그릴 것이 그것뿐"* 이라 화면을 차지했지만, 여기는 **그릴 것(목록)이 있다.**

⚠️ **남는 위험은 인정하고 넘어간다**: 스낵바가 사라지면 사용자는 불완전한 목록을 완전하다고 믿는다.
그 대응은 **UI 가 아니라 계약·매퍼 쪽**이다 — 드롭이 실제로 관측되면 그건 화면을 고칠 일이 아니라
**서버 응답을 고칠 일**이고, 스낵바는 그 관측을 가능하게 하는 최소 장치다.

#### §3.3.1 `BetStrip` 승격 — 사본을 만들지 않는다

`BetStrip.kt:31` 은 `internal` 이라 보관함에서 쓸 수 없다. 그대로 두면 **보관함이 사본을 뜬다.**

**승격이 안전한 이유**: 이미 완전히 파라미터화돼 있다 — `text: String` 하나뿐이고, KDoc 이
*"포맷팅은 호출부(State)의 책임"* 이라고 명시한다. **렌더 코드를 한 줄도 바꾸지 않고 파일만 옮기고
`internal` → `public` 으로 여는 것**이라 홈 화면의 픽셀이 변하지 않는다. 바뀌는 건 import 한 줄이다.
(`EmptyStateCard` 승격과 같은 성격 — [loser-ranking §4.4](../loser-ranking/design.md))

🔴 **KDoc 을 고쳐라.** 현재 *"[ChallengeCard] 와 [ReceivedChallengeCard] 가 픽셀 동일하게 공유한다"*
인데, 승격 후엔 보관함 카드도 호출부다. 안 고치면 **다음 사람이 홈 전용으로 오독하고 또 사본을 뜬다** —
[loser-ranking §4.4.1](../loser-ranking/design.md) 이 발견한 EmptyState 사본 3개가 정확히 그 경로였다.

#### §3.3.2 `ConfirmDialog` 신설 — `PermissionSettingsDialog` 를 건드리지 않는다

앱의 `AlertDialog` 사용처는 현재 **`PermissionSettingsDialog` 1곳뿐**이다. 탈퇴 확인이 2번째다.

`PermissionSettingsDialog` 를 일반화하지 않는 이유:
- 이름·문구(`"설정 열기"` / `"나중에"`)가 권한 전용으로 굳어 있고, **출시된 화면이 쓰고 있다.**
- 🔴 **버튼 색 배치가 반대다** — 권한 쪽은 confirm=`primary`, 여기는 confirm=`error` /
  dismiss=`primary`(§1.6). 파라미터로 열면 시그니처가 색 2개만큼 넓어지고, 그러면 **호출부마다
  다른 색 조합을 넘길 수 있게 되어** 위계 규칙이 컴포넌트 밖으로 새어 나간다.

→ **`ConfirmDialog` 를 `:core:ui` 에 신설**하고 **`PermissionSettingsDialog` 는 그대로 둔다.**
두 다이얼로그의 통합은 3번째 사용처가 생길 때 판단할 별건이다 → **pm-lead 백로그 등재**(§9).
([loser-ranking §4.4](../loser-ranking/design.md) 가 `HomeEmptyState` 를 안 건드린 것과 같은 처리)

**시그니처 (제안)**:

```
ConfirmDialog(
    title: String,
    message: String,
    confirmLabel: String,
    onConfirm: () -> Unit,
    onDismiss: () -> Unit,
    modifier: Modifier = Modifier,
    dismissLabel: String = "취소",
    destructive: Boolean = false,   // true 면 confirm=error / dismiss=primary
)
```

🔴 **색을 개별 파라미터로 열지 말고 `destructive: Boolean` 한 개로 묶어라.** 그래야 §1.6 의
위계 규칙(*"파괴적 액션에서는 안전한 쪽이 먼저 눈에 들어온다"*)이 **컴포넌트 안에 남는다.**

### §3.4 🔴 `materialIconsExtended` 의존이 없다

`feature/mypage/build.gradle.kts` 는 **6줄짜리 빈 껍데기**다. `:core:designsystem` 이 갖고 있지만
`implementation` 이라 전이되지 않는다 — 홈·랭킹이 각자 선언했다(`feature/ranking/build.gradle.kts` 에
사유 주석까지 달려 있다).

→ `Description` / `KeyboardArrowRight` / `Logout` / `SportsKabaddi` 를 쓰려면
**마이페이지 모듈에도 선언해야 한다.**

[colors.md](../../design-system/colors.md)에 `success` 슬롯이 있고 값도 있는데,
**Lovable 안에서 `text-success` 의 쓰임이 일관되지 않다**:

| 자리 | 승을 무슨 색으로 |
|---|---|
| `mypage.tsx:45` 프로필 카드 | `text-success` |
| `index.tsx:139` 홈 StatsBar | `text-primary` |
| `mypage.tsx:69,77` 캘린더 성공 셀 | `text-success` / `bg-success/20` |

프로필 카드도 `primary` 로 보냈으므로, **`success` 는 이번에도 미사용으로 남는다.**

⚠️ **tokens.md §8 확인 항목에 올릴 대상은 아니다** — `success` 는 `VerificationStatusPill` 등
인증 축에서 쓰일 여지가 있어 chart 5색처럼 닫을 수 없다. **다만 "승 = success" 라는 정본의
한 줄이 앱 관례와 어긋난다는 사실은 §6-① 에 확인 대상으로 올렸다.**
디자이너가 `success` 쪽으로 뒤집으면 **홈 StatsBar 까지 함께 바뀌어야 한다** — 그건 이 feature 범위 밖이다.

### §5.2 ⚠️ 미적용으로 남는 항목 2건 (기존 미결, 이 화면이 만든 문제 아님)

| ⑬ | **월 섹션 헤더 `stickyHeader`** — 정본에 없다 | sticky 로 진행 (§2.3.2). 월 이동 UI 를 뺀 대가를 이게 갚는다. 구현 부담이 크면 일반 `item` 허용 |
| ⑭ | 🔴 **조회 단위 — 월 이동 UI 를 만들지 않는다** | **전체 + 월 섹션 헤더**로 진행 (§2.1). 사용자 지시 문면("월별로 조회")보다 의도("월별로 정리")를 따랐다. **이 항목만은 사용자 재확인 가치가 있다** — pm-lead 판단 |
| ⑯ | **전적 조회 실패 문구** — 정본에 없다 | `"전적을 불러오지 못했어요"` 제안 (§1.7.3). 승/패/무 행은 그리지 않는다 |
| ⑮ | 🔴 **승률 분모 — 정본의 산수를 버렸다.** 정본은 `7승 3패 2무 · 70%` = `win/(win+lose)` 인데, 랭킹 패율은 서버 실측상 분모가 `totalChallenges`(무 포함)다. 그대로 두면 같은 사용자가 **승률 70% / 패율 25%** 로 두 탭에서 합이 112% 가 된다 | **`win + lose + draw` 로 통일** — 위 사용자는 58% (§1.2.5.1). 정본 수(70)보다 낮아 보이는 것이 유일한 단점. 🔴 **정본 쪽을 고수하면 랭킹 패율 분모도 바꿔야 하고, 그건 `confirmed` 계약 개정 + 정렬 3차 키 변경이다** — 한 화면만 정할 수 없다 |

> ✅ **①~⑬·⑮·⑯ 은 위 제안값으로 진행 확정** (⑧ 은 확인 대상이 아니라 문서 내부 모순이었고 닫혔다). 디자이너 확인을 기다리지 않는다 — 지금 이 화면들을
> 만들려면 어차피 그 값들이 필요하고, 제안값이 전부 보수적이라 뒤집혀도 교체 비용이 작다.
> (⑮ 는 뒤집히면 비용이 크지만, **뒤집는 쪽이 계약 개정이라** 기본값은 계약을 지키는 쪽이어야 한다.)
>
> ⚠️ **⑭ 는 성격이 다르다.** 사용자가 직접 준 지시("월별로 조회")의 **문면에서 벗어난** 유일한
> 항목이라, pm-lead 가 사용자에게 한 번 확인할 가치가 있다. 다만 **확인을 기다리며 멈추지는 않는다** —
> 뒤집혀도 서버는 파라미터 하나가 붙고 앱은 월 이동 UI 가 추가되는 것이라 카드·헤더는 그대로 산다.
>
> 🔴 **표에서 지우지 마라.** *"진행 확정"* 은 *"디자이너가 승인했다"* 가 아니라 **확인을 기다리지 않고
> 구현한다**는 뜻이다. 지우면 나중에 이 값들이 디자이너가 정한 값인지 우리가 정한 값인지 구분할 수 없다.

| ⑦ | **페이지네이션** | **미적용 권고.** 넣는다면 **커서** — 월 오프셋 페이지는 금지 | §2.1. 프로젝트 관례(친구·active·랭킹 전부 비페이지네이션)와 같다. 재검토 임계치를 숫자로 박는 것은 찬성(랭킹 선례) |
| ⑧ | **진행 중 챌린지 보유자 탈퇴** | **자연 판정 권장에 찬성** | 보관함에 영향 없다 — `COMPLETED` 만 담고, 배치가 판정하면 그때 들어온다. 상대 화면에서 `vs 탈퇴한 사용자` 로 정상 표시 |
| ⑨ | **프로필 카드** | **계약 변경 0.** `GET /record` + `UserInfo` 그대로. **서버가 승률을 계산해 줄 필요 없다** | §1.2.5. 총 챌린지·승률 둘 다 `UserRecord` 4값에서 도출된다. 🔴 **승률 분모 = `win + lose + draw`** — 서버 `totalChallenges` 와 같은 값이라(`UserRecord.kt:114` 불변식) 랭킹 패율과 분모가 일치한다. 반올림 방향도 `LoserRanking.kt:68` 과 맞춘다 (§1.2.5.1·§1.2.5.2) |

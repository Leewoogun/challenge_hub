### spec.md — 🔴 pm 자기 정정 3건

착수 후 드러난 내 오류다. 셋 다 **팀원이 잡았고**, 셋 다 조용히 틀리는 종류였다.

**① §3.1 *"동시 기권은 저절로 닫힌다"* — 순차에서만 참이었다** (적발: backend-dev)

원문은 *"첫 기권이 즉시 `COMPLETED` 라 두 번째는 `IN_PROGRESS` 게이트에 걸린다"*. READ COMMITTED
에서 동시 요청 둘은 **양쪽 다 `IN_PROGRESS` 를 읽고 통과**한다. 전적이 두 번 오르고
`total_challenges` 는 소급 정정이 불가능하다.

🔴 **더 나쁜 건 spec 이 스스로 모순이었다는 것이다** — §3 수용 기준은 처음부터 *"동시 요청으로
검증하라"* 를 요구하고 있었다. 한쪽을 읽은 사람은 테스트를 쓰고 다른 쪽을 읽은 사람은 안 쓴다.
→ §3.1 서두에 *"각 칸이 순차에서만 참인지 동시성에서도 참인지 갈라서 확인하라"* 를 넣고,
*"가드를 넣지 마라 는 **관측되지 않은** 위험에 대한 규칙이지 관측된 구조적 결함까지 덮으라는 뜻이
아니다"* 를 명시.

**② §3 수용 기준 `referencePending = false` — 두 겹으로 틀렸다** (적발: forfeit-mobile)

ⓐ 계약 확정값은 `null` ⓑ **더 근본적으로 값이 근거가 아니다** — 앱은 `isTappableInList` 에서 타입이
먼저 결론을 내고 «조건부» 인 타입만 그 필드를 본다.

🔴 **값만 `null` 로 고쳤다면 여전히 틀린 것을 검증했을 것이다.** 값을 단언하는 테스트는 서버가 값을
바꾸는 날 깨지는데, **정작 보장해야 할 것(타입 단계 비탭)은 그대로 참이다** — 그 테스트는 보장이
아니라 무관한 값을 감시하게 된다. → *"타입에서 곧바로 `false` + `true`/`false`/`null` 세 값 전부에서
결과 동일"* 로 교체.

⚠️ **이건 이론이 아니라 실제 피해를 냈다** — 이 기준을 그대로 받은 mobile 의 child 지시서에 `false` 가
실려 나갔고, **child 가 계약 파일을 5줄 더 읽고 이견을 내서** 잡혔다. (구현된 테스트는 처음부터
세 값을 돌고 있었다 — 중복 추가 없음)

**③ `ChallengeOutcome` KDoc 초안에 관점 한정 누락** (적발: mobile 의 child)

내가 *"기권하면 `OPPONENT_WIN`"* 이라고 단정했으나 `ChallengeResult` 는 **역할 기준**이라 내가
opponent 면 `CHALLENGER_WIN` 이다. 하필 **역산이 틀린 답을 낸다고 경고하는 문장**에서 역할을
안 따졌다. → *"내가 challenger 인데"* 한정 추가.
🔑 backend 실캡처가 이 함정을 실증한다 — **opponent 가 기권했더니 `CHALLENGER_WIN`** 이었다.
